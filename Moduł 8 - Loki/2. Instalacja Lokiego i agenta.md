# Instalacja Lokiego i agenta

Od czystej maszyny do działającego zbierania logów Apache. Wszystko z pakietów APT z repozytorium Grafany — bez binarek z GitHuba i bez ręcznie pisanych unitów systemd.

Wykonane na maszynie szkoleniowej **vmobserv15** (`10.123.3.215`); zrzuty i liczby pochodzą z tej instalacji.

| | |
|---|---|
| Loki | 3.7.7 (pakiet z repozytorium Grafany) |
| Agent | **Grafana Alloy** 1.19.2 |
| Grafana | 13.2.1 (już zainstalowana) |
| Źródło logów | Apache 2 — `access.log` i `error.log` |
| Porty | Loki `3100`, Alloy UI `12345`, Grafana `3000` |

---

## Krok 1. Instalacja

Loki jest w **repozytorium APT Grafany** — jeśli masz już zainstalowaną Grafanę z pakietu, repo jest na miejscu i nic nie trzeba dodawać.

```bash
# jeśli repo Grafany jeszcze nie ma:
sudo mkdir -p /etc/apt/keyrings
wget -qO - https://apt.grafana.com/gpg.key | sudo gpg --dearmor -o /etc/apt/keyrings/grafana.gpg
echo "deb [signed-by=/etc/apt/keyrings/grafana.gpg] https://apt.grafana.com stable main" \
  | sudo tee /etc/apt/sources.list.d/grafana.list
sudo apt update

# instalacja Lokiego i agenta naraz
sudo apt install -y loki alloy
```

Sprawdź, co wpadło:

```bash
dpkg -l loki alloy | grep ^ii
# loki   3.7.7
# alloy  1.19.2-1
```

Pakiety zakładają użytkowników systemowych, katalogi i unity systemd — nie trzeba pisać ich ręcznie.

## Krok 2. Konfiguracja Lokiego

### ⚠️ Domyślna konfiguracja trzyma dane w `/tmp`

Pakiet instaluje `/etc/loki/config.yml`, w którym stoi:

```yaml
common:
  path_prefix: /tmp/loki
  storage:
    filesystem:
      chunks_directory: /tmp/loki/chunks
      rules_directory: /tmp/loki/rules
```

`/tmp` jest czyszczony przy restarcie systemu (a na wielu systemach to tmpfs w RAM-ie). **Po pierwszym reboocie stracisz wszystkie logi.** To pierwsza rzecz do poprawienia — i dobry moment, żeby na szkoleniu pokazać, że domyślna konfiguracja pakietu jest demonstracyjna, nie produkcyjna.

```bash
sudo cp /etc/loki/config.yml /etc/loki/config.yml.orig

sudo sed -i 's|/tmp/loki|/var/lib/loki|g; s|log_level: debug|log_level: info|' \
  /etc/loki/config.yml

sudo mkdir -p /var/lib/loki/chunks /var/lib/loki/rules
sudo chown -R loki:nogroup /var/lib/loki
```

> **Uwaga na grupę.** Pakiet zakłada użytkownika `loki`, ale **nie zakłada grupy `loki`** — konto ma grupę `nogroup`. `chown -R loki:loki` zwróci `błędna grupa: "loki:loki"` i katalog zostanie bez właściciela, przez co Loki nie wystartuje. Właściwe jest `loki:nogroup`.

Przy okazji zmieniamy `log_level` z `debug` na `info` — domyślny debug zasypuje journal.

### Start

```bash
sudo systemctl enable --now loki
curl -s http://localhost:3100/ready
```

Pierwsze kilkanaście sekund `ready` zwraca `Ingester not ready: waiting for 15s after being ready` — to normalne, ingester ma celowe opóźnienie startowe. Po chwili odpowiada `ready`.

Szybki test, że działa:

```bash
curl -s http://localhost:3100/metrics | grep -c loki_    # kilkaset metryk
```

### Test bez agenta

Zanim wejdzie agent, warto pokazać grupie, że Loki to zwykłe API HTTP — można do niego wepchnąć log ręcznie:

```bash
# wyślij testowy log
curl -s -XPOST http://localhost:3100/loki/api/v1/push \
  -H "Content-Type: application/json" \
  --data-raw '{"streams":[{"stream":{"job":"test"},"values":[["'$(date +%s)000000000'","hello loki"]]}]}'

# odpytaj o niego
curl -sG http://localhost:3100/loki/api/v1/query --data-urlencode 'query={job="test"}'
```

Zwrócenie linii `hello loki` oznacza, że magazyn działa. To również najkrótsza demonstracja modelu push: **nadawca ustala etykiety**, Lokiego nie obchodzi, kto przysłał dane. Wrócimy do tego przy bezpieczeństwie w rozdziale [6](6.%20Agent%20na%20drugiej%20maszynie.md).

## Krok 3. Konfiguracja Alloya — tu się dzieją etykiety

To jest najważniejszy plik w całej instalacji. Cały `/etc/alloy/config.alloy`:

```alloy
// ---------------------------------------------------------------------------
// 1. WYKRYWANIE PLIKÓW + ETYKIETY STATYCZNE
// ---------------------------------------------------------------------------
local.file_match "apache" {
  path_targets = [
    {
      __path__ = "/var/log/apache2/access.log",
      job      = "apache",
      log_type = "access",
      env      = "szkolenie",
      host     = constants.hostname,
    },
    {
      __path__ = "/var/log/apache2/error.log",
      job      = "apache",
      log_type = "error",
      env      = "szkolenie",
      host     = constants.hostname,
    },
  ]
}

// ---------------------------------------------------------------------------
// 2. CZYTANIE PLIKÓW
// ---------------------------------------------------------------------------
loki.source.file "apache" {
  targets    = local.file_match.apache.targets
  forward_to = [loki.process.apache.receiver]
}

// ---------------------------------------------------------------------------
// 3. PRZETWARZANIE
// ---------------------------------------------------------------------------
loki.process "apache" {

  stage.match {
    selector = "{log_type=\"access\"}"

    stage.regex {
      expression = "^(?P<clientip>\\S+) \\S+ (?P<remote_user>\\S+) \\[(?P<ts>[^\\]]+)\\] \"(?P<method>[A-Z]+) (?P<path>\\S+) (?P<proto>[^\"]*)\" (?P<status>\\d{3}) (?P<bytes>\\S+)"
    }

    stage.timestamp {
      source = "ts"
      format = "02/Jan/2006:15:04:05 -0700"
    }

    // ETYKIETY — pola o MAŁEJ liczbie możliwych wartości
    stage.labels {
      values = { method = "", status = "" }
    }

    // STRUCTURED METADATA — pola WYSOKOKARDYNALNE
    stage.structured_metadata {
      values = { clientip = "", path = "" }
    }
  }

  forward_to = [loki.write.default.receiver]
}

// ---------------------------------------------------------------------------
// 4. WYSYŁKA
// ---------------------------------------------------------------------------
loki.write "default" {
  endpoint {
    url = "http://localhost:3100/loki/api/v1/push"
  }
}
```

### Co robi każdy blok

**`local.file_match`** — wykrywa pliki i przypina im etykiety statyczne. Wszystko, co wpiszesz obok `__path__`, staje się etykietą strumienia. `constants.hostname` podstawia nazwę maszyny, dzięki czemu ta sama konfiguracja działa na każdym hoście bez zmian.

**`loki.source.file`** — tailuje pliki, pilnuje pozycji (żeby po restarcie nie czytać od początku), obsługuje rotację.

**`stage.match`** — ogranicza dalsze przetwarzanie do wybranych strumieni. Logi dostępowe Apache mają format Combined, a błędy zupełnie inny — nie ma sensu przepuszczać błędów przez regexp przeznaczony dla accessów.

**`stage.regex`** — rozbija linię na nazwane pola. Pola wyekstrahowane **nie stają się automatycznie niczym** — trafiają do wewnętrznej mapy, z której korzystają kolejne etapy.

**`stage.timestamp`** — bierze czas z treści logu zamiast z momentu odczytu pliku. Bez tego przy pierwszym uruchomieniu cała historia pliku dostałaby znacznik „teraz" i na wykresie zobaczyłbyś jeden gigantyczny słupek. Format podaje się w konwencji Go (`02/Jan/2006` to referencyjna data, nie przykład).

**`stage.labels`** — dopiero to zamienia wyekstrahowane pole w etykietę.

**`stage.structured_metadata`** — nowość Lokiego 3: pole zapisane przy linii, po którym da się filtrować w LogQL, ale **które nie tworzy nowego strumienia**.

Podział pól między `stage.labels` a `stage.structured_metadata` to najważniejsza decyzja w tym pliku. Uzasadnienie i pełna mechanika — [4. Etykiety i kardynalność](4.%20Etykiety%20i%20kardynalno%C5%9B%C4%87.md).

### Uprawnienia

Logi Apache mają uprawnienia `root:adm 640`. Pakiet Alloya dodaje swojego użytkownika do grup `adm` i `systemd-journal` przy instalacji, więc zwykle nic nie trzeba robić — ale warto zweryfikować, bo to najczęstsza przyczyna „agent działa, a logów nie ma":

```bash
id alloy
# uid=995(alloy) gid=988(alloy) grupy=988(alloy),4(adm),999(systemd-journal)
```

Gdyby brakowało: `sudo usermod -aG adm alloy && sudo systemctl restart alloy`.

### Walidacja i start

Alloy potrafi sprawdzić składnię, zanim wystartujesz usługę:

```bash
sudo alloy fmt /etc/alloy/config.alloy > /dev/null && echo "składnia OK"
sudo systemctl enable --now alloy
sudo journalctl -u alloy -n 20 --no-pager
```

W logu szukasz dwóch rzeczy: `{^_^} Alloy is running` oraz `start tailing file` dla każdego pliku.

## Krok 4. Interfejs Alloya

Alloy ma własne UI z grafem pipeline'u. Domyślnie słucha tylko na `127.0.0.1:12345`. Na maszynie szkoleniowej wygodniej wystawić je szerzej:

```bash
# /etc/default/alloy
CUSTOM_ARGS="--server.http.listen-addr=0.0.0.0:12345"
```

```bash
sudo systemctl restart alloy
```

> W produkcji **nie wystawiaj tego portu** bez ograniczenia dostępu — UI pokazuje pełną konfigurację agenta razem z adresami i nazwami komponentów.

![Graf pipeline'u w UI Alloya](/grafiki/m8-09-alloy-ui@2x.png)

Graf pokazuje dokładnie to, co napisaliśmy w konfiguracji: cztery komponenty połączone sygnałem `Logs`, od wykrycia plików po zapis do Lokiego. Liczba na krawędzi (tu `0.2`) to przepływ w liniach na sekundę — świetne narzędzie diagnostyczne: jeśli gdzieś przepływ spada do zera, wiesz, na którym etapie logi giną.

## Krok 5. Weryfikacja z terminala

Zanim wejdziesz do Grafany, warto pokazać grupie, że Loki to zwykłe API.

```bash
# jakie etykiety w ogóle istnieją
curl -s "http://localhost:3100/loki/api/v1/labels" | python3 -m json.tool
```

```json
["__stream_shard__", "env", "filename", "host", "job",
 "log_type", "method", "service_name", "status"]
```

Dwie etykiety, których nie wpisaliśmy:

- **`service_name`** — Loki 3 dokłada ją automatycznie, zgadując nazwę usługi z `job` lub `app`. Służy do automatycznego grupowania w Grafana Drilldown.
- **`__stream_shard__`** — wewnętrzny podział strumienia o dużym wolumenie na kilka równoległych. Nie nadajesz jej ręcznie i nie używasz w zapytaniach.

```bash
# jakie wartości ma konkretna etykieta
curl -s "http://localhost:3100/loki/api/v1/label/status/values"
# {"status":"success","data":["200","301","302","304","403","404","412"]}

# ile strumieni powstało
curl -s --get "http://localhost:3100/loki/api/v1/series" \
  --data-urlencode 'match[]={job="apache"}' | python3 -m json.tool | head -20
```

Na naszej maszynie wyszło **7 strumieni** — to iloczyn kombinacji etykiet, które faktycznie wystąpiły: `log_type` × `method` × `status` (plus osobny strumień dla `error.log`, który nie ma `method` ani `status`, bo nie przeszedł przez regexp).

## Pułapki

| Objaw | Przyczyna | Naprawa |
|---|---|---|
| Logi znikają po restarcie maszyny | domyślny `path_prefix: /tmp/loki` | przestaw na `/var/lib/loki` |
| Loki nie startuje po zmianie katalogu | `chown loki:loki` zawodzi — nie ma grupy `loki` | `chown -R loki:nogroup` |
| `Ingester not ready: waiting for 15s` | normalne opóźnienie startowe | odczekaj kilkanaście sekund |
| `bind: address already in use` | port 3100 zajęty | `sudo ss -tlnp \| grep 3100`, zatrzymaj kolidujący proces |
| Agent działa, brak logów | brak uprawnień do plików | `usermod -aG adm alloy` |
| Cała historia z jednym znacznikiem czasu | brak `stage.timestamp` | dodaj etap z formatem Go |
| Etykiety `method`/`status` puste dla `error.log` | regexp dotyczy tylko formatu Combined | to poprawne — `stage.match` odsiewa błędy |
| Alloy nie wstaje po edycji configu | błąd składni | `alloy fmt /etc/alloy/config.alloy` przed restartem |
