# Agent na drugiej maszynie

Dokładanie kolejnego hosta do istniejącej instalacji. Serwer z Lokim i Grafaną już stoi ([rozdział 2](2.%20Instalacja%20Lokiego%20i%20agenta.md)) — teraz stawiamy agenta na kliencie i uczymy go wysyłać logi na serwer.

To jest moment, w którym etykiety zaprojektowane w [rozdziale 4](4.%20Etykiety%20i%20kardynalno%C5%9B%C4%87.md) zaczynają zarabiać na siebie: dwie maszyny, dwa różne serwery WWW, jeden spójny zestaw zapytań.

| | Serwer | Klient |
|---|---|---|
| Adres | `10.123.3.215` | `10.123.3.90` |
| Hostname | `szkolenie` | `monitoring` |
| System | Ubuntu 24.04 | Ubuntu 24.04.3 |
| Rola | Loki `:3100`, Prometheus `:9090`, Grafana `:3000` | źródło logów |
| Serwer WWW | Apache | **nginx** |

---

## Jak to będzie działać

Najważniejsza rzecz do zrozumienia: **logi i metryki płyną w przeciwnych kierunkach.**

```
KLIENT 10.123.3.90                          SERWER 10.123.3.215

  Alloy ──────── push logów ──────────────▶  Loki :3100
                                                 │
  node_exporter :9100  ◀──── pull metryk ──── Prometheus :9090
                                                 │
                                             Grafana :3000 ◀── pyta oba
```

**Loki to model push** — agent sam wysyła, serwer czeka. Klient musi dosięgnąć serwera na porcie 3100.

**Prometheus to model pull** — serwer sam dobija się po metryki. Serwer musi dosięgnąć klienta na porcie 9100. To już działa; klient jest wśród celów Prometheusa jako `szkolenie_klient`.

Ta asymetria ma praktyczne konsekwencje przy projektowaniu sieci i reguł firewalla — warto ją na sali narysować, zanim ktoś zacznie szukać, dlaczego „monitoring nie działa" w jedną stronę.

## Krok 0. Warunki wstępne

Dwie rzeczy sprawdź **zanim** zaczniesz instalować — obie potrafią zmarnować pół godziny.

### Zegary

```bash
# na serwerze
date
# na kliencie
date
```

Muszą się zgadzać. Jeśli zegar klienta odbiega, jego logi wylądują z przesuniętymi znacznikami czasu, a przy większej różnicy Loki je **odrzuci** komunikatem `400: entry too far behind`. Naprawa: `sudo timedatectl set-ntp true`.

> Stan zweryfikowany: serwer `11:31:11`, klient `11:31:12` — różnica 1 sekunda, w porządku.

### Łączność do Lokiego

Z klienta:

```bash
curl -s http://10.123.3.215:3100/ready
```

Ma zwrócić `ready`. Jeśli nic nie wraca — firewall albo Loki nasłuchuje tylko na localhoście (sprawdź `http_listen_port` i `ss -tlnp | grep 3100` na serwerze).

> Stan zweryfikowany: `HTTP 200`, Loki osiągalny z klienta.

## Krok 1. Repozytorium Grafany

Na kliencie **go jeszcze nie ma** — są tylko repozytoria Ubuntu i Zabbiksa. Trzeba dodać:

```bash
sudo mkdir -p /etc/apt/keyrings
wget -qO - https://apt.grafana.com/gpg.key \
  | sudo gpg --dearmor -o /etc/apt/keyrings/grafana.gpg

echo "deb [signed-by=/etc/apt/keyrings/grafana.gpg] https://apt.grafana.com stable main" \
  | sudo tee /etc/apt/sources.list.d/grafana.list

sudo apt update
```

## Krok 2. Instalacja Alloya

```bash
sudo apt install -y alloy
dpkg -l alloy | grep ^ii
```

Na kliencie **nie instalujemy Lokiego** — magazyn jest jeden, na serwerze. Agent tylko czyta i wysyła.

## Krok 3. Uprawnienia

Logi nginx mają uprawnienia `640` i grupę `adm`. Alloy musi do niej należeć:

```bash
id alloy
```

Pakiet dopisuje go przy instalacji. Gdyby brakowało:

```bash
sudo usermod -aG adm alloy
```

## Krok 4. Konfiguracja

```bash
sudo nano /etc/alloy/config.alloy
```

Zastąp całą zawartość:

```alloy
// ===========================================================================
// ŹRÓDŁO — LOGI NGINX
// ===========================================================================
local.file_match "nginx" {
  path_targets = [
    {
      __path__ = "/var/log/nginx/access.log",
      job      = "nginx",
      log_type = "access",
      env      = "szkolenie",
      host     = constants.hostname,
    },
    {
      __path__ = "/var/log/nginx/error.log",
      job      = "nginx",
      log_type = "error",
      env      = "szkolenie",
      host     = constants.hostname,
    },
  ]
}

loki.source.file "nginx" {
  targets    = local.file_match.nginx.targets
  forward_to = [loki.process.nginx.receiver]
}

// ===========================================================================
// PRZETWARZANIE
// ===========================================================================
loki.process "nginx" {
  stage.match {
    selector = "{log_type=\"access\"}"

    stage.regex {
      expression = "^(?P<clientip>\\S+) \\S+ (?P<remote_user>\\S+) \\[(?P<ts>[^\\]]+)\\] \"(?P<method>[A-Z]+) (?P<path>\\S+) (?P<proto>[^\"]*)\" (?P<status>\\d{3}) (?P<bytes>\\S+)"
    }

    stage.timestamp {
      source = "ts"
      format = "02/Jan/2006:15:04:05 -0700"
    }

    stage.labels {
      values = { method = "", status = "" }
    }

    stage.structured_metadata {
      values = { clientip = "", path = "" }
    }
  }

  forward_to = [loki.write.default.receiver]
}

// ===========================================================================
// WYSYŁKA — TU JEST CAŁA RÓŻNICA WOBEC SERWERA
// ===========================================================================
loki.write "default" {
  endpoint {
    url = "http://10.123.3.215:3100/loki/api/v1/push"
  }
}
```

### Co się zmieniło wobec konfiguracji serwera

**Tylko dwie rzeczy.** Warto to na sali podkreślić, bo pokazuje, że konfiguracja agenta jest przenośna:

1. **Adres w `loki.write`** — `10.123.3.215:3100` zamiast `localhost:3100`. To jedyna zmiana architektoniczna.
2. **Ścieżki i `job`** — `/var/log/nginx/` i `job = "nginx"` zamiast Apache.

Etapy parsowania są **identyczne**, bo domyślny format `combined` w nginksie jest zgodny z Apache Combined Log Format. Ten sam regexp obsłuży oba.

> **Uwaga na hostname.** Ten klient nazywa się `monitoring`, więc `constants.hostname` da etykietę `host="monitoring"` — mimo że to maszyna kliencka. Mylące, ale prawdziwe. Jeśli chcesz czytelniejszą nazwę, wpisz ją wprost zamiast `constants.hostname`, tylko pamiętaj, żeby przy kopiowaniu configu na kolejne maszyny za każdym razem ją zmienić.

## Krok 5. Walidacja i start

```bash
sudo alloy fmt /etc/alloy/config.alloy > /dev/null && echo "składnia OK"
sudo systemctl enable --now alloy
sudo systemctl status alloy --no-pager
```

## Krok 6. Weryfikacja z obu stron

### Na kliencie — czy agent czyta i wysyła

```bash
sudo journalctl -u alloy -n 20 --no-pager | grep -iE "tailing|error"
```

Szukasz `start tailing file` dla obu plików i braku błędów.

Metryki samego agenta:

```bash
curl -s http://localhost:12345/metrics | grep -E "loki_write_(sent|dropped)_entries_total"
```

- `sent` rośnie → Loki przyjmuje.
- `dropped` rośnie → coś odrzuca, sprawdź journal po treść błędu.

### Na serwerze — czy dane dotarły

```bash
curl -s http://localhost:3100/loki/api/v1/label/job/values
curl -s http://localhost:3100/loki/api/v1/label/host/values
```

Powinny dojść: `nginx` w `job` i `monitoring` w `host`.

### W Grafanie

```logql
{job="nginx"}
{host="monitoring"}
```

## Krok 7. Zapytania, dla których to wszystko robimy

Teraz, przy dwóch hostach w jednym Lokim, etykiety zaczynają zarabiać na siebie:

```logql
# wszystko z obu maszyn
{env="szkolenie"}

# tylko klient
{host="monitoring"}

# porównanie ruchu na obu maszynach na jednym wykresie
sum by (host) (rate({env="szkolenie", log_type="access"}[5m]))

# błędy 4xx/5xx niezależnie od tego, który serwer WWW je wygenerował
{env="szkolenie", status=~"4..|5.."}

# rozbicie po serwerze WWW
sum by (job, status) (rate({env="szkolenie", log_type="access"}[5m]))
```

Ostatnie zapytanie to dobra puenta: **jeden wykres, dwie maszyny, dwa różne serwery WWW**, a składnia identyczna — bo etykiety zostały zaprojektowane spójnie na obu hostach.

To jest praktyczny argument za tym, żeby zestaw etykiet ustalić **raz, dla całej instalacji**, zanim wjedzie trzecia i dziesiąta maszyna. Poprawianie tego później oznacza dziurę w danych na granicy zmiany (patrz [rozdział 4, sekcja 5](4.%20Etykiety%20i%20kardynalno%C5%9B%C4%87.md)).

## Pułapki

| Objaw | Przyczyna | Naprawa |
|---|---|---|
| `dropped_entries` rośnie, `400: entry too far behind` | rozjechane zegary | `timedatectl set-ntp true` na obu |
| Agent czyta, ale nic nie dociera | port 3100 zablokowany | `curl http://10.123.3.215:3100/ready` z klienta |
| `read_lines` = 0 | brak uprawnień do `/var/log/nginx` | `usermod -aG adm alloy` |
| Logi z dwóch maszyn się zlewają | ten sam hostname (klon VM) | zmień hostname albo wpisz `host` na sztywno |
| Etykiety `method`/`status` puste | inny format logu nginx niż `combined` | dostosuj regexp do własnego `log_format` |
| Brak pakietu `alloy` | brak repozytorium Grafany | wróć do kroku 1 |

## Bezpieczeństwo — o czym powiedzieć grupie

Loki na serwerze ma `auth_enabled: false` i nasłuchuje na wszystkich interfejsach. Znaczy to, że **każdy, kto dosięgnie portu 3100, może wpychać logi** — bez hasła, pod dowolnymi etykietami. Może też podszyć się pod inny host, bo etykiety ustala nadawca.

Na labie to wygodne i w porządku. W produkcji stosuje się jedno z trzech:

- reverse proxy przed Lokim z basic authem (u nas naturalnie: NPM),
- `auth_enabled: true` i nagłówek `X-Scope-OrgID` na każdej maszynie (multi-tenancy),
- ograniczenie dostępu do portu 3100 firewallem do znanych adresów agentów.

## Opcjonalnie: metryki też przez push

Metryki z klienta już płyną — Prometheus je ciągnie z `10.123.3.90:9100`. Gdybyś chciał ujednolicić i mieć oba sygnały w modelu push, na kliencie dokładasz:

```alloy
prometheus.exporter.unix "host" { }

prometheus.scrape "host" {
  targets    = prometheus.exporter.unix.host.targets
  forward_to = [prometheus.remote_write.default.receiver]
}

prometheus.remote_write "default" {
  endpoint {
    url = "http://10.123.3.215:9090/api/v1/write"
  }
}
```

`prometheus.exporter.unix` to node_exporter wbudowany w Alloya — zastąpiłby osobną usługę `prometheus-node-exporter` na kliencie.

⚠️ **To wymaga zmiany na serwerze.** Prometheus nie ma teraz włączonego odbiornika remote-write (`POST /api/v1/write` zwraca 404). Trzeba dodać do `ARGS` w `/etc/default/prometheus`:

```
--web.enable-remote-write-receiver
```

Na tej instalacji **nie ma potrzeby tego robić** — pull działa i nic nie jest zepsute. Wariant push ma sens przy nowych maszynach albo gdy agent siedzi za NAT-em i serwer nie może się do niego dobić.
