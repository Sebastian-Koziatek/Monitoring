# Etykiety i kardynalność

Najważniejszy rozdział w tym module. Wszystko inne w Lokim da się odkręcić — źle dobrane etykiety nie.

Tu wchodzimy w mechanizm: skąd etykieta się bierze, w którym momencie powstaje, jak ją dołożyć, zmienić i usunąć — oraz jak podpiąć drugie źródło (dziennik systemd), bo to najlepszy poligon do ćwiczeń z etykietami.

Wszystkie liczby i zrzuty pochodzą z działającej instalacji na **vmobserv15**.

---

## 1. Etykieta, strumień, chunk

Trzy pojęcia, bez których reszta się nie klei.

**Etykieta** to para klucz–wartość przypięta do linii logu, np. `job="apache"`.

**Strumień (stream)** to **unikalny zestaw etykiet**. Nie plik, nie usługa, nie host — dokładnie zestaw etykiet. Te dwie linie trafią do dwóch różnych strumieni:

```
{job="apache", status="200"}   ← strumień A
{job="apache", status="404"}   ← strumień B
```

**Chunk** to skompresowana paczka linii należących do jednego strumienia, zamykana po zapełnieniu albo po upływie czasu.

Loki indeksuje **wyłącznie zestawy etykiet**. Treść linii nie jest indeksowana w ogóle. Zapytanie przebiega tak:

```
{job="apache", status="404"} |= "timeout"
└──────────── 1 ───────────┘ └──── 2 ────┘

1. selektor → indeks wskazuje strumienie i ich chunki     (szybkie, mały indeks)
2. filtr    → chunki są rozpakowywane i przeszukiwane     (kosztowne, liniowe)
```

Stąd bierze się cała dyscyplina wokół etykiet: **to, co jest etykietą, filtruje się za darmo; wszystko inne kosztuje rozpakowanie chunków**.

## 2. Pięć miejsc, w których powstaje etykieta

To jest mapa, do której warto wracać. W naszej konfiguracji występują wszystkie pięć.

| # | Mechanizm | Gdzie w configu | Przykład u nas |
|---|---|---|---|
| 1 | **statyczna przy źródle** | `local.file_match` → `path_targets` | `job`, `log_type`, `env`, `host` |
| 2 | **z relabelingu metadanych** | `loki.relabel` → `rule` | `unit`, `level` (z journald) |
| 3 | **z parsowania linii** | `stage.regex` + `stage.labels` | `method`, `status` |
| 4 | **wyliczona** | `stage.template` + `stage.labels` | `status_class` (2xx/4xx) |
| 5 | **stała w pipeline** | `stage.static_labels` | `datacenter` |

Do tego dochodzą etykiety, których **nie nadajesz** — dokłada je sam Loki albo Grafana:

- **`service_name`** — Loki 3 zgaduje ją z `job`/`app`/`service`. Napędza Grafana Drilldown.
- **`filename`** — dokłada `loki.source.file`, żeby dało się odróżnić pliki w obrębie zadania.
- **`__stream_shard__`** — wewnętrzny podział bardzo ruchliwego strumienia na równoległe. Nie używasz jej w zapytaniach.
- **`detected_level`** — to **nie jest** etykieta w Lokim. Grafana zgaduje poziom logu z treści linii już po pobraniu danych. Stąd `UNK` przy liniach bez słowa `error`/`warn`/`info`.

## 3. Mechanizmy po kolei, na naszym configu

### 3.1. Etykieta statyczna przy źródle

Najprostsza. Wszystko, co wpiszesz obok `__path__`, staje się etykietą:

```alloy
local.file_match "apache" {
  path_targets = [
    {
      __path__ = "/var/log/apache2/access.log",
      job      = "apache",
      log_type = "access",
      env      = "szkolenie",
      host     = constants.hostname,     // podstawia nazwę maszyny
    },
  ]
}
```

`constants.hostname` to wbudowana zmienna Alloya — dzięki niej ta sama konfiguracja działa na każdym hoście bez edycji. Promtail nie ma odpowiednika; tam wpisujesz nazwę na sztywno albo używasz `${HOSTNAME}` z flagą `-config.expand-env=true`.

### 3.2. Etykieta z parsowania linii

Dwa etapy, i to jest miejsce, w którym ludzie najczęściej się mylą:

```alloy
stage.regex {
  expression = "... (?P<method>[A-Z]+) (?P<path>\\S+) ... (?P<status>\\d{3}) ..."
}

stage.labels {
  values = { method = "", status = "" }
}
```

**`stage.regex` sam z siebie nie tworzy żadnej etykiety.** Wyciągnięte pola lądują w wewnętrznej mapie, która żyje tylko na czas przetwarzania tej linii. Dopiero `stage.labels` promuje wybrane pola na etykiety.

Pusty łańcuch po prawej (`method = ""`) znaczy „weź pole o tej samej nazwie". Gdybyś chciał przemianować, piszesz `metoda = "method"`.

To rozdzielenie jest celowe: zwykle parsujesz **więcej** pól, niż chcesz mieć etykiet. U nas regexp wyciąga siedem pól, a etykietami zostają trzy.

### 3.3. Etykieta wyliczona

Czasem potrzebujesz etykiety, której nie ma wprost w linii. `stage.template` liczy ją z pól już wyciągniętych:

```alloy
stage.template {
  source   = "status_class"
  template = "{{ if .status }}{{ printf \"%.1s\" .status }}xx{{ end }}"
}
```

`source` to nazwa pola, które ma powstać. Szablon bierze pierwszy znak z `status` i dokleja `xx`, czyli `200 → 2xx`, `404 → 4xx`. Potem `status_class` trafia do `stage.labels` jak każde inne pole.

Po co, skoro jest już `status`? Bo `{status_class="4xx"}` filtruje po **jednej** etykiecie zamiast po regexpie `{status=~"4.."}`. Pierwsze działa na indeksie, drugie też, ale czytelniej i taniej jest mieć gotową klasę.

> **Uwaga na szablony.** Funkcja `slice` bywa zawodna w tym kontekście — w trakcie przygotowania tych materiałów `{{ slice .status 0 1 }}` nie wyprodukowało niczego i etykieta po prostu nie powstała, bez żadnego błędu w logu. `printf "%.1s"` działa pewnie. Jeśli etykieta nie pojawia się w Lokim, a config jest poprawny składniowo, podejrzewaj cichy błąd szablonu.

### 3.4. Etykieta stała w pipeline

```alloy
stage.static_labels {
  values = { datacenter = "homelab" }
}
```

Doklejana do **każdej** linii przechodzącej przez ten `loki.process`, niezależnie od tego, czy cokolwiek się sparsowało. Dobre na `datacenter`, `cluster`, `tenant` — rzeczy stałe dla całej instalacji. Kardynalność rośnie o czynnik 1, więc jest darmowa.

### 3.5. Etykieta z relabelingu

To mechanizm dla źródeł, które **same dostarczają metadane**: journald, Docker, Kubernetes. Opisany w następnej sekcji, bo tam ma sens.

## 4. Drugie źródło: dziennik systemd

Pliki to jedno, ale prawdziwa siła journalda polega na tym, że **każdy wpis ma już kilkadziesiąt pól metadanych** — nazwę unitu, PID, UID, priorytet, nazwę hosta. Tylko trzeba je przepisać na etykiety.

### 4.1. Konfiguracja

```alloy
// Reguły relabelingu. forward_to = [] bo ten komponent niczego nie przesyła —
// istnieje tylko po to, żeby wyeksportować .rules do źródła journala.
loki.relabel "journal" {
  forward_to = []

  rule {
    source_labels = ["__journal__systemd_unit"]
    target_label  = "unit"
  }

  rule {
    source_labels = ["__journal_priority_keyword"]
    target_label  = "level"
  }

  rule {
    source_labels = ["__journal__hostname"]
    target_label  = "host"
  }

  // job trzeba wymusić regułą — argument "labels" przegrywa z domyślnym
  // job = <id komponentu>, który ustawia sam loki.source.journal
  rule {
    target_label = "job"
    replacement  = "systemd-journal"
  }
}

loki.source.journal "system" {
  path          = "/var/log/journal"
  max_age       = "12h"
  relabel_rules = loki.relabel.journal.rules
  labels        = { env = "szkolenie" }
  forward_to    = [loki.write.default.receiver]
}
```

### 4.2. Skąd te dziwne nazwy pól

journald nazywa swoje pola wielkimi literami z podkreśleniami (`_SYSTEMD_UNIT`, `PRIORITY`, `_HOSTNAME`). Agent przepisuje je na `__journal_` + nazwa małymi literami. Pola „zaufane" (te, które nadaje samo systemd, a nie aplikacja) mają dodatkowe podkreślenie:

| Pole journald | Nazwa w agencie | Co zawiera |
|---|---|---|
| `_SYSTEMD_UNIT` | `__journal__systemd_unit` | `sshd.service`, `loki.service` |
| `PRIORITY` | `__journal_priority` | `0`–`7` |
| — | `__journal_priority_keyword` | `err`, `warning`, `info`, `debug` |
| `_HOSTNAME` | `__journal__hostname` | nazwa maszyny |
| `SYSLOG_IDENTIFIER` | `__journal_syslog_identifier` | nazwa programu |
| `_PID` | `__journal__pid` | PID procesu |
| `_TRANSPORT` | `__journal__transport` | `stdout`, `journal`, `kernel` |

**Wszystko, czego nie przepiszesz regułą, przepada.** To jest celowe — gdyby agent zamieniał wszystkie pola na etykiety, `_PID` samo wysadziłoby kardynalność.

### 4.3. Trzy rzeczy, które nie zadziałają za pierwszym razem

**Uprawnienia.** Agent musi należeć do grupy `systemd-journal`. Pakiet Alloya dopisuje go przy instalacji, ale warto sprawdzić:

```bash
id alloy
# uid=995(alloy) gid=988(alloy) grupy=988(alloy),4(adm),999(systemd-journal)
```

**Etykieta `job` jest nadpisywana.** `loki.source.journal` ustawia `job` na identyfikator komponentu (`loki.source.journal.system`) i wygrywa to z argumentem `labels`. Widać to w Label browserze jako trzecią, niechcianą wartość. Rozwiązanie to reguła relabelingu z `replacement`, jak wyżej.

**Pętla logów.** Loki i Alloy logują własną pracę do journala. Loki zapisuje te wpisy, co generuje kolejne wpisy, i tak w kółko. U nas dało to **16 800 linii na godzinę** — przy 250 żądaniach HTTP wygenerowanych ręcznie. Prawie wszystko to własne logi stosu.

Lekarstwo: odsiej hałaśliwe unity regułą z akcją `drop`:

```alloy
rule {
  source_labels = ["__journal__systemd_unit"]
  regex         = "(loki|alloy|grafana-server)\\.service"
  action        = "drop"
}
```

Alternatywnie podnieś `log_level` tych usług albo ogranicz `max_age`.

### 4.4. Efekt

![Logi z journala w Grafanie](/grafiki/m8-12-journal-logi@2x.png)

Etykiety `unit`, `level`, `host`, `job`, `env` — wszystkie po 100%. Zapytania, które od razu mają sens:

```logql
{job="systemd-journal", unit="sshd.service"}
{job="systemd-journal", level="err"}
{job="systemd-journal", unit=~"loki|alloy"} |= "error"
sum by (unit) (rate({job="systemd-journal", level="err"}[5m]))
```

Ostatnie to gotowy wykres „błędy na sekundę wg usługi" — bez żadnego eksportera.

### 4.5. To samo w Promtailu

Dla spójności z [rozdziałem 5](5.%20Wariant%20z%20Promtailem.md):

```yaml
scrape_configs:
  - job_name: journal
    journal:
      path: /var/log/journal
      max_age: 12h
      labels:
        job: systemd-journal
        env: szkolenie
    relabel_configs:
      - source_labels: ['__journal__systemd_unit']
        target_label: 'unit'
      - source_labels: ['__journal_priority_keyword']
        target_label: 'level'
      - source_labels: ['__journal__hostname']
        target_label: 'host'
```

W Promtailu `labels` **nie** jest nadpisywane, więc `job` można ustawić wprost. Użytkownik `promtail` też musi być w grupie `systemd-journal` — pakiet go nie dopisuje.

### 4.6. Przy okazji: Docker

Ten sam wzorzec, inne źródło metadanych:

```alloy
discovery.docker "containers" {
  host = "unix:///var/run/docker.sock"
}

discovery.relabel "containers" {
  targets = discovery.docker.containers.targets

  rule {
    source_labels = ["__meta_docker_container_name"]
    regex         = "/(.*)"
    target_label  = "container"
  }
  rule {
    source_labels = ["__meta_docker_container_label_com_docker_compose_service"]
    target_label  = "compose_service"
  }
}

loki.source.docker "containers" {
  host       = "unix:///var/run/docker.sock"
  targets    = discovery.relabel.containers.output
  labels     = { job = "docker" }
  forward_to = [loki.write.default.receiver]
}
```

Metadane nazywają się `__meta_docker_*` zamiast `__journal_*`, reszta myślenia jest identyczna. W Kubernetesie będzie `__meta_kubernetes_*`.

## 5. Zmiana i usuwanie etykiet

### W agencie

```alloy
// wyrzuć konkretne etykiety
stage.label_drop {
  values = ["filename"]
}

// zostaw TYLKO wymienione
stage.label_keep {
  values = ["job", "log_type", "status"]
}
```

W relabelingu dochodzą akcje:

| Akcja | Działanie |
|---|---|
| `replace` (domyślna) | przepisz `source_labels` → `target_label` |
| `keep` | zostaw tylko cele pasujące do `regex` |
| `drop` | odrzuć cele pasujące do `regex` |
| `labeldrop` | usuń etykiety o nazwach pasujących do `regex` |
| `labelmap` | przepisz hurtowo wg wzorca nazwy |

### Co się dzieje po zmianie etykiet

**Stare strumienie nie znikają.** Dodanie etykiety tworzy nowe strumienie od momentu zmiany; dane sprzed zmiany zostają w starych, ze starym zestawem etykiet. Dlatego po edycji configu zapytanie na szerszym zakresie czasu potrafi zwrócić „dziurę".

Widać to u nas w Label browserze: `job` ma trzy wartości, w tym nieaktualne już `loki.source.journal.system` — resztkę sprzed poprawki. Zniknie, gdy stare chunki wypadną z retencji.

## 6. Etykiety w czasie zapytania

Etykiet nie trzeba ustalać wyłącznie przy zapisie. LogQL umie je tworzyć w locie:

```logql
# wyciągnij pole parserem i użyj jako etykiety tylko w tym zapytaniu
{job="apache"} | logfmt | duration > 200ms

# przemianuj / złóż nową etykietę
{job="apache"} | label_format usluga="{{.job}}-{{.log_type}}"

# usuń etykiety z wyniku (np. żeby agregacja się skleiła)
{job="apache"} | drop filename, __stream_shard__

# zamień pole na wartość liczbową do agregacji
sum by (path) (sum_over_time({job="apache"} | unwrap bytes [5m]))
```

**Kluczowa różnica:** etykiety z czasu zapytania **nie zwiększają kardynalności** i nie powstają żadne nowe strumienie. Kosztują za to procesor przy każdym uruchomieniu zapytania. Etykieta przy zapisie = szybko i na stałe drogo; etykieta przy zapytaniu = elastycznie i drogo za każdym razem.

## 7. Kardynalność — sedno sprawy

**Każda unikalna kombinacja wartości etykiet tworzy osobny strumień.** Strumień to własny zestaw chunków, własne wpisy w indeksie, własny bufor w ingesterze.

Nasza konfiguracja Apache daje:

```
log_type (2) × method (~5) × status (~10)  =  do 100 strumieni
```

W praktyce wyszło **7**, bo większość kombinacji nie wystąpiła. To jest zdrowa liczba.

A teraz wyobraź sobie, że `path` zrobiliśmy etykietą:

```
log_type (2) × method (5) × status (10) × path (tysiące) = dziesiątki tysięcy strumieni
```

Loki zacznie odrzucać zapisy (`Maximum active stream limit exceeded`), ingester będzie zjadał pamięć, a zapytania zwolnią — bo indeks, który miał być mały, przestanie nim być. To samo dotyczy `clientip`, identyfikatorów sesji, `user_id`, `trace_id`.

### Reguła kciuka

| Rodzaj pola | Gdzie to trafia | Przykład |
|---|---|---|
| Kilka–kilkanaście stałych wartości | **etykieta** | `job`, `env`, `host`, `status`, `method`, `log_type` |
| Setki i więcej wartości, ale filtrujesz po nich | **structured metadata** | `path`, `clientip`, `trace_id`, `user_id` |
| Treść, po której szukasz tekstowo | **zostaw w linii** | komunikat błędu, stack trace |

Praktyczne pytanie kontrolne przed dodaniem etykiety: **„czy ta wartość może przyjąć nową, nieznaną wcześniej wartość w trakcie działania systemu?"** Jeśli tak — to nie jest etykieta.

- `status` → nie, kodów HTTP jest skończenie wiele. **Etykieta.**
- `unit` → prawie nie, nowe usługi dochodzą przy wdrożeniach. **Etykieta.**
- `path` → tak, każdy nowy URL to nowa wartość. **Structured metadata.**
- `clientip`, `trace_id`, `user_id`, `session_id` → tak, i to masowo. **Structured metadata.**

### Liczby z tej instalacji

![Label browser z pełną listą etykiet](/grafiki/m8-13-label-browser@2x.png)

Stan po podłączeniu obu źródeł:

| Etykieta | Wartości | Skąd |
|---|---|---|
| `job` | 3 | statyczna (+ resztka po poprawce) |
| `log_type` | 2 | statyczna |
| `env`, `host`, `datacenter` | 1 | statyczne |
| `method` | 3 | z parsowania |
| `status` | 5 | z parsowania |
| `status_class` | 2 | wyliczona |
| `unit` | **29** | relabeling z journala |

Strumienie:

```
{job="apache"}            14 strumieni
{job="systemd-journal"}   12 strumieni
razem w ingesterze        67   (z resztkami po zmianach configu)
```

Teoretyczny iloczyn dla apache to `log_type × method × status × status_class` ≈ 60, ale realnie wystąpiło 14 kombinacji. **To jest normalne** — liczy się to, co faktycznie występuje, nie iloczyn kartezjański. Dlatego szacowanie „na papierze" zawsze wychodzi pesymistycznie, a mierzyć trzeba na żywo.

`unit` z 29 wartościami to górna granica tego, co bym jeszcze nazwał bezpiecznym. Rośnie wolno (nowe unity pojawiają się rzadko) i jest oczywistym wymiarem filtrowania, więc zarabia na siebie.

## 8. Diagnostyka etykiet

```bash
# jakie etykiety w ogóle istnieją
curl -s "http://localhost:3100/loki/api/v1/labels" | python3 -m json.tool

# wartości konkretnej etykiety
curl -s "http://localhost:3100/loki/api/v1/label/unit/values"

# pełne zestawy etykiet (= strumienie) dla selektora
curl -s --get "http://localhost:3100/loki/api/v1/series" \
  --data-urlencode 'match[]={job="systemd-journal"}' | python3 -m json.tool

# ile strumieni ma dany selektor — jedna liczba
curl -s --get "http://localhost:3100/loki/api/v1/series" \
  --data-urlencode 'match[]={job="apache"}' \
  | python3 -c 'import sys,json;print(len(json.load(sys.stdin)["data"]))'

# ile strumieni trzyma ingester — najważniejsza liczba przy podejrzeniu kardynalności
curl -s http://localhost:3100/metrics | grep "^loki_ingester_memory_streams"
```

W Grafanie to samo klikalnie: **Explore → Label browser**. Wybierasz etykiety, widzisz ich wartości i gotowy selektor na dole. Do nauki lepsze niż pisanie LogQL z pamięci.

## 9. Pułapki

| Objaw | Przyczyna | Naprawa |
|---|---|---|
| Etykieta nie powstaje mimo `stage.regex` | brak `stage.labels` — regex tylko wyciąga pola | dodaj `stage.labels` |
| Etykieta wyliczana nie powstaje, brak błędu | cichy błąd szablonu (np. `slice`) | użyj `printf "%.1s"`, sprawdź `stage.template` |
| `job` z journala = `loki.source.journal.system` | komponent nadpisuje argument `labels` | reguła relabelingu z `replacement` |
| Brak logów z journala | agent spoza grupy `systemd-journal` | `usermod -aG systemd-journal <user>` |
| Journald zalewa Lokiego | pętla: Loki loguje swoje logowanie | reguła `action = "drop"` na własne unity |
| `Maximum active stream limit exceeded` | za dużo kombinacji etykiet | przenieś pola do structured metadata |
| Dziura w danych po zmianie configu | nowe etykiety = nowe strumienie | to normalne, stare dane zostają w starych |
| Nieaktualna wartość etykiety nie znika | stare chunki jeszcze żyją | poczekaj na retencję |
| Zapytanie wolne mimo wąskiego wyniku | filtr po treści zamiast po etykiecie | zawęź selektor `{}` |

## 10. Ćwiczenia dla grupy

1. Dodaj etykietę `datacenter` przez `stage.static_labels` i sprawdź w `/api/v1/series`, o ile wzrosła liczba strumieni. (Odpowiedź: o zero — jedna wartość.)
2. Spróbuj zrobić `path` etykietą zamiast structured metadata. Obserwuj `loki_ingester_memory_streams` przez kilka minut i porównaj z wartością wyjściową.
3. Odsiej z journala unity `loki.service` i `alloy.service`, potem porównaj wolumen w Explore przed i po.
4. Zbuduj zapytanie, które pokazuje błędy 5xx Apache obok błędów systemd z tej samej minuty — dwa zapytania w trybie **Split** w Explore.
