# Integracja z Grafaną

Loki jest już uruchomiony i przyjmuje logi Apache ([rozdział 2](2.%20Instalacja%20Lokiego%20i%20agenta.md)). Teraz podłączamy go do Grafany i przechodzimy całą ścieżkę: od pierwszego zapytania w Explore, przez koszt zapytania i metryki liczone z logów, po dashboard i alerty.

Zrzuty pochodzą z instalacji na **vmobserv15** (Grafana 13.2.1, Loki 3.7.7).

---

## Dodanie Lokiego jako data source

### Metoda 1: przez interfejs

**Connections → Data sources → Add data source**, filtr `loki`:

![Wybór typu data source](/grafiki/m8-01-dodaj-datasource@2x.png)

Jedyne pole obowiązkowe to adres:

![Konfiguracja adresu Lokiego](/grafiki/m8-02-konfiguracja-datasource@2x.png)

```
http://localhost:3100
```

Loki i Grafana stoją na tej samej maszynie, więc `localhost` wystarczy. Uwierzytelnienia nie ustawiamy, bo w konfiguracji Lokiego mamy `auth_enabled: false` — pojedyncza instancja bez multi-tenancy.

**Save & test**:

![Potwierdzenie połączenia](/grafiki/m8-03-save-and-test@2x.png)

Warto zwrócić uwagę na dwa pola wyżej na tej stronie:

- **Maximum lines** (domyślnie 1000) — limit linii zwracanych do Explore.
- **Derived fields** — zamienia fragment linii logu w klikalny link, np. `trace_id` → skok do Tempo. To jest ten mechanizm, który spina logi ze śladami.

### Metoda 2: provisioning

Provisioning konfiguruje data source przy starcie Grafany — bez klikania i z konfiguracją trzymaną w repozytorium.

```bash
sudo mkdir -p /etc/grafana/provisioning/datasources
sudo nano /etc/grafana/provisioning/datasources/loki.yaml
```

```yaml
apiVersion: 1

datasources:
  - name: Loki
    type: loki
    access: proxy
    url: http://localhost:3100
    jsonData:
      maxLines: 1000
      derivedFields:
        - datasourceUid: tempo
          matcherRegex: "trace_id=(\\w+)"
          name: TraceID
          url: '$${__value.raw}'
    editable: true
    version: 1
```

| Parametr | Znaczenie |
|---|---|
| `type` | dla Lokiego zawsze `loki` |
| `access` | `proxy` — Grafana łączy się ze swojego backendu, nie z przeglądarki |
| `maxLines` | maksymalna liczba linii zwracanych w zapytaniu |
| `derivedFields` | pola pochodne do korelacji z innymi źródłami |
| `editable` | czy da się edytować przez UI |

```bash
sudo systemctl restart grafana-server
```

### Metoda 3: API

```bash
curl -X POST http://admin:HASLO@localhost:3000/api/datasources \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Loki",
    "type": "loki",
    "url": "http://localhost:3100",
    "access": "proxy",
    "jsonData": { "maxLines": 1000 }
  }'
```

## Explore — anatomia zapytania LogQL

![Explore z podstawowym zapytaniem](/grafiki/m8-04-explore-podstawy@2x.png)

Zapytanie jest najprostsze z możliwych:

```logql
{job="apache", log_type="access"}
```

To jest **selektor strumienia** — obowiązkowa część każdego zapytania LogQL. Nie da się zapytać Lokiego „pokaż wszystkie logi ze słowem error" bez wskazania strumieni; selektor jest tym, co pozwala Lokiemu nie czytać całego dysku.

Co widać na ekranie i o czym warto powiedzieć:

- **Logs volume** — histogram liczby linii w czasie. Widać dwa piki ruchu wygenerowanego skryptem i płaskie tło z odpytywania Zabbixa przez Grafanę co 10 sekund.
- **Panel Fields** po lewej — wszystkie etykiety i pola structured metadata z procentem linii, w których występują. `clientip`, `path` i `status` mają 100%, bo wszystkie linie accessu przeszły przez regexp.
- **Common labels** nad listą — etykiety wspólne dla wszystkich wyników.
- **`detected_level`** — Grafana sama zgaduje poziom logu z treści; stąd znaczniki `UNK` przy liniach, w których nie znalazła ani `error`, ani `warn`, ani `info`. **To nie jest etykieta w Lokim** — powstaje po stronie Grafany, już po pobraniu danych.

### Filtr po etykiecie

```logql
{job="apache", status="404"}
```

![Filtrowanie po etykiecie status](/grafiki/m8-05-filtr-po-etykiecie@2x.png)

To jest **najtańsze możliwe zapytanie**. Loki nie rozpakowuje żadnego chunka poza tymi, które należą do strumieni z `status="404"` — wybór następuje na poziomie indeksu.

To właśnie dlatego `status` zasługuje na bycie etykietą: ma dziesięć wartości, a filtruje się po nim bez przerwy.

## Structured metadata i koszt zapytania

```logql
{job="apache", log_type="access"} | path=~"/zabbix/.*" | status!="200"
```

![Filtr po structured metadata](/grafiki/m8-06-structured-metadata@2x.png)

`path` **nie jest etykietą** — to structured metadata. Filtrowanie po nim działa, ale inaczej: Loki musi najpierw wybrać strumienie po `{job, log_type}`, a potem przejść przez ich zawartość.

Spójrz na **`Total bytes processed`** w obu zrzutach:

| Zapytanie | Przetworzone |
|---|---|
| `{job="apache", log_type="access"}` | **871 kB** |
| `{...} \| path=~"/zabbix/.*" \| status!="200"` | **6,16 MB** |

Siedmiokrotnie więcej, choć wynik jest znacznie węższy (39 linii). To jest liczba, którą warto pokazać grupie na żywo — uczy myślenia o koszcie zapytania lepiej niż jakikolwiek wykład.

Grafana pokazuje też szacunek **przed** wykonaniem: `This query will process approximately 1.0 MiB`.

### Wniosek praktyczny

```logql
# ✅ DOBRE — zawężenie na poziomie indeksu
{job="apache", host="server01", status="404"}

# ❌ ZŁE — ten sam wynik, ale przez rozpakowanie wszystkich chunków
{job="apache"} |= "404" |= "server01"
```

Kolejność myślenia przy pisaniu zapytania: **najpierw zawęź `{}`, potem filtruj treść.**

## Metryki policzone z logów

To jest funkcja, która najbardziej zaskakuje ludzi znających Loki tylko ze słyszenia.

```logql
sum by (status) (rate({job="apache", log_type="access"}[5m]))
```

![Metryki wyliczone z logów](/grafiki/m8-07-metryki-z-logow@2x.png)

Loki zwraca **szereg czasowy**, dokładnie taki jak Prometheus — osobna seria dla każdego kodu odpowiedzi. Bez eksportera, bez instrumentacji aplikacji, wyłącznie z linii logu.

Najczęściej używane funkcje:

| Wyrażenie | Znaczenie |
|---|---|
| `rate({...}[5m])` | linii na sekundę w oknie 5 minut |
| `count_over_time({...}[1h])` | liczba linii w oknie godziny |
| `bytes_rate({...}[5m])` | bajtów na sekundę |
| `sum by (status) (...)` | agregacja po etykiecie |
| `topk(5, sum by (path) (...))` | pięć najczęstszych wartości |

Składnia agregacji jest identyczna jak w PromQL — jeśli grupa przerabiała wcześniej Prometheusa, to jest moment, żeby to podkreślić. Pełna lista funkcji: [7. Ściąga LogQL](7.%20%C5%9Aci%C4%85ga%20LogQL.md).

## Podgląd na żywo

Przycisk **Live** w prawym górnym rogu Explore przełącza na strumieniowanie przez WebSocket:

![Live tail](/grafiki/m8-08-live-tail@2x.png)

Linie dopisują się na bieżąco, na dole masz **Pause**, **Clear logs**, **Exit live mode** oraz informację `Last line received: 5s ago`.

Do demonstracji przydaje się generator ruchu, który sypie żądaniami o różnych kodach odpowiedzi:

```bash
#!/bin/bash
PATHS=("/zabbix/" "/zabbix/index.php" "/nie-ma-takiej-strony" "/admin" "/.env" "/wp-login.php")
AGENTS=("Mozilla/5.0 Firefox/141.0" "curl/8.5.0" "kube-probe/1.29" "Googlebot/2.1")
for i in $(seq 1 "${1:-200}"); do
  p="${PATHS[$((RANDOM % ${#PATHS[@]}))]}"
  a="${AGENTS[$((RANDOM % ${#AGENTS[@]}))]}"
  m="GET"; [ $((RANDOM % 7)) -eq 0 ] && m="POST"
  curl -s -o /dev/null -X "$m" -A "$a" "http://localhost${p}" --max-time 3
  sleep 0.05
done
```

Ścieżki `/admin`, `/.env` i `/wp-login.php` nie są przypadkowe — generują 404 i wyglądają jak typowe skanowanie, więc przy okazji można pokazać, jak wygląda szum botów w logach.

> Live tail przy dużym ruchu potrafi obciążyć przeglądarkę. Do dłuższej obserwacji lepszy jest zwykły zakres z auto-odświeżaniem.

### Log context

Klikając w wybraną linię i wybierając **Show context**, zobaczysz logi bezpośrednio przed nią i po niej — w obrębie tego samego strumienia. Przy diagnozie błędu to zwykle pierwsza rzecz, po którą się sięga.

## Dashboard

![Dashboard z panelami opartymi o Loki](/grafiki/m8-10-dashboard@2x.png)

Cztery panele pokazujące cztery różne sposoby użycia tego samego źródła:

1. **Żądania na sekundę wg kodu odpowiedzi** (`timeseries`) — `sum by (status) (rate(...))`, legenda w trybie tabeli ze średnią i maksimum.
2. **Błędy 4xx/5xx w zakresie** (`stat`) — `sum(count_over_time({... status=~"4..|5.."}[$__range]))`. Zmienna `$__range` podstawia aktualny zakres czasu dashboardu, więc licznik reaguje na time picker. Progi kolorów: zielony → pomarańczowy od 20 → czerwony od 100.
3. **Najczęstsze metody HTTP** (`barchart`) — agregacja instant po etykiecie `method`.
4. **Strumień logów — tylko błędy** (`logs`) — surowe linie z filtrem `status=~"4..|5.."`.

Zestawienie panelu z logami obok wykresu jest tym, co daje Lokiemu przewagę w codziennej pracy: widzisz skok błędów na wykresie i **te same błędy w treści** obok, bez przełączania narzędzia.

> **Zasada doboru zapytania do panelu.** Do wykresu zawsze zapytanie metryczne (`rate`, `count_over_time`), nigdy surowe logi — panel wykresu z zapytaniem logowym albo nie narysuje nic, albo przetworzy znacznie więcej danych, niż potrzeba. Surowe linie mają swój typ panelu: `logs`.

### Import gotowego dashboardu

Dashboard można wgrać przez API zamiast klikać:

```bash
curl -s -u admin:HASLO -H "Content-Type: application/json" \
  -X POST http://localhost:3000/api/dashboards/db -d @dash.json
```

Plik `dash.json` ma strukturę `{"dashboard": {...}, "overwrite": true}`, a w każdym panelu wskazujesz `"datasource": {"type": "loki", "uid": "<uid twojego datasource>"}`. UID znajdziesz w adresie strony konfiguracji datasource'u albo przez `curl -u admin:HASLO http://localhost:3000/api/datasources`.

## Alerty na podstawie logów

Alert w Grafanie potrzebuje **liczby**, a nie linii tekstu — więc regułę buduje się zawsze na zapytaniu metrycznym.

### Tworzenie reguły

1. **Alerting → Alert rules → New alert rule**.
2. Jako źródło wybierz **Loki** i wpisz zapytanie metryczne.
3. Ustaw warunek progowy, interwał ewaluacji i czas trwania (`for`).
4. Wskaż **contact point** i zapisz.

### Przykładowe reguły

```logql
# Wysoki odsetek błędów serwera — więcej niż 1 błąd 5xx na sekundę
sum(rate({job="apache", log_type="access", status=~"5.."}[5m])) > 1

# Jakikolwiek błąd krytyczny w dzienniku systemd
sum(count_over_time({job="systemd-journal", level="err"}[5m])) > 0

# Heartbeat — alarm, gdy logi PRZESTAJĄ płynąć
sum(count_over_time({job="apache"}[10m])) < 1
```

Ostatni przypadek jest wart osobnego komentarza na sali: **brak logów to też incydent**. Alert na ciszę wykrywa padnięty serwer WWW albo zatrzymanego agenta, czego żaden alert „na błędy" nie złapie.

> Loki ma również własny komponent **ruler**, który wykonuje reguły po stronie serwera i wysyła alerty prosto do Alertmanagera (`localhost:9093` jest już wpisany w domyślnej konfiguracji pakietu). To wariant dla instalacji, w których alerty mają działać niezależnie od Grafany.

## Korelacja z metrykami z Prometheusa

Największą wartość Loki daje wtedy, gdy stoi obok Prometheusa w tej samej Grafanie.

**Wspólny dashboard** — panel z obciążeniem CPU (Prometheus) i panel z logami tej samej maszyny (Loki), na jednym zakresie czasu. Przesunięcie time pickera dotyczy obu naraz.

**Data links** — w ustawieniach panelu z metrykami dodajesz link prowadzący do Explore z gotowym zapytaniem:

```
Title: Zobacz logi
URL: /explore?left={"datasource":"Loki","queries":[{"expr":"{host=\"${host}\"}"}]}
```

Klikasz w skok na wykresie metryki i lądujesz w logach tej samej maszyny z tego samego momentu.

**Derived fields** — droga w drugą stronę: z linii logu do śladu w Tempo. Konfiguracja w ustawieniach data source'u (patrz wyżej).

Warunek, żeby to wszystko działało bez tarcia: **spójne nazwy etykiet między Prometheusem a Lokim**. Jeśli w metrykach host nazywa się `instance`, a w logach `host`, każda korelacja wymaga ręcznego tłumaczenia.

## Diagnostyka

### „Data source is not working"

```bash
curl http://localhost:3100/ready              # czy Loki żyje
sudo journalctl -u loki -n 50 --no-pager      # co mówi Loki
sudo journalctl -u grafana-server -n 50       # co mówi Grafana
```

Najczęstsze przyczyny: zły adres URL, Loki nasłuchujący tylko na localhoście przy Grafanie na innej maszynie, firewall.

### „No logs found"

Zanim zaczniesz poprawiać zapytanie, sprawdź, czy dane w ogóle doszły:

```bash
curl -s "http://localhost:3100/loki/api/v1/labels" | python3 -m json.tool
curl -s "http://localhost:3100/loki/api/v1/label/job/values"
```

Jeśli etykiet nie ma — problem jest po stronie agenta, nie Grafany. Wróć do [rozdziału 2](2.%20Instalacja%20Lokiego%20i%20agenta.md).

Jeśli etykiety są, a wynik pusty — najczęściej zakres czasu (logi mają znacznik z treści, nie z momentu odczytu) albo literówka w wartości etykiety. **Label browser** w Explore pokazuje wyłącznie wartości, które faktycznie istnieją — używaj go zamiast pisać selektory z pamięci.

### Powolne zapytania

W kolejności skuteczności:

1. Zawęź selektor `{}` — to jedyna zmiana działająca na poziomie indeksu.
2. Skróć zakres czasu.
3. Zamień zapytanie logowe na metryczne tam, gdzie rysujesz wykres.
4. Przejrzyj etykiety pod kątem kardynalności ([rozdział 4](4.%20Etykiety%20i%20kardynalno%C5%9B%C4%87.md)).

### Timeout

Konfiguracja data source'u → sekcja **HTTP** → **Timeout**. Podnoszenie timeoutu leczy objaw, nie przyczynę — najpierw sprawdź punkty wyżej.

## Podsumowanie

- Data source dodaje się trzema drogami: UI, provisioning (do repozytorium) i API.
- Explore to miejsce, w którym uczysz się LogQL — z **Label browserem** zamiast pisania z pamięci.
- **`Total bytes processed`** to najważniejsza liczba na ekranie: uczy, ile kosztuje zapytanie.
- Metryki liczone z logów dają wykresy bez eksportera i bez instrumentacji.
- Do wykresu — zapytanie metryczne; do linii — panel `logs`.
- Alert buduje się na liczbie; alert na **brak** logów bywa ważniejszy niż alert na błędy.

**Kolejny krok:** mechanika etykiet, drugie źródło logów i kardynalność — [4. Etykiety i kardynalność](4.%20Etykiety%20i%20kardynalno%C5%9B%C4%87.md).
