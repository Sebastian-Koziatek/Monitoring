# Wariant z Promtailem

Ta sama instalacja co w [2. Instalacja Lokiego i agenta](2.%20Instalacja%20Lokiego%20i%20agenta.md), ale logi zbiera **Promtail** zamiast Grafana Alloy.

Po stronie Lokiego i Grafany **nic się nie zmienia** — te same etykiety, te same zapytania LogQL, ten sam dashboard. Różnica dotyczy wyłącznie agenta.

| | |
|---|---|
| Loki | 3.7.7 |
| Agent | **Promtail 3.6.11** |
| Grafana | 13.2.1 |
| Źródło logów | Apache 2 — `access.log` i `error.log` |
| Porty | Loki `3100`, Promtail `9080`, Grafana `3000` |

---

## Kiedy sięgać po tę wersję

Promtail jest **wycofany**. Ostatnie wydanie to `3.6.11` — od Loki 3.7 Promtaila nie ma już w wydaniach projektu, a Grafana Labs kieruje wszystkich na Alloya. Mimo to ten wariant ma sens w trzech sytuacjach:

1. **Utrzymujesz istniejące środowisko.** Promtail stoi w tysiącach wdrożeń i nie zniknie z dnia na dzień. Trzeba umieć go czytać i poprawiać.
2. **Prostota konfiguracji.** YAML Promtaila jest bliższy temu, co ludzie znają z Prometheusa. Alloy wprowadza własny język i graf komponentów — więcej mocy, ale też więcej do wytłumaczenia na sali.
3. **Materiały w sieci.** Ogromna większość tutoriali i wpisów na Stack Overflow dotyczy Promtaila. Grupa i tak na nie trafi.

### Promtail kontra Alloy

| | Promtail | Alloy |
|---|---|---|
| Status | wycofany (ostatnie 3.6.11) | rozwijany |
| Konfiguracja | YAML, płaska struktura | język Alloy, graf komponentów |
| Zakres | tylko logi | logi, metryki, ślady, profile |
| Interfejs | lista celów i pozycji | graf pipeline'u z przepływem |
| Port UI | 9080 | 12345 |
| Uprawnienia po instalacji | **user spoza grupy `adm`** | user już w `adm` i `systemd-journal` |
| Konwersja | — | `alloy convert` czyta configi Promtaila |

Jeśli budujesz coś nowego — Alloy. Jeśli uczysz się czytać cudze wdrożenia — Promtail.

## Krok 1. Loki

Bez zmian względem wersji z Alloyem. W skrócie:

```bash
sudo apt install -y loki

# dane z /tmp na trwały katalog
sudo cp /etc/loki/config.yml /etc/loki/config.yml.orig
sudo sed -i 's|/tmp/loki|/var/lib/loki|g; s|log_level: debug|log_level: info|' /etc/loki/config.yml
sudo mkdir -p /var/lib/loki/chunks /var/lib/loki/rules
sudo chown -R loki:nogroup /var/lib/loki      # UWAGA: nie ma grupy "loki"

sudo systemctl enable --now loki
curl -s http://localhost:3100/ready
```

Szczegóły i uzasadnienie każdej z tych linii są w [rozdziale 2, sekcja „Krok 2"](2.%20Instalacja%20Lokiego%20i%20agenta.md).

## Krok 2. Instalacja Promtaila

Promtail jest w tym samym repozytorium APT co Loki i Grafana:

```bash
sudo apt install -y promtail
dpkg -l promtail | grep ^ii
# promtail  3.6.11
```

> Nie potrzebujesz binarki z GitHuba. Repozytorium `apt.grafana.com` nadal serwuje `promtail` w wersji **3.6.11** — ostatniej przed wycofaniem.

### ⚠️ Trzy pułapki pakietu, wszystkie naraz

**1. Usługa startuje sama przy instalacji, z domyślną konfiguracją.**

`dpkg` uruchamia `promtail.service` zaraz po rozpakowaniu. Jeśli potem podmienisz `/etc/promtail/config.yml` i wykonasz `systemctl enable --now promtail`, **nic się nie stanie** — usługa już działa, a `--now` na aktywnym unicie nie przeładowuje konfiguracji. Promtail dalej czyta `/var/log/messages` z etykietą `job=varlogs`.

Objaw: w journalu widzisz `Adding target key="/var/log/messages:{job=\"varlogs\"}"`, a `promtail_sent_entries_total` stoi na zerze.

Lekarstwo: **`systemctl restart promtail`**, nie `enable --now`.

**2. Użytkownik `promtail` nie jest w grupie `adm`.**

Logi Apache mają `root:adm 640`. Pakiet Alloya dopisuje swojego użytkownika do `adm` przy instalacji — pakiet Promtaila **nie**:

```bash
id promtail
# uid=115(promtail) gid=65534(nogroup) grupy=65534(nogroup)     ← brak adm
```

```bash
sudo usermod -aG adm promtail
sudo systemctl restart promtail
```

**3. Plik pozycji domyślnie leży w `/tmp`.**

```yaml
positions:
  filename: /tmp/positions.yaml
```

Plik pozycji pamięta, ile bajtów każdego pliku już wysłano. Skasowanie go oznacza, że po starcie Promtail przeczyta **wszystkie pliki od początku** i wyśle je ponownie. Na `/tmp` zdarzy się to po każdym reboocie.

Przenosimy go razem z resztą:

```bash
sudo mkdir -p /var/lib/promtail
sudo chown promtail:nogroup /var/lib/promtail
```

## Krok 3. Konfiguracja

Cały `/etc/promtail/config.yml` — odpowiednik konfiguracji Alloya z rozdziału 2, linia po linii:

```yaml
server:
  http_listen_port: 9080
  grpc_listen_port: 0

# Pozycje w pliku trwałym, NIE w /tmp — inaczej po reboocie Promtail
# czyta wszystkie pliki od początku i duplikuje dane w Lokim.
positions:
  filename: /var/lib/promtail/positions.yaml

clients:
  - url: http://localhost:3100/loki/api/v1/push

scrape_configs:
  - job_name: apache

    # --------------------------------------------------------------------
    # 1. PLIKI + ETYKIETY STATYCZNE
    #    Każdy klucz w "labels" (poza __path__) staje się etykietą strumienia.
    # --------------------------------------------------------------------
    static_configs:
      - targets: [localhost]
        labels:
          job: apache
          log_type: access
          env: szkolenie
          host: szkolenie
          __path__: /var/log/apache2/access.log
      - targets: [localhost]
        labels:
          job: apache
          log_type: error
          env: szkolenie
          host: szkolenie
          __path__: /var/log/apache2/error.log

    # --------------------------------------------------------------------
    # 2. PRZETWARZANIE
    # --------------------------------------------------------------------
    pipeline_stages:
      - match:
          selector: '{log_type="access"}'
          stages:
            # Rozbicie linii Combined Log Format na nazwane pola
            - regex:
                expression: '^(?P<clientip>\S+) \S+ (?P<remote_user>\S+) \[(?P<ts>[^\]]+)\] "(?P<method>[A-Z]+) (?P<path>\S+) (?P<proto>[^"]*)" (?P<status>\d{3}) (?P<bytes>\S+)'

            # Czas z linii logu zamiast czasu odczytu pliku
            - timestamp:
                source: ts
                format: 02/Jan/2006:15:04:05 -0700

            # ETYKIETY — tylko pola niskokardynalne
            - labels:
                method:
                status:

            # STRUCTURED METADATA — pola wysokokardynalne
            - structured_metadata:
                clientip:
                path:
```

### Różnice wobec Alloya, na które warto zwrócić uwagę grupy

**Struktura.** Promtail ma jeden `scrape_configs` z listą zadań; Alloy ma osobne komponenty połączone przez `forward_to`. Promtail jest krótszy, Alloy bardziej jawny — w Alloyu widać strzałkami, co do czego płynie.

**Etykiety statyczne** w Promtailu siedzą w `labels:` obok `__path__`. Ta sama zasada: klucz staje się etykietą strumienia, `__path__` jest specjalny i wskazuje plik.

**`pipeline_stages` to lista** wykonywana po kolei. W Alloyu odpowiada jej ciąg bloków `stage.*` wewnątrz `loki.process`. Nazwy etapów są niemal identyczne (`regex`, `timestamp`, `labels`, `structured_metadata`), więc przepisanie konfiguracji w jedną i drugą stronę jest mechaniczne.

**Składnia `labels:`** jest nieoczywista. Zapis:

```yaml
- labels:
    method:
    status:
```

to mapa z **pustymi wartościami** — znaczy „weź z wyekstrahowanych pól klucz o tej samej nazwie". Gdybyś chciał zmienić nazwę, piszesz `metoda: method`. W Alloyu to samo wygląda jak `values = { method = "", status = "" }`.

**Nazwa hosta.** Alloy ma `constants.hostname`. Promtail nie ma odpowiednika — albo wpisujesz nazwę na sztywno (jak wyżej), albo używasz zmiennej środowiskowej `${HOSTNAME}` i dokładasz do wywołania flagę `-config.expand-env=true`.

### Walidacja i start

Promtail potrafi sprawdzić plik bez uruchamiania:

```bash
sudo promtail -config.file /etc/promtail/config.yml -check-syntax
# Valid config file! No syntax issues found
```

```bash
sudo systemctl restart promtail        # restart, nie enable --now
sudo systemctl enable promtail
```

## Krok 4. Weryfikacja

### Interfejs Promtaila

Promtail wystawia prostą stronę pod `http://<host>:9080/targets`:

![Lista celów w interfejsie Promtaila](/grafiki/m8-11-promtail-targets@2x.png)

Widać dokładnie to, co potrzebne do diagnozy:

- **`apache (2/2 ready)`** — oba pliki przechwycone i czytane.
- **Labels** — etykiety nadane każdemu celowi, jako gotowe chipy.
- **Position** — ile bajtów danego pliku już wysłano. Jeśli ta liczba stoi w miejscu przy rosnącym pliku, agent się zaciął albo stracił uprawnienia.

Zakładka **Config** pokazuje konfigurację, którą Promtail faktycznie wczytał — przydatne, gdy podejrzewasz, że działa na starym pliku (patrz pułapka nr 1).

> Promtail domyślnie słucha na **wszystkich interfejsach** (`http_listen_port: 9080` bez ograniczenia adresu). To wygodne na szkoleniu, ale w produkcji ogranicz dostęp — strona `Config` ujawnia pełną konfigurację agenta.

### Metryki

Najszybsza kontrola, czy dane faktycznie płyną:

```bash
curl -s http://localhost:9080/metrics | grep -E "^promtail_(read_lines|sent_entries|dropped_entries)_total"
```

```
promtail_read_lines_total{path="/var/log/apache2/access.log"} 21373
promtail_read_lines_total{path="/var/log/apache2/error.log"}  187
promtail_sent_entries_total{host="localhost:3100"}            14712
```

Trzy liczby, trzy różne pytania:

- **`read_lines`** rośnie? Agent czyta pliki. Jeśli nie — uprawnienia albo zła ścieżka.
- **`sent_entries`** rośnie? Loki przyjmuje. Jeśli nie — sprawdź `clients.url` i czy Loki żyje.
- **`dropped_entries`** rośnie? Coś jest odrzucane — etykieta `reason` mówi co.

### Kontrola po stronie Lokiego

```bash
curl -s "http://localhost:3100/loki/api/v1/labels" | python3 -m json.tool
curl -s "http://localhost:3100/loki/api/v1/label/status/values"
```

Wynik jest **identyczny jak przy Alloyu**: `env`, `filename`, `host`, `job`, `log_type`, `method`, `service_name`, `status`. To jest sedno — Loki nie wie i nie obchodzi go, który agent przysłał dane.

## Krok 5. Grafana, LogQL, dashboard

Od tego miejsca **wszystko jest identyczne** jak w wersji z Alloyem. Datasource, Explore, filtrowanie po etykietach, structured metadata, metryki z logów, live tail i dashboard — patrz [3. Integracja z Grafaną](3.%20Integracja%20z%20Grafan%C4%85.md).

Ta identyczność sama w sobie jest lekcją, którą warto nazwać na sali: **agent to element wymienny**. Kontrakt między agentem a Lokim to protokół push i zestaw etykiet. Wszystko, czego uczysz się po stronie LogQL, przeżyje zmianę agenta.

## Pułapka: dwa agenty na tych samych plikach

Jeśli — jak przy tworzeniu tych materiałów — uruchomisz Promtaila na maszynie, na której wcześniej działał Alloy, zobaczysz to:

```
promtail_dropped_entries_total{reason="ingester_error"} 6965
```

W journalu:

```
level=error msg="final error sending batch" status=400
  error="server returned HTTP status 400 Bad Request (400):
  entry with timestamp 2026-09-15 09:31:21 ..."
```

Co się dzieje: nowy agent nie ma pliku pozycji, więc czyta `access.log` **od początku**. Wysyła linie sprzed dwóch dni do strumieni, w których Loki ma już wpisy z „teraz". Loki przyjmuje spóźnione wpisy tylko w ograniczonym oknie (domyślnie połowa `max_chunk_age`, czyli godzina) — starsze odrzuca kodem 400.

To nie jest awaria, tylko konsekwencja projektu. Wnioski praktyczne:

- **Nie uruchamiaj dwóch agentów na tych samych plikach.** Przy zamianie zatrzymaj stary: `sudo systemctl disable --now alloy`.
- Przy migracji **przenieś plik pozycji** albo pogódź się z tym, że historii nie doślesz.
- Jeśli naprawdę potrzebujesz zaimportować stare logi, podnieś w Lokim `limits_config.reject_old_samples_max_age` i okno akceptacji spóźnionych wpisów.

## Migracja Promtail → Alloy

Gdy przyjdzie czas na przesiadkę, Alloy ma wbudowany konwerter:

```bash
sudo alloy convert --source-format=promtail \
  --output=/etc/alloy/config.alloy \
  /etc/promtail/config.yml
```

Konwerter obsługuje `static_configs`, `pipeline_stages` i `clients`. Wypisuje ostrzeżenia przy konstrukcjach bez odpowiednika — najczęściej przy service discovery i niestandardowych etapach. Wynik i tak trzeba przeczytać: konwerter tłumaczy dosłownie, więc nie skorzysta z tego, co w Alloyu wyszłoby czytelniej.

Kolejność bezpiecznej zamiany:

```bash
sudo systemctl stop promtail
sudo cp /var/lib/promtail/positions.yaml /var/lib/alloy/           # opcjonalnie
sudo systemctl enable --now alloy
sudo systemctl disable promtail
```

## Pułapki — skrócona lista

| Objaw | Przyczyna | Naprawa |
|---|---|---|
| Agent czyta `/var/log/messages`, `job=varlogs` | usługa wstała przy instalacji ze starym configiem | `systemctl restart promtail` |
| `read_lines` = 0 | `promtail` spoza grupy `adm` | `usermod -aG adm promtail` |
| Po reboocie logi lecą drugi raz | pozycje w `/tmp` | przenieś na `/var/lib/promtail` |
| `dropped_entries{reason="ingester_error"}` rośnie | wpisy starsze niż okno akceptacji | zatrzymaj drugi agent / podnieś limit |
| `dropped_entries{reason="rate_limited"}` | limit ingestu w Lokim | `limits_config.ingestion_rate_mb` |
| `dropped_entries{reason="stream_limited"}` | za dużo strumieni | **przejrzyj etykiety — kardynalność** |
| Etykiety `method`/`status` puste dla `error.log` | `match` dotyczy tylko accessu | poprawne zachowanie |
| Zmiana configu nie działa | Promtail wczytał stary plik | zakładka **Config** w UI, potem restart |
| Cała historia z jednym znacznikiem czasu | brak etapu `timestamp` | dodaj etap z formatem Go |

## Stan maszyny po tych materiałach

Na **vmobserv15** zainstalowane są **oba agenty**, ale **aktywny jest tylko Promtail** — Alloy został zatrzymany przed jego uruchomieniem, żeby nie dublować danych.

Przełączenie z powrotem na Alloya:

```bash
sudo systemctl disable --now promtail
sudo systemctl enable --now alloy
```

Obie konfiguracje zostają na dysku (`/etc/alloy/config.alloy` i `/etc/promtail/config.yml`), więc można je porównywać obok siebie — to dobre ćwiczenie na sali.
