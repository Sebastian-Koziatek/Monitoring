# Integracja Elasticsearch z Grafaną

## Wprowadzenie

Grafana potrafi czytać dane z Elasticsearch i wizualizować logi, metryki oraz zdarzenia
obok danych z Prometheusa, Lokiego czy Zabbiksa. W tym rozdziale konfigurujesz połączenie,
budujesz panele i poznajesz surowy Query DSL w edytorze zapytań.

### Kiedy Grafana, a kiedy Kibana

Pytanie pada zawsze i warto je rozstrzygnąć na wstępie.

| Zadanie | Narzędzie |
|---|---|
| Analiza logów, struktura dokumentów, ingest pipeline, mapowania | **Kibana** |
| Jeden dashboard łączący Elasticsearcha z Prometheusem, Lokim, Zabbiksem | **Grafana** |
| Alerty dla całej infrastruktury w jednym miejscu | **Grafana** |
| Gotowe dashboardy integracji Elastica | **Kibana** |

W skrócie: **Kibana do analizy, Grafana do jednej szyby**. Jeśli w firmie Grafana jest już
głównym narzędziem, sensowne jest podpięcie Elasticsearcha obok reszty źródeł.

## Dodanie źródła danych Elasticsearch

### Krok 1: Dodanie Data Source

```
Connections → Data sources → Add new data source → Elasticsearch
```

> W Grafanie starszej niż 10 ścieżka wyglądała inaczej: `Configuration (⚙️) → Data Sources`.

### Krok 2: Połączenie i uwierzytelnianie

Od **Elasticsearch 8** bezpieczeństwo jest włączone domyślnie. Oznacza to trzy rzeczy,
których nie było w wersji 7 i które są najczęstszą przyczyną nieudanej konfiguracji:

| Parametr | Wartość | Uwagi |
|---|---|---|
| **Name** | `Elasticsearch-Logs` | dowolna nazwa |
| **URL** | `https://localhost:9200` | **HTTPS, nie HTTP** — ES 8 nie nasłuchuje po HTTP |
| **Authentication** | `Basic authentication` | |
| **User** | `elastic` | lub dedykowane konto o prawach tylko do odczytu |
| **Password** | hasło użytkownika | |
| **Skip TLS certificate validation** | ☑ | certyfikat ES jest self-signed |

Zamiast wyłączać weryfikację TLS możesz wgrać urząd certyfikacji Elasticsearcha przez
**Add self-signed certificate**:

```bash
sudo cat /etc/elasticsearch/certs/http_ca.crt
```

### Krok 3: Elasticsearch details

| Parametr | Wartość | Uwagi |
|---|---|---|
| **Index name** | `logs-*` | wzorzec indeksów lub data streamów |
| **Pattern** | `No pattern` | patrz uwaga niżej |
| **Time field name** | `@timestamp` | standard ECS; **nie** `timestamp` |
| **Max concurrent Shard Requests** | `5` | wartość domyślna |
| **Min time interval** | `10s` | dopasuj do częstotliwości zbierania danych |
| **Default query mode** | `Logs` lub `Metrics` | zależnie od przeznaczenia źródła |

> **`Pattern: No pattern` przy data streamach.** Nowoczesny Elastic (Agent, Beaty od 8.x)
> zapisuje dane do **data streamów**, które same zarządzają rotacją indeksów. Jeśli wybierzesz
> `Daily`, Grafana zacznie budować nazwy w stylu `logs-2026.09.17`, które nie istnieją,
> i nie znajdzie nic. Wzorce dat mają sens tylko przy klasycznych indeksach z ręczną rotacją.

### Krok 4: Pola logów

| Parametr | Typowa wartość |
|---|---|
| **Message field name** | `message` |
| **Level field name** | `log.level` |

> **Pułapka, o której trzeba wiedzieć.** Pole z treścią logu **nie zawsze nazywa się tak samo**.
> Integracja Apache w Elastic Agencie ma w ingest pipeline procesor `rename`, który przenosi
> `message` → `event.original`. Zwykłe logi plikowe takiego przetwarzania nie mają. Efekt:
>
> ```
> logs-apache.access-default    →  event.original   (pola "message" NIE MA)
> logs-var_log_grafana-default  →  message          (pola "event.original" NIE MA)
> ```
>
> Datasource ma tylko **jedno** pole „Message field name", więc obsłuży jedno albo drugie.
> Przy złym ustawieniu panel Logs pokaże zamiast treści same identyfikatory dokumentów.
> Rozwiązanie: **osobny datasource na każdy format**, np. `Elasticsearch-Apache`
> z `Index name: logs-apache*` i `Message field name: event.original`.

### Krok 5: Test połączenia

Kliknij **Save & test**. Komunikat sukcesu:

```
Elasticsearch data source is healthy.
```

### Diagnostyka — kod błędu mówi, gdzie jesteś

Warto znać tę sekwencję, bo każdy komunikat wskazuje inną warstwę:

| Komunikat | Warstwa | Przyczyna |
|---|---|---|
| `Failed to connect to Elasticsearch` | sieć / TLS | `http://` zamiast `https://`, zła nazwa hosta, firewall |
| `401 Unauthorized` | uwierzytelnianie | złe hasło **albo puste pole User** |
| `certificate signed by unknown authority` | TLS | brak `Skip TLS` i brak wgranego CA |
| `Elasticsearch data source is healthy` | — | komplet |

> **Podstępny wariant 401.** Formularz pokazuje `elastic` w polu User, ale wartość nigdy
> nie została zapisana — Grafana wysyła wtedy basic auth z pustym loginem. Rozstrzyga
> sprawdzenie, co jest **naprawdę** w bazie Grafany, a nie co wyświetla formularz:
>
> ```bash
> curl -s -u admin:HASLO http://localhost:3000/api/datasources \
>   | python3 -m json.tool | grep -A2 basicAuth
> ```

## Model zapytań — Builder kontra Code

To jest najważniejsza różnica wobec Prometheusa i Lokiego. Grafana **nie ma dla
Elasticsearcha języka zapytań** w rodzaju PromQL czy LogQL. Zamiast tego oferuje dwa tryby:

**Builder** — budujesz agregację z klocków:

```
Lucene Query   →  data_stream.dataset:"apache.access"    (filtr: co bierzemy)
Metric         →  Count                                   (co liczymy)
Group By       →  Terms  http.response.status_code        (pierwszy poziom podziału)
Then By        →  Date Histogram  @timestamp              (drugi poziom podziału)
```

**Code** (`Query language: DSL`) — wpisujesz surowe zapytanie Elasticsearcha.

Builder tylko **generuje** ten sam JSON, który w trybie Code piszesz ręcznie. Przełączanie
się między nimi to najlepszy sposób nauki DSL — klikasz w Builderze, przełączasz na Code
i widzisz, co powstało.

### Kolejność Group By ma znaczenie

Najczęstszy błąd początkujących:

| Kolejność | Wynik |
|---|---|
| `Terms` → `Date Histogram` | **osobna seria czasowa dla każdej wartości** ✅ |
| `Date Histogram` → `Terms` | jedna seria, w każdym punkcie pomieszane wartości ❌ |
| tylko `Terms` | tabela lub wykres słupkowy, bez wymiaru czasu |
| tylko `Date Histogram` | jedna seria czasowa łącznie |

### Query type — cztery tryby

| Tryb | Zwraca | Panel |
|---|---|---|
| **Metrics** | serie czasowe z agregacji | timeseries, stat, gauge |
| **Logs** | surowe dokumenty | Logs |
| **Raw Data** | dokumenty jako tabela | Table |
| **Raw Document** | pełny JSON dokumentu | diagnostyka |

## Lucene Query Syntax

Grafana filtruje dane w Elasticsearchu składnią **Lucene** — nie KQL, którego używasz
w Kibanie. Różnice są drobne, ale bolesne, bo złe zapytanie zwykle **nie zwraca błędu**,
tylko złe wyniki.

| | Kibana (KQL) | Grafana (Lucene) |
|---|---|---|
| Równość | `status : 404` | `status:404` |
| I / LUB | `and`, `or` (małe litery) | `AND`, `OR` (**wielkie**) |
| Negacja | `not status : 200` | `NOT status:200` |
| Zakres domknięty | `status >= 400 and status <= 599` | `status:[400 TO 599]` |
| Zakres otwarty | `status > 3000` | `status:{3000 TO *}` |
| Istnienie pola | `status : *` | `_exists_:status` |

### Podstawowa składnia

```bash
# Dokładne dopasowanie
log.level:ERROR

# Fraza
message:"connection timeout"

# Alternatywa
log.level:(ERROR OR CRITICAL)

# Koniunkcja
log.level:ERROR AND service.name:auth-service

# Negacja
NOT log.level:INFO

# Wildcard
service.name:auth*

# Zakres domknięty
http.response.status_code:[400 TO 599]

# Zakres otwarty (nawiasy klamrowe = wyłączny)
event.duration:{3000 TO *}

# Pole istnieje
_exists_:error.code

# Kombinacja
log.level:ERROR AND service.name:payment* NOT service.environment:test
```

> **Uwaga na `>` i `<`.** Zapis `response_time:>3000` **nie jest poprawnym Lucene** —
> to składnia KQL. W Grafanie użyj `response_time:{3000 TO *}`.

## Query DSL w trybie Code — przykłady

Poniższe zapytania są sprawdzone na działającej instalacji (Elastic Agent zbierający logi
Apache i metryki systemowe do data streamów). Nazwy pól są zgodne z **ECS**.

Wybierz `Query language: DSL` i tryb **Code**. Pole musi być puste przed wklejeniem —
domyślnie potrafi w nim zostać znak z poprzedniego trybu, co daje błąd `raw DSL query is empty`.

### 1. Liczba dokumentów w czasie

Najprostsze możliwe zapytanie — punkt wyjścia do wszystkich pozostałych.

```json
{
  "query": { "match_all": {} },
  "aggs": {
    "w_czasie": {
      "date_histogram": { "field": "@timestamp", "fixed_interval": "1m" }
    }
  }
}
```

Panel: **timeseries**. `query` mówi, co bierzemy, `aggs` — jak grupujemy.

### 2. Rozbicie po kodzie odpowiedzi

```json
{
  "query": {
    "bool": {
      "filter": [ { "term": { "data_stream.dataset": "apache.access" } } ]
    }
  },
  "aggs": {
    "po_kodzie": {
      "terms": { "field": "http.response.status_code", "size": 10 },
      "aggs": {
        "w_czasie": {
          "date_histogram": { "field": "@timestamp", "fixed_interval": "1m" }
        }
      }
    }
  }
}
```

To jest dokładnie ten sam wynik, co klikane `Count + Terms + Date Histogram`. Zwróć uwagę
na **zagnieżdżenie**: `date_histogram` siedzi wewnątrz `terms`, co odpowiada kolejności
`Group By` → `Then By` z Buildera.

### 3. Percentyle — przewaga nad Prometheusem

```json
{
  "query": { "match_all": {} },
  "aggs": {
    "percentyle": {
      "percentiles": {
        "field": "http.response.body.bytes",
        "percents": [50, 95, 99]
      }
    }
  }
}
```

Przykładowy wynik z rzeczywistych danych:

| percentyl | wartość |
|---|---|
| p50 | 765 B |
| p95 | 6 959 B |
| p99 | 252 194 B |

**To jest mocny argument dydaktyczny.** Prometheus liczy percentyle z histogramu o progach
ustalonych z góry przy instrumentacji — jeśli nie przewidziałeś kubełka, nie policzysz go
po fakcie. Elasticsearch liczy z surowych wartości, więc dowolny percentyl jest dostępny
zawsze. Tutaj rozrzut p50 → p99 jest ponad 300-krotny, a średnia (5 599 B) kompletnie go
nie oddaje.

### 4. Ranking wartości — bez wymiaru czasu

```json
{
  "query": { "match_all": {} },
  "aggs": {
    "sciezki": {
      "terms": {
        "field": "url.path",
        "size": 10,
        "order": { "_count": "desc" }
      }
    }
  }
}
```

Panel: **table** albo **bar chart**. Brak `date_histogram` oznacza brak osi czasu.

### 5. Kilka metryk w jednym zapytaniu

```json
{
  "query": { "match_all": {} },
  "aggs": {
    "unikalne_ip":    { "cardinality": { "field": "source.ip" } },
    "sredni_rozmiar": { "avg":         { "field": "http.response.body.bytes" } },
    "max_rozmiar":    { "max":         { "field": "http.response.body.bytes" } }
  }
}
```

`cardinality` to odpowiednik `COUNT(DISTINCT ...)` z SQL-a. Jest **przybliżona** —
używa algorytmu HyperLogLog++, więc przy dużych zbiorach daje wynik z błędem rzędu
pojedynczych procent w zamian za stałe zużycie pamięci.

### 6. Podział na klasy odpowiedzi — agregacja `filters`

```json
{
  "query": { "match_all": {} },
  "aggs": {
    "klasy": {
      "filters": {
        "filters": {
          "sukces":       { "range": { "http.response.status_code": { "lt": 400 } } },
          "blad_klienta": { "range": { "http.response.status_code": { "gte": 400, "lt": 500 } } },
          "blad_serwera": { "range": { "http.response.status_code": { "gte": 500 } } }
        }
      },
      "aggs": {
        "w_czasie": {
          "date_histogram": { "field": "@timestamp", "fixed_interval": "1m" }
        }
      }
    }
  }
}
```

**Tego nie da się wyklikać w Builderze.** Agregacja `filters` z nazwanymi kubełkami jest
dostępna tylko w surowym DSL — i to jest najlepsze uzasadnienie, po co ten tryb istnieje.
Zamiast dziesięciu serii po jednym kodzie dostajesz trzy sensowne kategorie biznesowe.

### 7. Metryki systemowe

Dla źródła wskazującego na `metrics-*`:

```json
{
  "query": {
    "bool": { "filter": [ { "term": { "data_stream.dataset": "system.cpu" } } ] }
  },
  "aggs": {
    "w_czasie": {
      "date_histogram": { "field": "@timestamp", "fixed_interval": "30s" },
      "aggs": {
        "cpu": { "avg": { "field": "system.cpu.total.norm.pct" } }
      }
    }
  }
}
```

Jednostka panelu: `percentunit` (wartości 0–1). Ten sam wykres można postawić obok
z Prometheusa i porównać — dobra ilustracja tego, że wybór magazynu nie zmienia tego,
co widzi użytkownik.

### 8. Zapytanie z jawnym zakresem czasu

Grafana zwykle dokłada filtr z time pickera sama. Jeśli panel zdaje się go ignorować,
dopisz go jawnie:

```json
{
  "query": {
    "bool": {
      "filter": [
        { "term": { "data_stream.dataset": "apache.access" } },
        { "range": {
            "@timestamp": {
              "gte": "$__timeFrom",
              "lte": "$__timeTo",
              "format": "epoch_millis"
            }
        } }
      ]
    }
  },
  "aggs": {
    "w_czasie": {
      "date_histogram": {
        "field": "@timestamp",
        "fixed_interval": "$__interval",
        "min_doc_count": 0
      }
    }
  }
}
```

**Zmienne Grafany dostępne w DSL:**

| Zmienna | Znaczenie |
|---|---|
| `$__timeFrom` | początek zakresu z Time Pickera |
| `$__timeTo` | koniec zakresu |
| `$__interval` | interwał dobrany do szerokości panelu |

`"min_doc_count": 0` wypełnia puste kubełki zerami — bez tego wykres ma dziury zamiast
płaskiej linii w okresach bez ruchu.

### `term` kontra `match`

| Zapytanie | Działanie | Kiedy |
|---|---|---|
| `term` | dokładna wartość, bez analizy | pola `keyword`: `data_stream.dataset`, `url.path`, `host.name` |
| `match` | analizuje tekst na tokeny | pola `text`: treść wiadomości |
| `match_phrase` | fraza w kolejności | szukanie dokładnych zwrotów |

Najczęstszy błąd: `term` na polu typu `text` nie zwróci nic, bo porównuje z całym,
nieprzeanalizowanym tekstem.

## Budowa paneli

### 1. Wykres liczby logów w czasie (Time Series)

**Builder:**
- Metric: `Count`
- Group By: `Date Histogram` → `@timestamp`, Interval: `auto`
- Lucene Query: `log.level:ERROR OR log.level:CRITICAL`

### 2. Rozbicie po serwisie

- Metric: `Count`
- Group By: `Terms` → `service.name`, Top 10
- Then By: `Date Histogram` → `@timestamp`

### 3. Stat — liczba błędów

- Wizualizacja: **Stat**
- Metric: `Count`
- Group By: `Date Histogram` → `@timestamp`
- Reduce: `Sum` albo `Max`

> **Uwaga na `Unique Count` w panelu Stat.** Kardynalność liczy się w obrębie **każdego
> kubełka czasowego**, nie globalnie. Ostatni kubełek bywa niepełny i daje zero, przez co
> panel pokazuje `0` mimo danych. Użyj redukcji `Max` zamiast `Last`, albo usuń
> `Date Histogram` i przejdź na panel Table.

### 4. Gauge — średni czas odpowiedzi

- Metric: `Average` → `event.duration`
- Group By: `Date Histogram` → `@timestamp`
- Progi: zielony 0–200, żółty 200–500, czerwony 500+

### 5. Bar Gauge — top serwisy z błędami

- Lucene Query: `log.level:ERROR`
- Metric: `Count`
- Group By: `Terms` → `service.name`, Top 10, Order by Doc Count

### 6. Table — szczegółowe logi

- Query type: **Raw Data**
- Size: 100
- Sort: `@timestamp` DESC
- Lucene Query: `log.level:ERROR AND service.name:payment*`

## Logs Panel

Dedykowany panel do przeglądania logów, działający jak `tail -f` z filtrowaniem.

**Konfiguracja:**
- Query type: **Logs**
- Limit: 100
- Show time: ☑
- Wrap lines: ☑

**Zapytanie:**

```
data_stream.dataset:"apache.access" AND http.response.status_code:[400 TO 599]
```

Pamiętaj o wielkim `TO` w zakresie — to Lucene, nie KQL.

### Derived Fields

Zamiana fragmentu logu w klikalny odnośnik. Przykład — identyfikator żądania:

```
Name:  Request ID
Regex: request_id=([a-f0-9]{32})
URL:   http://app.example.com/requests/${__value.raw}
```

To jest mechanizm, którym spina się logi ze śladami (traces) — wyciągasz `trace.id`
i linkujesz do Tempo albo Jaegera.

## Variables (zmienne)

### 1. Query Variable — lista serwisów

- Name: `service`
- Type: `Query`
- Data source: Elasticsearch
- Query:

```json
{ "find": "terms", "field": "service.name" }
```

**Użycie w panelu:**

```
service.name:$service
```

### 2. Multi-value Variable

- Multi-value: ☑
- Include All option: ☑

```
service.name:($service)
```

### 3. Interval Variable

- Name: `interwal`
- Type: `Interval`
- Values: `1m,5m,10m,30m,1h`

**Użycie w DSL:**

```json
{ "date_histogram": { "field": "@timestamp", "fixed_interval": "$interwal" } }
```

## Alerting

Grafana od wersji 9 używa **unified alerting**. Stara składnia
(`WHEN last() OF query(A, 5m, now) IS ABOVE 100`) została usunięta — reguła składa się teraz
z zapytania i **ekspresji** (Reduce, Threshold).

### Alert: wysoka liczba błędów

**Krok 1 — zapytanie (A):**
- Query type: `Metrics`
- Lucene: `http.response.status_code:[500 TO 599]`
- Metric: `Count`
- Group By: `Date Histogram` → `@timestamp`, interwał `1m`

**Krok 2 — Reduce (B):**
```
Function:   Last
Input:      A
Mode:       Strict
```

**Krok 3 — Threshold (C):**
```
Input:      B
IS ABOVE:   100
```

**Krok 4 — reguła:**
- Evaluate every: `1m`
- For: `5m` — alert odpala się dopiero, gdy warunek utrzymuje się 5 minut, co eliminuje
  pojedyncze skoki

**Szablon powiadomienia:**

```
🚨 Wysoka liczba błędów 5xx
Wartość: {{ $values.B }}
Host: {{ $labels.host_name }}
```

> **`For` jest ważniejsze, niż się wydaje.** Bez niego alert odpali się przy każdym
> jednominutowym skoku. Z `For: 5m` reaguje dopiero na trwały problem.

## Optymalizacja wydajności

### 1. Zawsze ograniczaj zakres czasowy

Elasticsearch przeszukuje tylko te indeksy, które mieszczą się w zakresie. Bez filtru
czasowego zapytanie przechodzi przez całą historię.

### 2. `size: 0` przy agregacjach

```json
{ "size": 0, "aggs": { } }
```

Bez tego Elasticsearch dołoży do odpowiedzi 10 przykładowych dokumentów, których i tak
nie użyjesz. Grafana zwykle ustawia to sama, ale w trybie Code warto dopisać jawnie.

### 3. Filtruj w `bool.filter`, nie w `bool.must`

```json
{
  "query": {
    "bool": {
      "filter": [
        { "term": { "data_stream.dataset": "apache.access" } },
        { "range": { "http.response.status_code": { "gte": 400 } } }
      ]
    }
  }
}
```

Klauzula `filter` **nie liczy punktacji trafności** (`_score`) i jest cache'owana.
Przy monitoringu trafność nie ma znaczenia — liczy się tylko, czy dokument pasuje.

### 4. Ograniczaj `size` w agregacji `terms`

`"size": 10` zamiast `"size": 1000`. Każdy kubełek to praca dla każdego sharda.

### 5. Rotacja indeksów

Data streamy robią to automatycznie. Przy klasycznych indeksach stosuj rotację dzienną
lub tygodniową:

```
logs-nginx-2026.09.17
logs-nginx-2026.09.18
```

zamiast jednego rosnącego `logs-nginx-all`.

### 6. Transformacje po stronie Grafany

Proste przeliczenia (zmiana jednostek, filtrowanie kolumn, łączenie serii) rób
transformacjami w Grafanie, a nie kolejnymi agregacjami — odciążasz klaster.

## Najlepsze praktyki

### Nazewnictwo

Konwencja Elastica dla data streamów to trójka:

```
{typ}-{dataset}-{namespace}

logs-apache.access-default
metrics-system.cpu-default
logs-nginx.error-produkcja
```

`namespace` to najprostszy sposób oddzielenia środowisk bez stawiania osobnych klastrów.

### Struktura dashboardów

- **Overview** — ogólny widok całości
- **Per serwis** — dedykowane dashboardy
- **Troubleshooting** — do szybkiej diagnostyki, z panelem Logs obok wykresów

### Zmienne

Używaj ich do filtrowania serwisów i środowisk oraz do dashboardów wielodostępnych.
Jeden dashboard ze zmienną `$service` zastępuje dziesięć kopii.

### Adnotacje

Nanoszenie wdrożeń na oś czasu wykresów:

## Pułapki — szybka lista

| Objaw | Przyczyna | Naprawa |
|---|---|---|
| `Failed to connect` | `http://` zamiast `https://` | ES 8 wymaga TLS |
| `401 Unauthorized` | puste pole User albo złe hasło | sprawdź przez API, nie w formularzu |
| `certificate signed by unknown authority` | self-signed CA | `Skip TLS` albo wgraj `http_ca.crt` |
| Pusty wykres mimo danych | `Pattern` inny niż `No pattern` | data streamy nie używają wzorców dat |
| Panel Logs pokazuje identyfikatory | złe `Message field name` | `event.original` dla Apache, `message` dla reszty |
| Zapytanie zwraca bzdury, bez błędu | składnia KQL zamiast Lucene | `AND`/`OR` wielkimi, zakresy `[400 TO 599]` |
| Jedna seria zamiast wielu | `Date Histogram` przed `Terms` | odwróć kolejność Group By |
| Stat pokazuje `0` przy Unique Count | niepełny ostatni kubełek | redukcja `Max` zamiast `Last` |
| `raw DSL query is empty` | pole Code niepuste lub niepoprawny JSON | wyczyść pole, sprawdź nawiasy |
| Dziury na wykresie | brak `min_doc_count: 0` | dopisz do `date_histogram` |
| Pusto przy `Last 15 minutes` | źródło danych zatrzymane | poszerz zakres czasu |

## Podsumowanie

Integracja Elasticsearcha z Grafaną daje:

- **wizualizacje** — timeseries, stat, gauge, table, bar chart, logs
- **dwa tryby zapytań** — Builder do nauki i szybkiej pracy, Code (DSL) do rzeczy,
  których Builder nie obsługuje, jak agregacja `filters`
- **Lucene** do filtrowania — podobne do KQL, ale **nie identyczne**
- **zmienne** do dashboardów wielokrotnego użytku
- **unified alerting** z ekspresjami Reduce i Threshold

Elasticsearch gromadzi i indeksuje, Grafana wizualizuje i alarmuje. Razem, obok Prometheusa
i Lokiego, składają się na jedno miejsce do obserwacji całej infrastruktury — i to jest
główny powód, dla którego warto to spinać, mimo że Kibana też potrafi rysować wykresy.
