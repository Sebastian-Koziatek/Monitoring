Kanały powiadomień w Alertmanagerze definiuje się w sekcji `receivers` pliku `alertmanager.yml`. Każdy receiver to nazwany zestaw konfiguracji jednego lub wielu typów integracji (`email_configs`, `slack_configs`, `webhook_configs` i innych), do którego przypisywane są alerty przez drzewo routingu (`route`). Poniżej znajdują się kompletne, gotowe do zastosowania konfiguracje trzech najczęściej wykorzystywanych kanałów.

## Powiadomienia e-mail (SMTP)

Konfiguracja SMTP może być zdefiniowana globalnie (dziedziczona przez wszystkie receivery) lub indywidualnie w danym receiverze.

```yaml
global:
  smtp_smarthost: "smtp.firma.pl:587"
  smtp_from: "alertmanager@firma.pl"
  smtp_auth_username: "alertmanager@firma.pl"
  smtp_auth_password: "SUPER_TAJNE_HASLO"
  smtp_require_tls: true

receivers:
  - name: "email-devops"
    email_configs:
      - to: "devops@firma.pl"
        send_resolved: true
        headers:
          Subject: '{{ template "email.subject" . }}'
        html: '{{ template "email.html" . }}'
```

Najważniejsze parametry `email_configs`:

| Parametr | Opis |
|---|---|
| `to` | Adres (lub lista adresów oddzielonych przecinkami) odbiorcy. |
| `send_resolved` | Czy wysyłać także powiadomienie o ustąpieniu alertu (domyślnie `false`). |
| `headers` | Niestandardowe nagłówki wiadomości, w tym temat (`Subject`). |
| `html` / `text` | Treść wiadomości — jako HTML lub czysty tekst, renderowana z szablonu Go template. |
| `require_tls` | Wymuszenie szyfrowania TLS dla danego receivera (nadpisuje `smtp_require_tls`). |

W praktyce hasło SMTP warto trzymać poza plikiem konfiguracyjnym, wykorzystując `smtp_auth_password_file` wskazujący na plik z sekretem, co ułatwia zarządzanie poświadczeniami w środowiskach z automatyzacją (Ansible, Kubernetes Secrets).

## Powiadomienia Slack

Integracja ze Slackiem wymaga utworzenia **Incoming Webhook** w danym workspace Slacka (Slack App → Incoming Webhooks → Add New Webhook to Workspace), co generuje unikalny URL w formacie `https://hooks.slack.com/services/T000/B000/XXXX`.

```yaml
global:
  slack_api_url: "https://hooks.slack.com/services/T000000/B000000/XXXXXXXXXXXXXXXXXXXXXXXX"

receivers:
  - name: "slack-devops"
    slack_configs:
      - channel: "#alerty-produkcja"
        send_resolved: true
        username: "Alertmanager"
        icon_emoji: ":rotating_light:"
        title: '{{ .CommonLabels.alertname }} ({{ .Status | toUpper }})'
        text: >-
          {{ range .Alerts }}
          *Instancja:* {{ .Labels.instance }}
          *Severity:* {{ .Labels.severity }}
          *Opis:* {{ .Annotations.description }}
          {{ end }}
        actions:
          - type: button
            text: "Otwórz w Prometheusie"
            url: '{{ (index .Alerts 0).GeneratorURL }}'
```

Najważniejsze parametry `slack_configs`:

| Parametr | Opis |
|---|---|
| `channel` | Kanał docelowy (może być nadpisany dla poszczególnych alertów przez routing). |
| `api_url` | URL webhooka Slacka — jeśli pominięty, dziedziczony z `global.slack_api_url`. |
| `title` / `text` | Treść wiadomości renderowana z szablonu; obsługuje formatowanie `mrkdwn` Slacka. |
| `color` | Kolor paska bocznego wiadomości — typowo warunkowany etykietą `severity` (np. `{{ if eq .Status "firing" }}danger{{ else }}good{{ end }}`). |
| `send_resolved` | Wysyła osobną wiadomość, gdy alert przechodzi w stan rozwiązany. |

Zaleca się przechowywanie URL-a webhooka jako sekretu (`slack_api_url_file`) zamiast wpisywania go wprost w repozytorium konfiguracji, ponieważ URL webhooka daje możliwość wysyłania wiadomości na dany kanał bez dodatkowego uwierzytelnienia.

## Generyczny webhook

`webhook_configs` pozwala zintegrować Alertmanagera z dowolnym systemem zewnętrznym (np. własnym systemem ticketowym, ChatOps, PagerDuty przez most webhookowy, systemem automatyzacji odpowiedzi). Alertmanager wysyła żądanie HTTP POST z ciałem JSON zgodnym ze standardowym schematem powiadomienia.

```yaml
receivers:
  - name: "webhook-automatyzacja"
    webhook_configs:
      - url: "https://automatyzacja.firma.pl/api/v1/alerty"
        send_resolved: true
        max_alerts: 10
        http_config:
          bearer_token: "TOKEN_UWIERZYTELNIAJACY"
          tls_config:
            insecure_skip_verify: false
```

Format ciała żądania POST wysyłanego przez Alertmanagera:

```json
{
  "version": "4",
  "groupKey": "{}:{alertname=\"HighCpuUsage\"}",
  "status": "firing",
  "receiver": "webhook-automatyzacja",
  "groupLabels": {"alertname": "HighCpuUsage"},
  "commonLabels": {"alertname": "HighCpuUsage", "severity": "warning"},
  "commonAnnotations": {"summary": "Wysokie zużycie CPU"},
  "externalURL": "http://alertmanager:9093",
  "alerts": [
    {
      "status": "firing",
      "labels": {"alertname": "HighCpuUsage", "instance": "web-01:9100", "severity": "warning"},
      "annotations": {"description": "CPU 92% na web-01"},
      "startsAt": "2026-09-04T18:23:00Z",
      "endsAt": "0001-01-01T00:00:00Z",
      "generatorURL": "http://prometheus:9090/graph?g0.expr=..."
    }
  ]
}
```

System odbierający webhook musi zwrócić kod HTTP z zakresu `2xx` — w przeciwnym razie Alertmanager potraktuje dostarczenie jako nieudane i podejmie ponowną próbę zgodnie z mechanizmem retry (`http_config` pozwala też skonfigurować proxy, TLS oraz uwierzytelnianie: `basic_auth`, `bearer_token` lub `bearer_token_file`).

## Szablony wiadomości (templates)

Domyślne szablony Alertmanagera są bardzo skromne. W praktyce niemal zawsze definiuje się własne szablony w plikach `.tmpl`, które są następnie wskazywane w sekcji `templates` głównego pliku konfiguracyjnego i referencjonowane w receiverach za pomocą funkcji `template`.

```yaml
templates:
  - "/etc/alertmanager/templates/*.tmpl"
```

Przykładowy plik `email.tmpl`:

```gotemplate
{{ define "email.subject" }}
[{{ .Status | toUpper }}] {{ .CommonLabels.alertname }} ({{ .Alerts | len }} alertów)
{{ end }}

{{ define "email.html" }}
<h2>{{ .CommonLabels.alertname }}</h2>
<p>Status: <strong>{{ .Status }}</strong></p>
<table border="1" cellpadding="6">
  <tr><th>Instancja</th><th>Severity</th><th>Opis</th></tr>
  {{ range .Alerts }}
  <tr>
    <td>{{ .Labels.instance }}</td>
    <td>{{ .Labels.severity }}</td>
    <td>{{ .Annotations.description }}</td>
  </tr>
  {{ end }}
</table>
{{ end }}
```

Szablony wykorzystują silnik Go template z dodatkowymi funkcjami dostarczanymi przez Alertmanagera (`toUpper`, `toLower`, `title`, `humanizeDuration`, `reReplaceAll` i inne). Kluczowe zmienne dostępne w kontekście szablonu:

- `.Status` — `firing` lub `resolved` dla całej grupy,
- `.Alerts` — lista alertów w grupie (można iterować przez `range`),
- `.CommonLabels` / `.CommonAnnotations` — etykiety/adnotacje wspólne dla wszystkich alertów w grupie,
- `.GroupLabels` — etykiety, po których alert został pogrupowany.

## Dobre praktyki

- Trzymaj sekrety (tokeny, hasła SMTP, URL-e webhooków) w osobnych plikach referencjonowanych przez `*_file` (np. `smtp_auth_password_file`, `slack_api_url_file`), a nie bezpośrednio w `alertmanager.yml`.
- Zawsze ustawiaj `send_resolved: true` dla kanałów, na których zespół oczekuje potwierdzenia ustąpienia problemu — brak tej informacji prowadzi do niepewności, czy alert nadal trwa.
- Personalizuj treść (`title`, `text`, szablony) tak, aby zawierała nazwę hosta, wartość metryki i link do runbooka — minimalizuje to czas potrzebny na wstępną diagnozę.
- Testuj konfigurację poleceniem `amtool config routes test` oraz `amtool alert add` na środowisku nieprodukcyjnym przed wdrożeniem zmian.
- Dla webhooków wdrażaj mechanizm idempotencji po stronie odbiorcy — Alertmanager może dostarczyć to samo powiadomienie wielokrotnie (retry, klaster HA).
