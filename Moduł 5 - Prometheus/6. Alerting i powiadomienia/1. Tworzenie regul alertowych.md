# Tworzenie reguł alertowych
![Prometheus](/grafiki/m5-6.1-tworzenie-regul-alertowych.png)
Reguły alertowe (ang. *alerting rules*) pozwalają Prometheusowi w sposób ciągły oceniać wyrażenia PromQL i generować alerty, gdy wynik spełnia zadany warunek. Same reguły definiuje się w plikach YAML, które są następnie wczytywane przez Prometheusa poprzez sekcję `rule_files` w `prometheus.yml`. Wygenerowane alerty trafiają do Alertmanagera, który odpowiada za ich dalszą obróbkę (grupowanie, wyciszanie, wysyłkę powiadomień).

## Struktura pliku z regułami

Plik z regułami ma strukturę grup (`groups`), z których każda zawiera listę reguł. Reguły w obrębie jednej grupy są ewaluowane sekwencyjnie, ale różne grupy mogą być ewaluowane równolegle — dlatego warto logicznie grupować powiązane reguły i nadawać im wspólny interwał ewaluacji.

```yaml
groups:
  - name: przyklad-grupy
    interval: 30s          # opcjonalnie - nadpisuje globalny evaluation_interval
    rules:
      - alert: NazwaAlertu
        expr: <wyrażenie PromQL>
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "Krótki opis alertu"
          description: "Rozszerzony opis z wartościami zmiennych"
```

### Znaczenie poszczególnych pól

| Pole | Wymagane | Opis |
|---|---|---|
| `alert` | tak | Nazwa alertu — powinna być unikalna, pisana w konwencji PascalCase, jednoznacznie opisująca problem (np. `HighCpuUsage`, `TargetDown`). |
| `expr` | tak | Wyrażenie PromQL zwracające wektor. Alert jest aktywny dla każdej serii czasowej zwróconej przez wyrażenie. |
| `for` | nie | Czas, przez jaki warunek `expr` musi być nieprzerwanie spełniony, zanim alert przejdzie ze stanu `pending` do `firing`. |
| `labels` | nie | Dodatkowe etykiety dołączane do alertu — wykorzystywane później przez Alertmanagera do routingu, grupowania i wyciszania. |
| `annotations` | nie | Metadane opisowe (np. `summary`, `description`, `runbook_url`) — nie są używane do routingu, tylko do prezentacji informacji człowiekowi. |

## Cykl życia alertu i rola parametru `for`

Alert przechodzi przez trzy stany:

1. **Inactive** — warunek `expr` nie jest spełniony.
2. **Pending** — warunek jest spełniony, ale nie upłynął jeszcze czas określony w `for`.
3. **Firing** — warunek jest spełniony nieprzerwanie przez co najmniej czas `for`; alert zostaje wysłany do Alertmanagera.

Parametr `for` jest kluczowym mechanizmem ochrony przed tzw. **flappingiem**, czyli sytuacją, w której metryka oscyluje wokół progu alarmowego, powodując naprzemienne generowanie i wygaszanie alertu w krótkich odstępach czasu. Bez `for` każde pojedyncze przekroczenie progu (nawet trwające jeden cykl ewaluacji) natychmiast generowałoby powiadomienie, co prowadzi do „zmęczenia alertami” (*alert fatigue*) i ignorowania powiadomień przez zespół.

Dobór wartości `for` powinien być kompromisem między szybkością reakcji a odpornością na chwilowe skoki metryki:

- alerty krytyczne dotyczące dostępności (np. `up == 0`) — zwykle `1m`–`2m`,
- alerty dotyczące zasobów (CPU, pamięć, dysk) — zwykle `5m`–`15m`,
- alerty o charakterze pojemnościowym (trend długoterminowy) — nawet `30m`–`1h`.

## Przykładowe kompletne reguły alertowe

### 1. Wysokie zużycie CPU

```yaml
groups:
  - name: zasoby-hosta
    rules:
      - alert: HighCpuUsage
        expr: |
          100 - (avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100) > 85
        for: 10m
        labels:
          severity: warning
          team: infra
        annotations:
          summary: "Wysokie zużycie CPU na {{ $labels.instance }}"
          description: >
            Instancja {{ $labels.instance }} wykazuje średnie zużycie CPU na poziomie
            {{ printf "%.2f" $value }}% w ciągu ostatnich 5 minut (próg: 85%).
```

### 2. Target niedostępny (down)

```yaml
      - alert: TargetDown
        expr: up == 0
        for: 2m
        labels:
          severity: critical
          team: infra
        annotations:
          summary: "Target {{ $labels.job }}/{{ $labels.instance }} jest niedostępny"
          description: >
            Prometheus nie może pobrać metryk z {{ $labels.instance }} (job: {{ $labels.job }})
            od ponad 2 minut. Sprawdź proces exportera oraz łączność sieciową.
```

### 3. Mało miejsca na dysku

```yaml
      - alert: LowDiskSpace
        expr: |
          (node_filesystem_avail_bytes{fstype!~"tmpfs|overlay"}
            / node_filesystem_size_bytes{fstype!~"tmpfs|overlay"}) * 100 < 10
        for: 15m
        labels:
          severity: warning
          team: infra
        annotations:
          summary: "Mało wolnego miejsca na {{ $labels.mountpoint }} ({{ $labels.instance }})"
          description: >
            Na partycji {{ $labels.mountpoint }} hosta {{ $labels.instance }} pozostało
            zaledwie {{ printf "%.2f" $value }}% wolnego miejsca. Rozważ czyszczenie
            logów lub rozszerzenie wolumenu.
```

## Zmienne `$labels` i `$value` w adnotacjach

Sekcje `annotations` (a także `labels`) obsługują szablony Go template (analogicznie do reguł zapisu). Dostępne są dwie kluczowe zmienne:

- `$labels.<nazwa_etykiety>` — pozwala odwołać się do dowolnej etykiety zwróconej przez `expr` (np. `instance`, `job`, `device`, `mountpoint`), co pozwala spersonalizować treść komunikatu bez tworzenia osobnej reguły dla każdego hosta.
- `$value` — zwraca liczbową wartość wyniku wyrażenia dla danej serii; warto formatować ją funkcją `printf`, aby uniknąć nadmiarowej liczby miejsc po przecinku (np. `{{ printf "%.2f" $value }}`).

Dzięki temu jedna reguła obsługuje dowolną liczbę instancji/etykiet, a każde powiadomienie zawiera konkretne, kontekstowe dane.

## Walidacja reguł narzędziem `promtool`

Przed wdrożeniem reguł na produkcję należy zawsze zwalidować składnię i semantykę pliku za pomocą narzędzia `promtool`, dołączonego do dystrybucji Prometheusa:

```bash
promtool check rules /etc/prometheus/rules/alerty.yml
```

Narzędzie wykrywa m.in.:

- błędy składni YAML,
- niepoprawne wyrażenia PromQL,
- brak wymaganych pól (`alert`, `expr`),
- ostrzeżenia dotyczące dobrych praktyk (np. brak `for` przy regułach opartych na chwilowych wartościach).

`promtool` umożliwia również testowanie reguł na podstawie symulowanych szeregów czasowych:

```bash
promtool test rules test_alerty.yml
```

## Dobre praktyki

- Nazywaj alerty jednoznacznie i konsekwentnie (PascalCase, bez skrótów wymagających kontekstu).
- Zawsze definiuj etykietę `severity` (np. `critical`, `warning`, `info`) — jest to podstawa późniejszego routingu w Alertmanagerze.
- Unikaj bardzo krótkich wartości `for` dla metryk o dużej zmienności — to prosta droga do flappingu.
- W `annotations.description` zawsze podawaj konkretną wartość (`$value`) oraz kontekst (`$labels`), aby dyżurny nie musiał uruchamiać dodatkowych zapytań, żeby zrozumieć skalę problemu.
- Dodawaj `annotations.runbook_url` wskazujący na dokumentację procedury reagowania — skraca czas diagnozy podczas dyżuru.
- Integruj `promtool check rules` z pipeline CI/CD, aby błędna reguła nigdy nie trafiła na środowisko produkcyjne.
