## Instrumentacja jako alternatywa dla eksportera zewnętrznego
![Prometheus](/grafiki/m5-4.3-biblioteki-klienckie-w-instrumentacji-aplikacji.png)

Gdy mamy dostęp do kodu źródłowego własnej aplikacji, najlepszym podejściem nie jest pisanie osobnego exportera obok niej, lecz bezpośrednia instrumentacja — wbudowanie generowania metryk w logikę aplikacji za pomocą oficjalnej biblioteki klienckiej (client library). Dzięki temu aplikacja sama staje się swoim własnym „exporterem": wystawia endpoint `/metrics` w tym samym procesie, w którym działa jej logika biznesowa, mając bezpośredni dostęp do wewnętrznego stanu (liczby żądań w danym module, czasu trwania konkretnych operacji, rozmiaru kolejek wewnętrznych), którego zewnętrzny exporter nigdy by nie zobaczył.

Prometheus utrzymuje oficjalne biblioteki klienckie dla czterech głównych języków, oraz szereg bibliotek wspieranych przez społeczność dla pozostałych:

| Język | Biblioteka | Uwagi |
|---|---|---|
| Go | `github.com/prometheus/client_golang` | Referencyjna implementacja, sam Prometheus jest napisany w Go |
| Java / JVM | `io.prometheus:simpleclient` (starsza) / `io.prometheus:prometheus-metrics-core` (nowa generacja) | Integracje ze Spring Boot (Micrometer), Dropwizard |
| Python | `prometheus_client` | Najprostsza w użyciu, popularna w skryptach i mikroserwisach Flask/Django/FastAPI |
| Node.js / JavaScript | `prom-client` | Middleware gotowe dla Express |

Każda z bibliotek implementuje ten sam zestaw prymitywów (Counter, Gauge, Histogram, Summary) i ten sam format ekspozycji, dzięki czemu niezależnie od języka aplikacji, dane trafiające do Prometheusa wyglądają identycznie.

## Instrumentacja krok po kroku — przykład w Pythonie

### 1. Instalacja zależności

```bash
pip install prometheus_client
```

### 2. Definicja metryk

Metryki definiuje się raz, jako obiekty globalne modułu, poza cyklem obsługi pojedynczego żądania:

```python
from prometheus_client import Counter, Histogram, start_http_server
import time
import random

# Counter — liczba obsłużonych żądań, z etykietami metody i statusu
REQUEST_COUNT = Counter(
    "app_http_requests_total",
    "Łączna liczba żądań HTTP obsłużonych przez aplikację",
    ["method", "endpoint", "status"]
)

# Histogram — czas trwania obsługi żądania w sekundach
REQUEST_LATENCY = Histogram(
    "app_http_request_duration_seconds",
    "Czas trwania obsługi żądania HTTP",
    ["endpoint"],
    buckets=[0.05, 0.1, 0.25, 0.5, 1, 2.5, 5, 10]
)
```

### 3. Instrumentacja logiki biznesowej

```python
def handle_request(endpoint: str):
    start_time = time.time()
    status = "200"
    try:
        # --- właściwa logika obsługi żądania ---
        time.sleep(random.uniform(0.01, 0.3))
        if random.random() < 0.05:
            status = "500"
            raise RuntimeError("Symulowany błąd wewnętrzny")
    except RuntimeError:
        pass
    finally:
        duration = time.time() - start_time
        REQUEST_LATENCY.labels(endpoint=endpoint).observe(duration)
        REQUEST_COUNT.labels(method="GET", endpoint=endpoint, status=status).inc()
```

Dekoratory biblioteki upraszczają ten wzorzec jeszcze bardziej — `@REQUEST_LATENCY.time()` automatycznie zmierzy czas wykonania funkcji, a `.inc()` wywoływane wprost w miejscu obsługi błędu jest czytelniejsze niż ręczne liczenie czasu.

### 4. Wystawienie endpointu /metrics

```python
if __name__ == "__main__":
    start_http_server(8000)  # uruchamia wątek HTTP serwujący /metrics na porcie 8000
    while True:
        handle_request(endpoint="/api/orders")
        time.sleep(1)
```

Po uruchomieniu skryptu pod adresem `http://localhost:8000/metrics` dostępny będzie standardowy format ekspozycji zawierający m.in.:

```
# TYPE app_http_requests_total counter
app_http_requests_total{endpoint="/api/orders",method="GET",status="200"} 42
app_http_requests_total{endpoint="/api/orders",method="GET",status="500"} 2
# TYPE app_http_request_duration_seconds histogram
app_http_request_duration_seconds_bucket{endpoint="/api/orders",le="0.1"} 15
app_http_request_duration_seconds_bucket{endpoint="/api/orders",le="0.25"} 33
app_http_request_duration_seconds_bucket{endpoint="/api/orders",le="+Inf"} 44
app_http_request_duration_seconds_sum{endpoint="/api/orders"} 6.71
app_http_request_duration_seconds_count{endpoint="/api/orders"} 44
```

### 5. Podłączenie do Prometheusa

Wystarczy dodać standardowy job scrape w `prometheus.yml`:

```yaml
scrape_configs:
  - job_name: 'moja-aplikacja'
    static_configs:
      - targets: ['localhost:8000']
```

W przypadku frameworków webowych (Flask, Django, FastAPI, Express) zamiast osobnego `start_http_server()` częściej podpina się middleware, które automatycznie owija każdy handler HTTP i eksponuje metryki na tym samym porcie co reszta aplikacji, np. na dedykowanej ścieżce `/metrics` wewnątrz istniejącego serwera WWW — jest to podejście bezpieczniejsze operacyjnie, bo nie wymaga otwierania dodatkowego portu.

## White-box vs black-box — fundamentalna różnica podejść

**Instrumentacja white-box** (biała skrzynka) oznacza pomiar systemu od wewnątrz, z pełną wiedzą o jego strukturze wewnętrznej. Biblioteki klienckie opisane powyżej są klasycznym przykładem white-box: kod aplikacji sam wie, kiedy rozpoczyna się i kończy dana operacja, jaki miała status, w którym module wystąpił błąd. White-box pozwala odpowiedzieć na pytanie „dlaczego coś jest wolne" — np. wskazać dokładnie, która funkcja czy zapytanie SQL zajmuje najwięcej czasu.

**Instrumentacja black-box** (czarna skrzynka), realizowana przez `blackbox_exporter`, polega na obserwacji systemu wyłącznie z zewnątrz, bez żadnej wiedzy o jego wnętrzu — dokładnie tak, jak widziałby go klient lub użytkownik końcowy. Sonda wysyła żądanie HTTP, ping ICMP czy zapytanie DNS i mierzy wynik (dostępność, czas odpowiedzi, poprawność certyfikatu), niezależnie od tego, czy monitorowana usługa w ogóle ma zainstalowaną jakąkolwiek instrumentację.

Te dwa podejścia są komplementarne, nie konkurencyjne:

| Aspekt | White-box | Black-box |
|---|---|---|
| Punkt widzenia | Wewnątrz aplikacji | Z zewnątrz, jak klient |
| Wymaga zmian w kodzie | Tak | Nie |
| Odpowiada na pytanie | „Co dokładnie jest wolne/zepsute?" | „Czy usługa w ogóle działa dla użytkownika?" |
| Typowe narzędzie | client library (`prometheus_client`, `client_golang`) | `blackbox_exporter` |
| Wykrywa awarie infrastruktury sieciowej (DNS, firewall, load balancer) | Zwykle nie | Tak |

Dojrzały system monitoringu stosuje oba podejścia równolegle: white-box do diagnozowania przyczyn źródłowych wewnątrz własnych aplikacji, black-box do weryfikacji rzeczywistego doświadczenia użytkownika końcowego oraz do monitorowania systemów, do których kodu nie mamy dostępu.
