Liczba dashboardów w organizacji rośnie proporcjonalnie do dojrzałości monitoringu — po kilku miesiącach eksploatacji typowe wdrożenie liczy dziesiątki, a w większych środowiskach setki dashboardów. Bez świadomej organizacji, konwencji nazewniczych i zarządzania jako kod dashboardy szybko stają się chaotyczną, niezarządzalną masą duplikatów. Poniższe praktyki adresują ten problem na poziomie organizacyjnym, technicznym i procesowym.

## Organizacja dashboardów w foldery

Grafana pozwala grupować dashboardy w hierarchię folderów (**Dashboards → New folder**), na których dodatkowo można nadawać uprawnienia niezależnie od uprawnień globalnych. Rekomendowana struktura folderów opiera się zwykle na jednym z dwóch kryteriów (lub ich kombinacji):

- **Wg zespołu/domeny odpowiedzialności** — np. `Infrastruktura`, `Bazy danych`, `Aplikacje-backend`, `Sieć`.
- **Wg środowiska** — np. `Produkcja`, `Staging`, `Lab/Dev`, co ułatwia stosowanie odrębnych uprawnień dostępu (środowisko produkcyjne często wymaga węższego grona edytorów).

W większych organizacjach stosuje się strukturę dwupoziomową, np. `Produkcja/Bazy danych`, `Produkcja/Aplikacje`, `Staging/Aplikacje`. Foldery „Ogólne” (General) powinny pozostać praktycznie puste — to typowe miejsce, gdzie z braku dyscypliny gromadzą się niesklasyfikowane dashboardy testowe.

## Konwencje nazewnicze

Spójna konwencja nazewnicza dashboardów i paneli jest warunkiem sprawnego wyszukiwania i utrzymania. Rekomendowany wzorzec nazwy dashboardu:

```
[Domena] - [Komponent] - [Poziom szczegółowości]
```

Przykłady: `Infra - Node Exporter - Overview`, `Infra - Node Exporter - Details`, `App - API Gateway - SLO`. Dodatkowo warto stosować **tagi** dashboardu (Dashboard settings → General → Tags), np. `prometheus`, `production`, `node-exporter`, umożliwiające filtrowanie na liście dashboardów niezależnie od struktury folderów.

Zasady dobrej konwencji:

- Unikać nazw generycznych typu „Dashboard 1”, „Test”, „kopia dashboardu XYZ”.
- Ujednolicić język (całość po polsku albo całość po angielsku — mieszanie utrudnia wyszukiwanie).
- W nazwach paneli unikać powtarzania nazwy dashboardu (kontekst jest już znany) — panel powinien nazywać się np. „Zużycie CPU”, a nie „Node Exporter – Zużycie CPU”.
- Numeracja wersji dashboardu (np. „v2”) w nazwie jest antywzorcem — do wersjonowania służy git, nie nazwa pliku/dashboardu.

## Zarządzanie dashboardami jako kod (Grafana as Code)

Ręczne tworzenie i edytowanie dashboardów przez UI jest wystarczające na etapie prototypowania, ale w środowisku produkcyjnym prowadzi do rozjazdu konfiguracji, braku historii zmian i ryzyka przypadkowej edycji przez osoby nieuprawnione. Standardem branżowym jest podejście **Grafana as Code** — trzymanie definicji dashboardów jako plików w repozytorium i automatyczne ładowanie ich do Grafany przez mechanizm **provisioning**.

### Provisioning z plików

Grafana od uruchomienia skanuje katalogi wskazane w konfiguracji provisioning i automatycznie ładuje z nich definicje dashboardów oraz data source'ów. Konfiguracja providera dashboardów (`/etc/grafana/provisioning/dashboards/dashboards.yaml`):

```yaml
apiVersion: 1

providers:
  - name: "Infrastruktura"
    orgId: 1
    folder: "Infrastruktura"
    type: file
    disableDeletion: false
    updateIntervalSeconds: 30
    allowUiUpdates: false
    options:
      path: /var/lib/grafana/dashboards/infrastruktura
      foldersFromFilesStructure: true
```

Kluczowe parametry:

- **allowUiUpdates: false** — blokuje zapisywanie zmian z poziomu UI dla dashboardów pochodzących z provisioningu, wymuszając edycję wyłącznie przez pliki źródłowe (zapobiega rozjazdowi konfiguracji).
- **foldersFromFilesStructure** — pozwala odwzorować strukturę katalogów na strukturę folderów w Grafanie.
- **updateIntervalSeconds** — częstotliwość, z jaką Grafana sprawdza katalog pod kątem zmian plików JSON.

Pliki dashboardów w katalogu `path` to standardowe eksporty JSON dashboardu (Dashboard settings → JSON Model, lub Share → Export → Save to file).

### Grafonnet i Jsonnet

Ręczne utrzymywanie surowego JSON-a dashboardu jest uciążliwe — pliki liczą tysiące linii, a drobna zmiana (np. dodanie panelu do wielu podobnych dashboardów) wymaga edycji w wielu miejscach. Rozwiązaniem jest **Jsonnet** — język szablonowy generujący JSON, w połączeniu z biblioteką **grafonnet** (oficjalna biblioteka Grafana Labs dostarczająca funkcje do programowego budowania paneli, zmiennych i layoutów).

Przykład fragmentu definicji panelu w grafonnet:

```jsonnet
local grafonnet = import 'github.com/grafana/grafonnet/gen/grafonnet-latest/main.libsonnet';
local panel = grafonnet.panel;
local ts = panel.timeSeries;

ts.new('Zużycie CPU')
+ ts.queryOptions.withTargets([
    grafonnet.query.prometheus.new(
      'Prometheus-prod',
      '100 - (avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100)'
    )
  ])
+ ts.standardOptions.withUnit('percent')
+ ts.standardOptions.thresholds.withSteps([
    { color: 'green', value: null },
    { color: 'yellow', value: 70 },
    { color: 'red', value: 90 },
  ])
```

Zalety podejścia Jsonnet/grafonnet:

- **Reużywalność** — wspólne definicje paneli (np. standardowy panel CPU) można zaimportować w wielu dashboardach dla różnych komponentów, eliminując duplikację.
- **Parametryzacja** — jeden szablon Jsonnet może generować rodzinę niemal identycznych dashboardów dla różnych mikroserwisów, różniących się tylko nazwą joba i etykietami.
- **Spójność wizualna** — wspólne definicje kolorów, progów i jednostek gwarantują jednolity wygląd wszystkich dashboardów w organizacji.

Kompilację plików `.jsonnet` do finalnego `.json` wykonuje się narzędziem `jsonnet` lub `jb` (jsonnet-bundler do zarządzania zależnościami), zwykle jako krok w pipeline CI/CD.

## Kontrola dostępu i uprawnień

Grafana oferuje kilka poziomów kontroli dostępu:

- **Role organizacyjne** — Viewer (tylko odczyt), Editor (tworzenie/edycja dashboardów), Admin (pełna administracja instancją).
- **Uprawnienia na poziomie folderu/dashboardu** — możliwość nadania konkretnemu zespołowi lub użytkownikowi uprawnień Viewer/Editor/Admin tylko do wybranego folderu, niezależnie od roli globalnej — kluczowe przy separacji dostępu do dashboardów produkcyjnych od środowisk deweloperskich.
- **Teams** — grupowanie użytkowników w zespoły i nadawanie uprawnień zespołowo zamiast indywidualnie każdemu kontu, co znacząco upraszcza administrację przy większej liczbie użytkowników.
- **Data source permissions** — ograniczenie, którzy użytkownicy/zespoły mogą wykorzystywać dane źródło danych w swoich zapytaniach, istotne przy segregacji dostępu do danych wrażliwych.

Zasada minimalnych uprawnień: dashboardy produkcyjne ładowane przez provisioning powinny mieć `allowUiUpdates: false`, a bezpośredni dostęp Editor do folderów produkcyjnych ograniczony do wąskiego grona osób odpowiedzialnych za utrzymanie monitoringu.

## Eksport, import i wersjonowanie w repozytorium git

Niezależnie od tego, czy dashboard powstał ręcznie w UI, czy jako wynik kompilacji Jsonnet, jego docelowym miejscem przechowywania powinno być repozytorium git, a nie wyłącznie wewnętrzna baza danych Grafany. Praktyczny workflow:

1. Eksport definicji dashboardu do JSON: **Dashboard settings → JSON Model** (podgląd) lub **Share → Export → Save to file** (pobranie pliku).
2. Commit pliku JSON (lub źródła Jsonnet) do repozytorium, w katalogu odzwierciedlającym strukturę folderów Grafany.
3. Pull request z code review — zmiany w dashboardach produkcyjnych powinny przechodzić ten sam proces przeglądu co zmiany w kodzie aplikacji, szczególnie przy modyfikacji progów alertowych powiązanych wizualnie z dashboardem.
4. Automatyczne wdrożenie przez pipeline CI/CD, które kopiuje zaktualizowane pliki JSON do katalogu provisioning Grafany (lub korzysta z Grafana API/Terraform provider `grafana_dashboard` do wdrożenia bez restartu usługi).

Dodatkowe zalecenia:

- Przed eksportem do repozytorium warto usunąć z JSON-a pole `id` (specyficzne dla instancji, w której dashboard powstał) i pozostawić `uid` jako stabilny identyfikator między środowiskami.
- Wartości `datasource` w eksportowanym JSON-ie warto sparametryzować (placeholder podstawiany przy imporcie), aby ten sam plik dashboardu działał identycznie w środowisku lab, staging i produkcyjnym, różniącym się nazwą data source'a.
- Historia zmian w git zastępuje mechanizm **Dashboard version history** wbudowany w Grafanę (Dashboard settings → Versions) — ten drugi jest przydatny do szybkiego podglądu „kto i kiedy zmienił dashboard z poziomu UI”, ale nie zastępuje pełnoprawnego procesu code review i nie przetrwa np. reinstalacji instancji Grafany.

Konsekwentne stosowanie powyższych praktyk — foldery, konwencje nazewnicze, provisioning, Jsonnet/grafonnet, kontrola dostępu i wersjonowanie w git — przekłada się bezpośrednio na czas potrzebny inżynierowi dyżurnemu na odnalezienie właściwego dashboardu podczas incydentu, co ma bezpośredni wpływ na czas MTTR (Mean Time To Resolution).
