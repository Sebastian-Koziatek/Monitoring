# Integracja Prometheus + Grafana
![Prometheus](/grafiki/m5-7.1-integracja-prometheus-grafana.png)
Prometheus dostarcza silnik zapytań i magazyn szeregów czasowych, natomiast wizualizacja, budowa dashboardów i prezentacja danych operacyjnych odbywa się w Grafanie. Poprawna integracja tych dwóch narzędzi to fundament, na którym opiera się cały dalszy proces dashboardingu — zaczyna się od skonfigurowania Prometheusa jako źródła danych (data source) w Grafanie.

## Dodawanie Prometheusa jako data source

Konfigurację źródła danych wykonuje się w Grafanie w sekcji **Connections → Data sources → Add data source → Prometheus**. Kluczowe pola konfiguracyjne:

- **Name** — nazwa identyfikująca źródło danych w dashboardach (np. `Prometheus-prod`, `Prometheus-lab`). W środowiskach z wieloma instancjami Prometheusa (multi-cluster, multi-region) nazwa powinna jednoznacznie wskazywać, którego środowiska dotyczy.
- **URL** — adres HTTP API Prometheusa, np. `http://prometheus.example.local:9090`. Musi wskazywać na endpoint API (Grafana odpytuje `/api/v1/query`, `/api/v1/query_range` itd.), nie na konkretną ścieżkę zapytania.
- **Access mode** — sposób, w jaki żądania trafiają do Prometheusa:
  - **Server (default)** — żądania wysyła serwer Grafany (backend), a nie przeglądarka klienta. To jest tryb rekomendowany w praktycznie wszystkich wdrożeniach produkcyjnych: adres Prometheusa nie musi być osiągalny z sieci użytkowników, a autoryzacja (np. certyfikaty klienckie, nagłówki) jest zarządzana centralnie po stronie serwera Grafany.
  - **Browser** — żądania HTTP wykonuje bezpośrednio przeglądarka użytkownika, co wymaga, aby Prometheus był publicznie osiągalny z sieci klienta oraz poprawnie skonfigurowany CORS po stronie Prometheusa (flaga `--web.cors.origin`). Tryb ten praktycznie nie jest stosowany w środowiskach korporacyjnych ze względu na wymogi bezpieczeństwa i utrudnioną autoryzację.

W większości wdrożeń jsystems/SADMIN standardem jest tryb **Server**, ponieważ eliminuje konieczność wystawiania Prometheusa poza sieć wewnętrzną.

## Autoryzacja i zabezpieczenie połączenia

Prometheus domyślnie nie ma wbudowanego mechanizmu uwierzytelniania — dostęp zabezpiecza się zwykle na poziomie warstwy pośredniczącej (reverse proxy). W konfiguracji data source w Grafanie dostępne są następujące mechanizmy:

- **Basic Auth** — nazwa użytkownika i hasło przesyłane w nagłówku `Authorization`, weryfikowane przez proxy (np. Nginx, Nginx Proxy Manager) stojące przed Prometheusem.
- **TLS Client Auth / With CA Cert** — konfiguracja certyfikatów klienckich, jeśli Prometheus lub proxy wymaga mTLS.
- **Custom HTTP Headers** — możliwość dodania własnych nagłówków, np. tokenów API wymaganych przez warstwę autoryzacyjną (przydatne przy integracji z reverse proxy typu OAuth2-Proxy).
- **Skip TLS Verify** — opcja do wyłączenia weryfikacji certyfikatu TLS; stosowana wyłącznie w środowiskach testowych z certyfikatami self-signed, nigdy na produkcji.

Przykład definicji data source jako provisioning YAML (montowanego do katalogu `/etc/grafana/provisioning/datasources/`):

```yaml
apiVersion: 1

datasources:
  - name: Prometheus-prod
    type: prometheus
    access: proxy          # odpowiednik trybu "Server" w UI
    url: http://prometheus.example.local:9090
    isDefault: true
    editable: false
    jsonData:
      httpMethod: POST
      timeInterval: 30s
      queryTimeout: 60s
      basicAuth: true
    secureJsonData:
      basicAuthPassword: "${PROM_BASIC_AUTH_PASSWORD}"
    basicAuthUser: "grafana-reader"
```

Wartość `access: proxy` w pliku provisioning odpowiada trybowi „Server” widocznemu w interfejsie graficznym — to częste źródło nieporozumień, ponieważ nazewnictwo w YAML i w UI się różni.

## Parametry zapytań

W sekcji `jsonData` warto świadomie ustawić:

- **httpMethod** — `POST` jest zalecane zamiast domyślnego `GET` przy długich zapytaniach PromQL (unika limitów długości URL i problemów z cache'owaniem po stronie proxy).
- **timeInterval** (Scrape interval) — informuje Grafanę o typowym interwale zbierania metryk, co wpływa na dobór kroku (`step`) w zapytaniach `query_range` i na działanie funkcji takich jak `rate()`.
- **queryTimeout** — maksymalny czas oczekiwania na odpowiedź Prometheusa; przy dużych zapytaniach agregujących po wielu etykietach warto go podnieść powyżej wartości domyślnej.

## Weryfikacja połączenia

Po zapisaniu konfiguracji należy użyć przycisku **Save & Test**. Grafana wykonuje wtedy zapytanie testowe do API Prometheusa (`/api/v1/query?query=1+1`) i zwraca jeden z komunikatów:

- „Successfully queried the Prometheus API” — połączenie i autoryzacja działają poprawnie.
- Błąd sieciowy (timeout, connection refused) — problem z routingiem, firewallem lub adresem URL.
- Błąd 401/403 — nieprawidłowa autoryzacja (błędne dane Basic Auth, brak wymaganego nagłówka).
- Błąd 404 lub nieprawidłowa odpowiedź JSON — URL wskazuje na zły endpoint (np. brakujący port, literówka w ścieżce).

Warto dodatkowo zweryfikować połączenie ręcznie z poziomu hosta, na którym działa Grafana, poleceniem `curl -s http://prometheus.example.local:9090/api/v1/query?query=up`, aby odróżnić problem sieciowy od błędu konfiguracji w samej Grafanie.

## Podstawy edytora zapytań Grafany dla Prometheusa

Po utworzeniu panelu w dashboardzie i wybraniu źródła danych typu Prometheus dostępny jest dedykowany **query editor**, który udostępnia:

- **Pole zapytania PromQL** z podpowiadaniem składni (autouzupełnianie nazw metryk, funkcji i etykiet na podstawie danych faktycznie dostępnych w Prometheusie).
- **Builder mode / Code mode** — tryb budowania zapytania metodą wyboru z list rozwijanych (metryka → etykiety → operacje) albo tryb tekstowy do ręcznego pisania PromQL. Tryb builder jest przydatny dla osób poznających PromQL, natomiast w praktyce zawodowej dominuje tryb Code ze względu na pełną kontrolę nad wyrażeniem.
- **Legend** — szablon nazw serii w legendzie, np. `{{instance}} - {{job}}`, pozwalający czytelnie opisać wiele serii zwracanych przez jedno zapytanie z etykietami.
- **Min step** — minimalny krok próbkowania wymuszany niezależnie od rozdzielczości wykresu; istotny przy metrykach o rzadkim próbkowaniu, aby uniknąć artefaktów interpolacji.

### Format: Time series vs Table

Wybór formatu zwracanych danych (**Format**) determinuje, jak Grafana interpretuje odpowiedź z Prometheusa:

| Format | Zastosowanie | Charakterystyka |
|---|---|---|
| **Time series** | Wykresy trendów w czasie (panel Time series, Graph) | Każda unikalna kombinacja etykiet staje się osobną serią czasową; oś X to czas, oś Y to wartość metryki |
| **Table** | Zestawienia, panele Table, Stat z wieloma wartościami | Dane prezentowane jako wiersze i kolumny — etykiety jako kolumny, wartość jako ostatnia kolumna; przydatne przy zapytaniach chwilowych (instant query) zwracających wiele serii do porównania |
| **Heatmap** | Histogramy i rozkłady (np. metryki typu `histogram_quantile`) | Dane grupowane w przedziały (bucket) prezentowane jako mapa cieplna |

Dla zapytań typu `range` (czyli standardowych wykresów czasowych) właściwym formatem jest **Time series**. Dla zapytań typu `instant` — czyli pojedynczego odczytu wartości w danym momencie, np. przy budowaniu tabeli rankingowej top-N instancji według zużycia CPU — właściwym formatem jest **Table**, w połączeniu z przełącznikiem **Type: Instant** w edytorze zapytania. Nieprawidłowe dopasowanie formatu do typu panelu jest jedną z najczęstszych przyczyn błędów typu „No data” lub nieczytelnych wykresów u początkujących użytkowników Grafany.
