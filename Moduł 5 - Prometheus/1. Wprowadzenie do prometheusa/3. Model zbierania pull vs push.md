## Dwa fundamentalne podejścia do zbierania metryk

W systemach monitoringu istnieją dwa przeciwstawne modele dostarczania danych telemetrycznych do systemu centralnego:

- **Push** — monitorowany system (agent, aplikacja) sam aktywnie wysyła dane do serwera monitoringu, w momencie ich powstania lub w ustalonych odstępach czasu. Tak działają m.in. StatsD, Graphite (klasycznie), InfluxDB (line protocol), CloudWatch.
- **Pull** — serwer monitoringu sam aktywnie odpytuje monitorowane systemy o aktualne wartości metryk, w regularnych, kontrolowanych przez siebie odstępach czasu. Tak działa domyślnie Prometheus.

Prometheus świadomie i konsekwentnie wybrał model pull jako podstawowy mechanizm zbierania danych, co jest jedną z najbardziej charakterystycznych i najczęściej dyskutowanych cech tego systemu.

## Jak działa model pull w Prometheusie

Każdy monitorowany cel (target) — aplikacja, exporter, usługa — udostępnia endpoint HTTP (domyślnie `/metrics`), pod którym w danym momencie eksponuje aktualny stan swoich metryk w formacie tekstowym. Prometheus Server, zgodnie z konfiguracją `scrape_interval` (domyślnie 15-60 sekund, zależnie od zadania), wykonuje żądanie HTTP GET pod ten endpoint i zapisuje otrzymane dane wraz ze znacznikiem czasu do lokalnej bazy TSDB.

```yaml
scrape_configs:
  - job_name: "api-backend"
    scrape_interval: 10s
    scrape_timeout: 5s
    static_configs:
      - targets: ["api-1:8080", "api-2:8080"]
```

Kluczowa cecha: to Prometheus decyduje, *kiedy* i *czy w ogóle* dane zbierze — target jedynie odpowiada na żądanie, nie inicjuje komunikacji.

## Dlaczego Prometheus wybrał model pull — uzasadnienie projektowe

Twórcy Prometheusa wskazują kilka konkretnych powodów tej decyzji architektonicznej:

- **Łatwiejsze wykrywanie awarii monitorowanego systemu.** Jeśli Prometheus nie może pobrać metryk z targetu (timeout, connection refused), automatycznie oznacza go jako `down` — to samo w sobie jest cennym sygnałem monitoringowym (metryka `up`). W modelu push brak danych jest niejednoznaczny: czy usługa padła, czy tylko przestała wysyłać metryki, czy jest problem sieciowy po stronie odbiorcy?
- **Scentralizowana kontrola częstotliwości zbierania.** Administrator w jednym miejscu (konfiguracja Prometheusa) kontroluje, jak często i które cele są odpytywane, bez potrzeby rekonfiguracji dziesiątek czy tysięcy agentów.
- **Łatwiejsze uruchamianie lokalnie i testowanie.** Można ręcznie odpytać dowolny target (`curl http://target:9100/metrics`) i natychmiast zobaczyć jego aktualny stan, bez czekania na kolejny cykl push.
- **Ochrona przed przeciążeniem serwera monitoringu.** Serwer sam kontroluje tempo napływu danych — w modelu push tysiące agentów mogłoby zalać serwer danymi jednocześnie (thundering herd), zwłaszcza po zbiorowym restarcie.
- **Naturalna integracja z Service Discovery.** Prometheus może dynamicznie pobrać aktualną listę celów z zewnętrznego źródła (Kubernetes API, Consul) i natychmiast zacząć je odpytywać — bez konieczności konfigurowania, dokąd agent ma wysyłać dane.

## Ograniczenia modelu pull i kiedy staje się problemem

Model pull ma naturalne ograniczenia w konkretnych scenariuszach:

- **Zadania krótkotrwałe (batch, cron job)** — proces, który wykonuje się przez kilka sekund i kończy działanie, może zniknąć zanim Prometheus zdąży go odpytać. Metryki takiego zadania (czas wykonania, sukces/porażka, liczba przetworzonych rekordów) zostałyby utracone.
- **Sieci z ograniczeniami połączeń przychodzących** — środowiska za NAT, w chmurach z restrykcyjnymi regułami firewall, gdzie serwer monitoringu nie ma bezpośredniej łączności sieciowej do targetu, ale target może inicjować połączenie wychodzące.
- **Urządzenia mobilne / edge / IoT** — urządzenia z przerywaną łącznością, gdzie nie da się zagwarantować, że będą dostępne w momencie scrape'u.

## Pushgateway — most między push a pull

Dla scenariuszy, w których model pull się nie sprawdza (przede wszystkim krótkotrwałe zadania wsadowe), Prometheus udostępnia komponent **Pushgateway**. Nie jest to zamiennik modelu pull, lecz pośrednik: krótkotrwałe zadanie wypycha (push) swoje metryki do Pushgateway po zakończeniu pracy, a Pushgateway przechowuje je i eksponuje jako stały, długożyjący endpoint `/metrics`, który Prometheus Server odpytuje w standardowy sposób (pull).

```
+-------------+                                   +------------------+                                +------------+
|  Batch job  |    ---- push (HTTP PUT/POST) --->  |    Pushgateway   |   <--- scrape (pull, GET) ---  | Prometheus |
|   (cron)    |                                   |  (bufor metryk)  |                                |   Server   |
+-------------+                                   +------------------+                                +------------+
```

Przykład wysłania metryki zakończonego zadania wsadowego z poziomu skryptu bash:

```bash
JOB_NAME="backup_database"
echo "backup_last_success_timestamp $(date +%s)" | \
  curl --data-binary @- http://pushgateway:9091/metrics/job/${JOB_NAME}/instance/db01
```

W praktyce najczęściej wykorzystywane jest to w skryptach cron uruchamiających kopie zapasowe, migracje danych, joby ETL — gdzie kluczowa jest informacja "czy i kiedy zadanie ostatnio zakończyło się sukcesem".

### Ważne zastrzeżenia dotyczące Pushgateway

- Pushgateway **nie agreguje** metryk w czasie ani nie liczy historii — przechowuje jedynie ostatnią wartość wysłaną dla danej kombinacji `job`/`instance`, dopóki nie zostanie nadpisana lub ręcznie usunięta.
- Metryki w Pushgateway **nie znikają automatycznie**, gdy zadanie, które je wysłało, przestaje istnieć — może to prowadzić do fałszywego wrażenia, że stary, nieaktualny stan wciąż obowiązuje. Wymaga to świadomego zarządzania cyklem życia metryk (np. jawne usuwanie po zakończeniu przetwarzania danego joba).
- Oficjalna dokumentacja Prometheusa jednoznacznie zaleca, aby Pushgateway stosować **wyłącznie** dla zadań krótkotrwałych typu batch/cron, a **nie** jako ogólny mechanizm zbierania metryk czy sposób na obejście modelu pull dla zwykłych, długożyjących usług.

## Zalety i wady obu podejść — tabela porównawcza

| Kryterium | Model pull (Prometheus) | Model push (Pushgateway / klasyczny push) |
|---|---|---|
| Wykrywanie awarii targetu | Naturalne (target `down` przy braku odpowiedzi) | Trudne do odróżnienia od zwykłego braku wysyłki |
| Kontrola częstotliwości zbierania | Scentralizowana, w jednym miejscu (Prometheus) | Rozproszona, po stronie każdego agenta |
| Zadania krótkotrwałe (batch) | Wymaga pośrednika (Pushgateway) | Naturalnie wspierane |
| Środowiska za NAT/firewall (brak połączeń przychodzących) | Problematyczne bez dodatkowej konfiguracji | Naturalnie wspierane (połączenie wychodzące) |
| Skalowalność przy tysiącach agentów | Serwer kontroluje tempo, mniejsze ryzyko przeciążenia | Ryzyko "thundering herd" przy jednoczesnym wysyłaniu |
| Testowanie/debugowanie ręczne | Proste (`curl /metrics`) | Wymaga symulacji wysyłki danych |
| Ryzyko nieaktualnych/martwych danych | Niskie (brak odpowiedzi = `up=0`) | Wysokie przy niewłaściwym zarządzaniu (stare wpisy w Pushgateway) |

## Rekomendacja praktyczna

Domyślnym i preferowanym podejściem w ekosystemie Prometheusa jest zawsze model pull — dla usług długożyjących (serwery HTTP, bazy danych, kontenery, mikroserwisy) należy instrumentować je bibliotekami klienckimi lub użyć dedykowanego exportera. Pushgateway powinien być traktowany jako wyjątek stosowany świadomie i wyłącznie dla zadań wsadowych o krótkim czasie życia, z jasno zdefiniowaną strategią czyszczenia nieaktualnych metryk.
