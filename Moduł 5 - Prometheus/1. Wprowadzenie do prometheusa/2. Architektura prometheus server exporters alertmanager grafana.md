## Ogólny obraz ekosystemu

Prometheus nie jest pojedynczą aplikacją, lecz ekosystemem współpracujących ze sobą, luźno powiązanych komponentów. Każdy z nich odpowiada za jeden, dobrze zdefiniowany zakres odpowiedzialności — zgodnie z filozofią Unix "rób jedną rzecz i rób ją dobrze". ## Prometheus Server

Prometheus Server to centralny komponent ekosystemu, składający się z trzech logicznych podsystemów:

1. **Retrieval (scraper)** — moduł odpowiedzialny za cykliczne odpytywanie (scrape) skonfigurowanych celów (target) przez wysyłanie żądań HTTP GET do endpointu `/metrics` i parsowanie odpowiedzi w formacie tekstowym Prometheusa (lub OpenMetrics).
2. **TSDB (Time Series Database)** — wbudowany silnik przechowywania danych na dysku lokalnym, zoptymalizowany pod kątem szeregów czasowych (szczegóły w rozdziale o TSDB).
3. **HTTP Server + PromQL engine** — udostępnia API HTTP do wykonywania zapytań PromQL, przeglądania konfiguracji, stanu targetów oraz wbudowany interfejs webowy do eksploracji danych.

Dodatkowo Prometheus Server zawiera silnik reguł (**Rule Manager**), który cyklicznie ewaluuje dwa typy reguł zdefiniowanych w plikach konfiguracyjnych:

- **recording rules** — prekalkulują często używane lub kosztowne wyrażenia PromQL i zapisują wynik jako nową serię czasową, przyspieszając późniejsze zapytania i dashboardy.
- **alerting rules** — definiują warunki, przy spełnieniu których generowany jest alert, przekazywany następnie do Alertmanagera.

Przykład konfiguracji zadania zbierania (`prometheus.yml`):

```yaml
global:
  scrape_interval: 15s
  evaluation_interval: 15s

rule_files:
  - "alerts/*.yml"

scrape_configs:
  - job_name: "node"
    static_configs:
      - targets: ["10.0.0.11:9100", "10.0.0.12:9100"]

  - job_name: "kubernetes-pods"
    kubernetes_sd_configs:
      - role: pod

alerting:
  alertmanagers:
    - static_configs:
        - targets: ["alertmanager:9093"]
```

## Exporters

Exporter to lekki, wyspecjalizowany proces, który pobiera dane telemetryczne z systemu docelowego (który sam nie potrafi mówić "językiem" Prometheusa) i eksponuje je w formacie tekstowym zgodnym z formatem ekspozycji Prometheusa pod endpointem HTTP (domyślnie `/metrics`). Exporter działa jako "tłumacz" pomiędzy natywnym API danego systemu a Prometheusem.

Najpopularniejsze exportery:

- **node_exporter** — metryki systemowe hosta Linux/Unix (CPU, RAM, dysk, sieć, filesystem).
- **windows_exporter** — odpowiednik dla systemów Windows.
- **mysqld_exporter**, **postgres_exporter** — metryki baz danych.
- **blackbox_exporter** — sondowanie dostępności (probing) usług przez HTTP, TCP, ICMP, DNS z zewnątrz.
- **cAdvisor** — metryki zużycia zasobów przez kontenery.
- **kube-state-metrics** — stan obiektów API Kubernetesa (Deploymenty, Pody, ReplicaSety).

Format ekspozycji metryki wygląda następująco:

```
# HELP node_cpu_seconds_total Seconds the CPUs spent in each mode.
# TYPE node_cpu_seconds_total counter
node_cpu_seconds_total{cpu="0",mode="idle"} 182933.44
```

Aplikacje własne zamiast osobnego exportera zwykle korzystają bezpośrednio z bibliotek klienckich (client library) Prometheusa, wbudowując endpoint `/metrics` we własny kod.

## Service Discovery

W środowiskach dynamicznych ręczne utrzymywanie listy targetów jest niepraktyczne. Service Discovery (SD) to mechanizm, dzięki któremu Prometheus Server automatycznie odkrywa, jakie cele powinien monitorować, i aktualizuje tę listę w czasie rzeczywistym. Prometheus wspiera natywnie wiele mechanizmów SD, m.in.:

- **kubernetes_sd_config** — odpytuje API Kubernetesa o Pody, Serwisy, Endpointy, Node'y.
- **consul_sd_config** — integracja z Consul.
- **ec2_sd_config / azure_sd_config / gce_sd_config** — odkrywanie instancji w chmurach publicznych.
- **dns_sd_config** — odkrywanie na podstawie rekordów DNS (SRV).
- **file_sd_config** — odkrywanie na podstawie plików JSON/YAML generowanych zewnętrznie (uniwersalny mechanizm integracji z dowolnym źródłem).
- **static_configs** — statyczna lista, stosowana w prostych/małych środowiskach.

Mechanizm SD dostarcza listę potencjalnych targetów wraz z metadanymi (etykiety), które następnie mogą zostać przetworzone przez reguły `relabel_configs` — pozwalające filtrować, przemianowywać lub odrzucać targety jeszcze przed rozpoczęciem scrape'owania.

## Alertmanager

Alertmanager to niezależny komponent odpowiedzialny za obsługę alertów wysyłanych przez jeden lub wiele serwerów Prometheus. Kluczowe funkcje:

- **Grupowanie (grouping)** — łączenie wielu powiązanych alertów w jedno powiadomienie (np. wszystkie alerty dotyczące tego samego klastra).
- **Wyciszanie (silencing)** — czasowe wstrzymanie powiadomień dla wybranych alertów, np. podczas zaplanowanych prac serwisowych.
- **Tłumienie (inhibition)** — blokowanie alertów niższego priorytetu, gdy aktywny jest już alert nadrzędny (np. brak sensu w wysyłaniu alertów o pojedynczych podach, gdy cały klaster jest niedostępny).
- **Routing** — kierowanie alertów do odpowiednich odbiorców (zespołów, kanałów) na podstawie etykiet, z obsługą eskalacji.
- **Integracje** — natywne wsparcie dla e-mail, Slack, PagerDuty, OpsGenie, webhooków generycznych.

Przykład prostej konfiguracji routingu (`alertmanager.yml`):

```yaml
route:
  receiver: "default-team"
  group_by: ["alertname", "cluster"]
  routes:
    - match:
        severity: critical
      receiver: "pagerduty-oncall"

receivers:
  - name: "default-team"
    slack_configs:
      - channel: "#alerts"
  - name: "pagerduty-oncall"
    pagerduty_configs:
      - routing_key: "<klucz>"
```

## Grafana

Grafana nie jest formalnie częścią projektu Prometheus, ale w praktyce stanowi standardowy front-end wizualizacyjny całego stosu. Grafana łączy się z Prometheus Server poprzez jego HTTP API, wykonując zapytania PromQL i renderując wyniki jako dashboardy, wykresy, tabele, alerty wizualne i panele stanu. Kluczowe elementy integracji:

- **Data source** — konfiguracja połączenia Grafany z endpointem Prometheusa (adres URL, uwierzytelnianie).
- **Dashboardy** — gotowe, importowalne szablony (np. dla node_exporter czy kube-state-metrics) dostępne w publicznym repozytorium grafana.com/dashboards.
- **Grafana Alerting** — od wersji Grafana 8+ możliwe jest również definiowanie reguł alertowania bezpośrednio w Grafanie, jako alternatywa lub uzupełnienie reguł Prometheusa/Alertmanagera.

## Przepływ danych od metryki do alertu — podsumowanie

1. Aplikacja/exporter eksponuje metryki pod `/metrics`.
2. Service Discovery dostarcza Prometheus Serverowi aktualną listę targetów.
3. Prometheus Server cyklicznie (co `scrape_interval`) pobiera (scrape) metryki i zapisuje je w TSDB.
4. Rule Manager ewaluuje recording rules (dane trafiają z powrotem do TSDB) oraz alerting rules.
5. Gdy warunek alertu jest spełniony przez czas określony w `for`, alert trafia do Alertmanagera.
6. Alertmanager grupuje, wycisza/tłumi i kieruje powiadomienie do odpowiedniego kanału.
7. Równolegle Grafana (lub wbudowany UI Prometheusa) wykonuje zapytania PromQL do wizualizacji trendów historycznych i bieżącego stanu systemu.
