Prometheus jest jednym z najlepiej samoobserwowalnych systemów monitoringu — sam eksponuje bogaty zestaw metryk o własnym działaniu oraz udostępnia dedykowane narzędzia diagnostyczne do analizy bazy danych szeregów czasowych (TSDB). Umiejętność korzystania z nich jest niezbędna do wykrywania problemów wydajnościowych, zanim doprowadzą one do przepełnienia pamięci, dysku lub utraty danych.

## Self-monitoring: `/metrics` samego Prometheusa

Prometheus scrape'uje sam siebie jak każdy inny target (typowa konfiguracja `job_name: 'prometheus'` wskazująca `localhost:9090`) i eksponuje setki metryk opisujących własny stan wewnętrzny. Najważniejsze grupy do monitorowania:

| Metryka | Znaczenie |
|---|---|
| `prometheus_tsdb_head_series` | Liczba aktywnych szeregów czasowych w head blocku — kluczowy wskaźnik kardynalności. |
| `prometheus_tsdb_head_chunks` | Liczba aktywnych chunków w pamięci. |
| `prometheus_tsdb_symbol_table_size_bytes` | Rozmiar tabeli symboli (nazwy metryk i wartości labeli) — rośnie wraz z kardynalnością etykiet. |
| `prometheus_tsdb_compactions_total` / `_failed_total` | Liczba (i błędy) kompakcji bloków na dysku. |
| `prometheus_tsdb_wal_fsync_duration_seconds` | Czas zapisu WAL — wysokie wartości sugerują wolny dysk. |
| `prometheus_tsdb_storage_blocks_bytes` | Rozmiar danych na dysku. |
| `prometheus_target_scrape_pool_targets` / `_pool_target_limit` | Liczba targetów w puli i ewentualny limit. |
| `prometheus_rule_evaluation_duration_seconds` | Czas ewaluacji reguł — wydłużanie się wskazuje na przeciążenie CPU lub zbyt złożone reguły. |
| `prometheus_rule_evaluation_failures_total` | Błędy ewaluacji reguł (np. przekroczenie limitu czasu). |
| `scrape_duration_seconds` (per target) | Czas trwania scrape'u — jeśli zbliża się do `scrape_interval`, grozi to pominiętymi cyklami. |
| `scrape_samples_scraped` | Liczba próbek pobranych z danego targetu w jednym scrape — nagły wzrost sygnalizuje eksplozję kardynalności po stronie exportera. |

Rekomendowany zestaw reguł alertujących dla self-monitoringu:

```yaml
groups:
  - name: prometheus-self-monitoring
    rules:
      - alert: PrometheusConfigReloadFailed
        expr: prometheus_config_last_reload_successful == 0
        for: 10m
        labels:
          severity: critical
      - alert: PrometheusTSDBCompactionsFailing
        expr: increase(prometheus_tsdb_compactions_failed_total[1h]) > 0
        labels:
          severity: warning
      - alert: PrometheusTooManyRestarts
        expr: changes(process_start_time_seconds{job="prometheus"}[15m]) > 2
        labels:
          severity: warning
      - alert: PrometheusRuleEvaluationSlow
        expr: prometheus_rule_group_last_duration_seconds > prometheus_rule_group_interval_seconds
        labels:
          severity: warning
```

## Status > TSDB Status w Web UI

Zakładka **Status → TSDB Status** w Web UI Prometheusa (dostępna też pod `/api/v1/status/tsdb`) prezentuje bezpośrednio z head blocku:

- **Head cardinality stats** — liczbę serii, chunków i próbek w bieżącym head blocku.
- **Top 10 metrics by series count** — nazwy metryk generujące najwięcej szeregów czasowych; pierwsze miejsce do sprawdzenia przy podejrzeniu eksplozji kardynalności.
- **Top 10 labels by number of series** — które etykiety (nazwy labeli) mają najwięcej unikalnych wartości.
- **Top 10 label pairs (name=value) by series count** — konkretne pary klucz-wartość odpowiedzialne za największą liczbę serii, np. `pod="..."` w środowisku z krótko żyjącymi podami.
- **Memory in bytes by label name** — ile pamięci zajmuje przechowywanie danej etykiety w tabeli symboli.

Ta strona jest pierwszym miejscem diagnostycznym przy podejrzeniu problemu z kardynalnością — pozwala natychmiast zidentyfikować, która metryka lub etykieta jest winowajcą, bez pisania zapytań PromQL.

## `promtool tsdb analyze`

`promtool` udostępnia narzędzia do analizy danych bezpośrednio z katalogu bloków na dysku, przydatne zwłaszcza przy analizie post-mortem lub w środowiskach bez dostępu do Web UI:

```bash
# Analiza konkretnego bloku TSDB
promtool tsdb analyze /var/lib/prometheus/data --limit=20

# Lista bloków wraz z zakresem czasowym i liczbą serii
promtool tsdb list /var/lib/prometheus/data

# Sprawdzenie spójności danych (wykrywanie uszkodzeń)
promtool tsdb dump /var/lib/prometheus/data
```

`promtool tsdb analyze` zwraca m.in.: liczbę serii w bloku, rozkład długości chunków, metryki z największą liczbą serii oraz etykiety z największą liczbą unikalnych wartości — analogicznie do strony TSDB Status, ale offline, na wybranym bloku historycznym, co pozwala prześledzić, jak kardynalność zmieniała się w czasie.

Inne przydatne polecenia diagnostyczne:

```bash
promtool check config /etc/prometheus/prometheus.yml
promtool check rules /etc/prometheus/rules/*.yml
promtool query instant http://localhost:9090 'up == 0'
promtool debug pprof http://localhost:9090   # profile CPU/heap (Go pprof)
```

`promtool debug pprof` pobiera profile `pprof` (CPU, heap, goroutine) bezpośrednio z działającego procesu — nieocenione przy diagnozowaniu, czy problem wydajnościowy leży w konkretnej funkcji silnika zapytań czy w samym zbieraniu danych.

## Typowe problemy wydajnościowe i ich rozwiązania

### Cardinality explosion (eksplozja kardynalności)

**Objawy:** gwałtowny wzrost `prometheus_tsdb_head_series`, rosnące zużycie RAM, spowolnienie zapytań i ewaluacji reguł, w skrajnym przypadku OOM-kill procesu.

**Typowe przyczyny:** etykiety o nieograniczonej liczbie wartości (`user_id`, `request_id`, pełny URL zamiast wzorca route), krótko żyjące zasoby w Kubernetes generujące nowe serie przy każdym restarcie poda (np. etykieta `pod` bez agregacji), błędnie zainstrumentowana aplikacja.

**Rozwiązania:**

- Identyfikacja winowajcy przez TSDB Status lub `promtool tsdb analyze`.
- Usunięcie lub przepisanie etykiety na etapie `metric_relabel_configs` (`action: labeldrop` / `action: drop`).
- Zmiana instrumentacji aplikacji tak, aby etykiety miały ograniczony, skończony zbiór wartości (np. route jako wzorzec `/users/:id`, nie pełny URL).
- W ostateczności: `promtool tsdb delete-series` (wymaga `--web.enable-admin-api`) do ręcznego usunięcia problematycznych serii z danych historycznych.

### Zbyt częsty `scrape_interval`

**Objawy:** wysokie zużycie CPU i I/O, duża liczba próbek (`scrape_samples_scraped`) bez proporcjonalnej wartości analitycznej.

**Rozwiązania:**

- Rewizja rzeczywistej potrzeby granularności — dla większości metryk infrastrukturalnych 30-60s jest wystarczające, 15s czy 5s uzasadnione tylko dla wąskiej klasy przypadków (SLO o wysokiej precyzji, debugging).
- Różnicowanie `scrape_interval` per `job_name` zamiast jednej globalnej wartości dla wszystkich targetów.
- Recording rules do wstępnej agregacji częstych metryk, jeśli dalsze zapytania i tak operują na dłuższych oknach czasowych.

### Zbyt długa retencja na dysku lokalnym

**Objawy:** rosnące zużycie przestrzeni dyskowej, wydłużający się czas kompakcji, wolniejsze zapytania obejmujące długi zakres czasu.

**Rozwiązania:**

- Ograniczenie `--storage.tsdb.retention.time` (np. 15-30 dni) i/lub `--storage.tsdb.retention.size` jako twardego limitu pojemności.
- Przeniesienie długoterminowej retencji do zewnętrznego systemu (Thanos, Mimir/Cortex) przez `remote_write`, zamiast trzymania wielomiesięcznych danych lokalnie.
- Weryfikacja, czy dysk pod danymi TSDB to szybki nośnik (SSD/NVMe) — na wolnych dyskach sieciowych (np. część rozwiązań NFS) kompakcja i WAL mogą stać się wąskim gardłem niezależnie od rozmiaru retencji.

## Kto pilnuje pilnującego — monitorowanie samego Prometheusa

Instancja Prometheusa nie powinna być jedynym punktem obserwacji własnego stanu — jeśli padnie, nikt nie zauważy alertu o jej awarii. Praktyczne wzorce:

- **Druga, niezależna instancja Prometheusa** (lub para instancji HA w tym samym środowisku) scrape'ująca `job="prometheus"` z pierwszej instancji i odwrotnie — wzajemna obserwacja.
- **Blackbox Exporter** sprawdzający z zewnątrz dostępność endpointu `/-/healthy` i `/-/ready`.
- **Alertmanager z niezależnym kanałem powiadomień** (np. heartbeat/dead man's switch — reguła, która zawsze powinna być aktywna, a jej brak w systemie zewnętrznym typu healthchecks.io sygnalizuje, że cały pipeline alertingu przestał działać).
- W środowisku Kubernetes: reguły `PrometheusDown` oparte o dane z zewnętrznego, niezależnego systemu monitoringu (np. innego klastra) lub prostego zewnętrznego probe'a HTTP.

Zasada nadrzędna: system monitoringu krytyczny dla produkcji wymaga własnej obserwowalności poza samym sobą — w przeciwnym razie awaria Prometheusa staje się niewidoczną awarią całego systemu wykrywania awarii.
