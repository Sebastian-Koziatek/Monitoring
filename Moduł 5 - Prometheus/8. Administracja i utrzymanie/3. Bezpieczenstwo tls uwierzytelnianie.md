Domyślna instalacja Prometheusa nie wymusza żadnego szyfrowania ani uwierzytelniania — Web UI, API oraz endpoint `/metrics` są dostępne po zwykłym HTTP dla każdego, kto ma dostęp sieciowy do portu 9090. W środowisku produkcyjnym jest to nieakceptowalne, ponieważ API Prometheusa daje dostęp nie tylko do odczytu metryk, ale (przy włączonych flagach administracyjnych) także do operacji takich jak usuwanie serii czy tworzenie snapshotów. Zabezpieczenie Prometheusa obejmuje warstwę transportową (TLS), warstwę uwierzytelniania (basic auth) oraz warstwę sieciową (firewall, reverse proxy).

## Konfiguracja TLS dla Web UI i API

Od wersji 2.24 Prometheus obsługuje natywne TLS oraz uwierzytelnianie poprzez oddzielny plik `web-config.yml`, wskazywany flagą startową:

```bash
prometheus \
  --config.file=/etc/prometheus/prometheus.yml \
  --web.config.file=/etc/prometheus/web-config.yml
```

Minimalna konfiguracja TLS w `web-config.yml`:

```yaml
tls_server_config:
  cert_file: /etc/prometheus/tls/prometheus.crt
  key_file: /etc/prometheus/tls/prometheus.key
  # opcjonalnie: wymuszenie mTLS (weryfikacja certyfikatu klienta)
  client_auth_type: "RequireAndVerifyClientCert"
  client_ca_file: /etc/prometheus/tls/ca.crt
  min_version: TLS12
```

Kluczowe parametry `tls_server_config`:

| Parametr | Znaczenie |
|---|---|
| `cert_file` / `key_file` | Certyfikat serwera i klucz prywatny (PEM). |
| `client_auth_type` | `NoClientCert` (domyślne), `RequestClientCert`, `RequireAndVerifyClientCert` — ten ostatni wymusza mTLS. |
| `client_ca_file` | Urząd certyfikacji do weryfikacji certyfikatów klienckich (przy mTLS). |
| `min_version` / `max_version` | Ograniczenie dopuszczalnych wersji protokołu (zalecane `TLS12` jako minimum). |
| `cipher_suites` | Opcjonalna lista dozwolonych zestawów szyfrów — istotne przy audytach bezpieczeństwa. |

Po uruchomieniu z TLS Web UI i API są dostępne wyłącznie po HTTPS (`https://host:9090`), a próba połączenia HTTP zostanie odrzucona. Certyfikaty warto rotować automatycznie (np. cert-manager w Kubernetes, certbot na hostach), a plik `web-config.yml` — podobnie jak `prometheus.yml` — obsługuje `SIGHUP`/`/-/reload`, więc rotacja certyfikatu nie wymaga restartu procesu.

## Basic auth

Uwierzytelnianie basic auth konfiguruje się w tym samym pliku `web-config.yml`, w sekcji `basic_auth_users`. Hasła **nie są przechowywane w postaci jawnej** — plik zawiera skróty bcrypt:

```yaml
basic_auth_users:
  admin: $2y$10$92j8XwqzM9ZkY6nQeF7c9uV1r3ZlH8qk5t7wQd0mB2xL4pR6sT8yO
  readonly_ci: $2y$10$Kq1lR9vD3xN8bZ2wH5tE6uYj7oP4mA1sC0dF9gL3nQ8rV5xT2wB6
```

Hash bcrypt generuje się poleceniem `htpasswd` (pakiet `apache2-utils`/`httpd-tools`) lub narzędziem `promtool`, jeśli dana wersja je udostępnia:

```bash
htpasswd -nBC 10 admin
# Interaktywnie poprosi o hasło i wypisze linię "admin:$2y$10$..."
```

Po skonfigurowaniu `basic_auth_users` każde żądanie do Web UI i API musi zawierać nagłówek `Authorization: Basic`, w tym żądania scrape'ów pochodzących od `federate` czy zapytania z Grafany — te źródła trzeba odpowiednio skonfigurować (`basic_auth:` w `datasource` Grafany, `basic_auth:` w `scrape_configs` instancji federującej).

### Best practices — basic auth

- Osobne konta dla ludzi (dostęp administracyjny) i dla systemów (Grafana, Alertmanager, skrypty CI) — ułatwia rotację i audyt.
- Rotacja haseł okresowo i natychmiast po odejściu pracownika mającego dostęp administracyjny.
- Basic auth **zawsze w połączeniu z TLS** — bez szyfrowania transportu poświadczenia (nawet zahashowane w pliku konfiguracyjnym) są przesyłane praktycznie jawnym tekstem (Base64) w każdym żądaniu HTTP.
- Rozważenie reverse proxy z OAuth2/OIDC (np. `oauth2-proxy` przed Prometheusem) w środowiskach z centralnym systemem tożsamości (SSO) — basic auth nie integruje się z SSO ani nie obsługuje MFA.

## Zabezpieczenie endpointów scrape (strona exporterów)

Ta sama mechanika `web-config.yml` (TLS + `basic_auth_users`) jest dostępna dla **exporterów** korzystających z biblioteki `exporter-toolkit` (Node Exporter, Blackbox Exporter i inne oficjalne exportery od wersji obsługującej `--web.config.file`). Oznacza to, że sam endpoint `/metrics` exportera może być zaszyfrowany i wymagać uwierzytelnienia — istotne, gdy exporter działa na hoście dostępnym z mniej zaufanej sieci.

Konfiguracja po stronie Prometheusa scrape'ującego taki endpoint:

```yaml
scrape_configs:
  - job_name: 'node'
    scheme: https
    tls_config:
      ca_file: /etc/prometheus/tls/ca.crt
      server_name: node-exporter.internal
      insecure_skip_verify: false
    basic_auth:
      username: prometheus
      password_file: /etc/prometheus/secrets/node_exporter_password
    static_configs:
      - targets: ['node-exporter.internal:9100']
```

Uwaga praktyczna: `insecure_skip_verify: true` wyłącza weryfikację certyfikatu serwera i **nie powinno być używane w produkcji** — jest akceptowalne wyłącznie tymczasowo w środowisku testowym. `password_file` (zamiast `password` wpisanego wprost) pozwala trzymać hasło poza plikiem konfiguracyjnym trafiającym do repozytorium Git.

## Ograniczanie dostępu sieciowego

TLS i basic auth to warstwa aplikacyjna — powinny być uzupełnione o segmentację sieciową:

- **Firewall** (iptables/nftables/firewalld, security groups w chmurze) ograniczający dostęp do portu 9090 (Prometheus), 9093 (Alertmanager) i portów exporterów wyłącznie do adresów, które faktycznie muszą się łączyć (sama instancja Prometheusa dla exporterów, Grafana i administratorzy dla Web UI Prometheusa).
- **Reverse proxy** (nginx, Traefik, NPM) jako jedyny publicznie eksponowany punkt wejścia — terminuje TLS, może dodatkowo egzekwować uwierzytelnianie (np. OIDC), rate limiting i logowanie dostępu, a ruch do samego Prometheusa kierować już tylko z sieci wewnętrznej.
- W Kubernetes: `NetworkPolicy` ograniczające, które namespace/pody mogą łączyć się z portem Prometheusa i Alertmanagera, oraz unikanie wystawiania ich przez `Service` typu `LoadBalancer` bezpośrednio do internetu.

## Alertmanager i Pushgateway — uwagi bezpieczeństwa

- **Alertmanager** obsługuje ten sam mechanizm `web-config.yml` (TLS + basic auth) co Prometheus i powinien być zabezpieczony analogicznie — jego API pozwala m.in. na wyciszanie alertów (`silences`), co w rękach nieuprawnionej osoby może ukryć realny incydent. Adresy webhooków integracji (Slack, PagerDuty, Opsgenie) zawierają sekrety i muszą być trzymane poza jawną konfiguracją (zmienne środowiskowe, `*_file`).
- **Pushgateway** wymaga szczególnej ostrożności: metryki wypchnięte do niego pozostają widoczne i scrape'owane w nieskończoność, dopóki nie zostaną jawnie usunięte (`DELETE /metrics/job/...`) — jest to zarówno pułapka operacyjna (stare, nieaktualne metryki „na zawsze”), jak i wektor ataku, jeśli endpoint push jest dostępny bez uwierzytelnienia: dowolny klient z dostępem sieciowym może nadpisać lub zaśmiecić metryki. Pushgateway powinien być wystawiony wyłącznie do zaufanej sieci wewnętrznej, najlepiej dodatkowo zabezpieczony `basic_auth_users` i TLS analogicznie jak Prometheus.

### Checklist bezpieczeństwa

- TLS włączony na Prometheusie, Alertmanagerze i tam, gdzie to możliwe, na exporterach.
- Basic auth (lub reverse proxy z OIDC) na wszystkich publicznie osiągalnych endpointach.
- Hasła wyłącznie jako hashe bcrypt w `web-config.yml`, sekrety poza repozytorium Git.
- Firewall/`NetworkPolicy` ograniczające dostęp do portów 9090/9093/9091 (Pushgateway) do niezbędnego minimum.
- `--web.enable-admin-api` i `--web.enable-lifecycle` włączone tylko tam, gdzie faktycznie potrzebne, i chronione tak samo jak reszta API.
- Pushgateway czyszczony z nieaktualnych metryk i niedostępny z niezaufanych sieci.
