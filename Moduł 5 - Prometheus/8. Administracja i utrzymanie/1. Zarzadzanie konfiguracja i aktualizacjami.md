Prometheus w środowisku produkcyjnym rzadko istnieje jako pojedyncza, ręcznie utrzymywana instancja. W praktyce administracyjnej konfigurację traktuje się jak kod (Configuration as Code), a proces jej zmiany i przeładowania musi odbywać się bez przerywania zbierania metryk i bez luk w danych wykorzystywanych przez reguły alertujące.

## Konfiguracja jako kod (IaC)

Plik `prometheus.yml`, reguły alertujące i reguły rekordujące powinny być wersjonowane w repozytorium Git, a nie edytowane ręcznie na serwerze. Takie podejście daje pełną historię zmian, możliwość code review przed wdrożeniem oraz łatwy rollback do poprzedniej wersji.

**Ansible** jest naturalnym wyborem do zarządzania konfiguracją Prometheusa na hostach — dostarcza plik `prometheus.yml` z szablonu Jinja2, zarządza plikami reguł w katalogu `rules.d/`, pilnuje wersji binarki i uruchamia reload po zmianie. Przykładowy fragment roli:

```yaml
- name: Wdróż konfigurację Prometheusa z szablonu
  template:
    src: prometheus.yml.j2
    dest: /etc/prometheus/prometheus.yml
    owner: prometheus
    group: prometheus
    mode: "0640"
    validate: "promtool check config %s"
  notify: reload prometheus

handlers:
  - name: reload prometheus
    uri:
      url: http://localhost:9090/-/reload
      method: POST
      status_code: 200
```

Kluczowy jest tu parametr `validate` — Ansible odrzuci wdrożenie, jeśli wygenerowany plik nie przejdzie walidacji `promtool check config`, zanim jeszcze trafi on na docelowy serwer.

**Terraform** sprawdza się głównie do prowizjonowania infrastruktury, na której Prometheus działa (instancje, dyski na dane TSDB, reguły firewalla, load balancery przed Alertmanagerem), oraz — w środowiskach Kubernetes — do zarządzania zasobami takimi jak `Namespace`, `PersistentVolumeClaim` czy zasobami Prometheus Operatora (`ServiceMonitor`, `PrometheusRule`) poprzez provider `kubernetes` lub `helm`.

**GitOps** to logiczne rozszerzenie powyższego: w klastrach Kubernetes narzędzia takie jak Argo CD lub Flux synchronizują stan zasobów `ServiceMonitor`, `PodMonitor` i `PrometheusRule` z repozytorium Git. Zmiana konfiguracji polega na utworzeniu pull requesta — po jego zaakceptowaniu kontroler GitOps automatycznie doprowadza klaster do zgodności ze stanem opisanym w repozytorium, a Prometheus Operator przelicza z tych zasobów finalny `prometheus.yml`.

### Checklist: konfiguracja jako kod

- Repozytorium Git jako jedyne źródło prawdy dla `prometheus.yml` i reguł.
- Walidacja składniowa (`promtool check config`, `promtool check rules`) jako krok w pipeline CI przed merge.
- Code review zmian reguł alertujących — literówka w wyrażeniu PromQL potrafi wyciszyć alert na miesiące.
- Oddzielne środowiska (dev/staging/prod) z niezależnymi plikami konfiguracyjnymi lub szablonami.
- Sekrety (np. hasła do `basic_auth` w `scrape_configs`) trzymane poza repozytorium — w Vault, SOPS lub Ansible Vault.

## Bezprzestojowe przeładowanie konfiguracji

Prometheus obsługuje przeładowanie konfiguracji „na żywo”, bez restartu procesu — kluczowe, ponieważ restart oznacza utratę danych z bufora WAL jeszcze niezapisanych na dysk oraz przerwę w scrape'owaniu.

**Sygnał SIGHUP** jest domyślnie dostępny i nie wymaga dodatkowej flagi startowej:

```bash
kill -HUP $(pgrep prometheus)
# lub w systemd:
systemctl reload prometheus
```

Jednostka systemd powinna definiować `ExecReload`, aby `systemctl reload` działał poprawnie:

```ini
[Service]
ExecStart=/usr/local/bin/prometheus \
  --config.file=/etc/prometheus/prometheus.yml \
  --storage.tsdb.path=/var/lib/prometheus/data \
  --storage.tsdb.retention.time=30d \
  --web.enable-lifecycle
ExecReload=/bin/kill -HUP $MAINPID
Restart=on-failure
```

**Endpoint `/-/reload`** wymaga jawnego uruchomienia Prometheusa z flagą `--web.enable-lifecycle` (domyślnie te endpointy są wyłączone ze względów bezpieczeństwa) i jest wygodniejszy w automatyzacji, ponieważ nie wymaga dostępu SSH do hosta:

```bash
curl -X POST http://localhost:9090/-/reload
```

W obu przypadkach Prometheus:

1. Wczytuje nowy plik `prometheus.yml` oraz pliki reguł wskazane przez `rule_files`.
2. Waliduje składnię — jeśli konfiguracja jest niepoprawna, **stara konfiguracja pozostaje aktywna**, a błąd trafia do logów procesu i jest widoczny w metryce `prometheus_config_last_reload_successful`.
3. Dopiero po pozytywnej walidacji podmienia aktywną konfigurację i przelicza harmonogramy scrape'ów.

Warto monitorować `prometheus_config_last_reload_successful` jako regułę alertującą — nieudany reload w środowisku zautomatyzowanym łatwo przeoczyć, jeśli proces CI/CD nie sprawdza kodu odpowiedzi z `/-/reload`.

## Aktualizacja wersji Prometheusa

Prometheus stosuje wersjonowanie semantyczne, a projekt deklaruje kompatybilność wsteczną w obrębie głównej wersji (2.x). Mimo to każdą aktualizację należy poprzedzić przeglądem **release notes** i pliku `CHANGELOG.md` w repozytorium `prometheus/prometheus`, zwracając szczególną uwagę na sekcje:

- **Breaking changes** — np. zmiany domyślnych wartości flag, usunięcie przestarzałych endpointów API.
- **Deprecated** — funkcje oznaczone do usunięcia w przyszłych wersjach (np. stare formaty `remote_write`).
- **Zmiany formatu bloków TSDB** — nowsza wersja Prometheusa zwykle potrafi odczytać starsze bloki danych, ale downgrade do starszej wersji binarki po aktualizacji formatu TSDB **nie jest gwarantowany** i może uniemożliwić odczyt danych.

### Proces aktualizacji na hoście (bare metal / VM)

1. Sprawdzić bieżącą wersję: `prometheus --version`.
2. Pobrać nową wersję binarki, zweryfikować sumę kontrolną (checksum z release GitHub).
3. Wykonać `promtool check config` nową binarką na aktualnym pliku konfiguracyjnym — parser bywa bardziej rygorystyczny w nowszych wersjach.
4. Zatrzymać usługę, podmienić binarkę, uruchomić ponownie (`systemctl restart prometheus`).
5. Zweryfikować metryki `prometheus_build_info`, brak błędów w logach oraz stan `up` dla wszystkich targetów.

### Aktualizacja w Kubernetes przez Helm

W klastrach Kubernetes standardem jest chart `kube-prometheus-stack` (lub samodzielny chart `prometheus`). Aktualizacja przebiega jako:

```bash
helm repo update
helm search repo prometheus-community/kube-prometheus-stack --versions | head
helm diff upgrade prometheus prometheus-community/kube-prometheus-stack \
  -n monitoring -f values.yaml
helm upgrade prometheus prometheus-community/kube-prometheus-stack \
  -n monitoring -f values.yaml --version 65.x.x
```

Wtyczka `helm-diff` pozwala zobaczyć dokładnie, co się zmieni (obrazy kontenerów, CRD, StatefulSet) przed wykonaniem `upgrade`. Warto pamiętać, że aktualizacja chartu często wiąże się z aktualizacją CRD (`PrometheusRule`, `ServiceMonitor`) — Helm domyślnie **nie aktualizuje CRD** przy `upgrade`, trzeba je zaktualizować ręcznie (`kubectl apply -f crds/`) zgodnie z instrukcją danego release'u.

## Strategie rollback

- **Rollback konfiguracji**: ponieważ konfiguracja jest w Git, rollback to `git revert` + ponowne wdrożenie + `/-/reload`. Nie wymaga restartu procesu.
- **Rollback binarki Prometheusa**: podmiana na poprzednią wersję i restart usługi. Bezpieczne w obrębie tej samej wersji formatu TSDB (zwykle kilka kolejnych wersji minor). Przy wątpliwościach co do formatu danych, bezpieczniejszą opcją jest przywrócenie snapshotu TSDB sprzed aktualizacji.
- **Rollback w Helm**: `helm rollback prometheus <REVISION> -n monitoring` przywraca poprzednią wersję manifestów; historia rewizji dostępna przez `helm history prometheus -n monitoring`.
- **Snapshot TSDB przed dużą aktualizacją**: endpoint `/api/v1/admin/tsdb/snapshot` (wymaga `--web.enable-admin-api`) tworzy spójny snapshot danych w katalogu `snapshots/`, który można zabezpieczyć przed ryzykowną operacją.

Rekomendowana kolejność wdrażania aktualizacji w środowisku produkcyjnym: **staging → jedna instancja produkcyjna (canary) → pozostałe instancje**, z obserwacją metryk `prometheus_tsdb_*`, `prometheus_rule_evaluation_failures_total` oraz `up` przez co najmniej jeden pełny cykl scrape'u i ewaluacji reguł przed rozszerzeniem na cały klaster.
