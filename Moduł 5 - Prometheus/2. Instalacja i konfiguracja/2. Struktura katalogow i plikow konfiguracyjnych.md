Niezależnie od wybranej metody instalacji (binarka, pakiet, Docker, Helm), Prometheus opiera się na tym samym modelu rozmieszczenia plików: oddzielny katalog na binaria, oddzielny na konfigurację i oddzielny na dane silnika TSDB (Time Series Database). Zrozumienie tego układu jest kluczowe przy planowaniu backupów, uprawnień i strategii retencji.

## Typowy układ katalogów (instalacja binarkowa/pakietowa na Linuksie)

```
/usr/local/bin/prometheus          # binarka główna
/usr/local/bin/promtool            # narzędzie CLI: walidacja config, debugowanie TSDB, testy reguł

/etc/prometheus/
├── prometheus.yml                 # główny plik konfiguracyjny
├── rules/                         # katalog z regułami alertowania i rekordowania
│   ├── alerting-rules.yml
│   └── recording-rules.yml
├── file_sd/                       # (opcjonalnie) pliki file-based service discovery
│   └── targets.json
├── consoles/                      # szablony konsol WWW (starszy mechanizm, legacy)
└── console_libraries/             # biblioteki do szablonów konsol

/var/lib/prometheus/               # katalog danych TSDB (--storage.tsdb.path)
├── 01HXYZ.../                     # bloki danych (block), nazwane ULID-em
│   ├── chunks/                    # skompresowane próbki (chunk files)
│   ├── index                      # indeks odwrócony (label → series)
│   ├── meta.json                  # metadane bloku (zakres czasu, poziom kompakcji)
│   └── tombstones                 # znaczniki usuniętych serii (po delete API)
├── wal/                           # Write-Ahead Log — bufor przed zapisem do bloku
│   ├── 00000000
│   └── checkpoint.00000001/
└── lock                           # plik blokady procesu (jedna instancja na katalog danych)
```

W instalacji kontenerowej (Docker/Kubernetes) te same ścieżki istnieją wewnątrz kontenera, montowane jako wolumeny — typowo `/etc/prometheus` (config, tylko do odczytu) i `/prometheus` (dane, wolumen trwały).

## Znaczenie poszczególnych elementów

- **`prometheus.yml`** — jedyny plik odczytywany bezpośrednio przy starcie (`--config.file`); wszystko inne (reguły, service discovery) jest z niego dołączane przez `rule_files` i konfigurację `scrape_configs`.
- **Katalog `rules/`** — konwencja, nie wymóg — Prometheus nie narzuca nazwy ani lokalizacji, liczy się wzorzec glob wskazany w `rule_files` w `prometheus.yml` (np. `rules/*.yml`).
- **`wal/` (Write-Ahead Log)** — każda przyjęta próbka trafia najpierw tutaj, zanim zostanie skompaktowana do bloku na dysku; chroni przed utratą danych przy awaryjnym restarcie. WAL jest odtwarzany przy starcie procesu — duży WAL wydłuża czas uruchomienia.
- **Bloki danych (`01H.../`)** — domyślnie obejmują 2h danych "surowych", później są kompaktowane w większe bloki (do maks. ok. 10% okresu retencji) przez proces kompakcji działający w tle.
- **`lock`** — zapobiega jednoczesnemu uruchomieniu dwóch procesów Prometheusa na tym samym katalogu danych (uszkodziłoby to TSDB).

## Użytkownik systemowy i prawa dostępu

Prometheus **nie powinien** działać jako `root`. Standardowa praktyka to dedykowany użytkownik systemowy bez powłoki logowania:

```bash
sudo useradd --no-create-home --shell /usr/sbin/nologin prometheus
sudo chown -R prometheus:prometheus /etc/prometheus /var/lib/prometheus
sudo chmod -R 750 /etc/prometheus /var/lib/prometheus
```

| Ścieżka | Właściciel | Uprawnienia | Uzasadnienie |
|---|---|---|---|
| `/usr/local/bin/prometheus` | `root:root` | `755` | binarka wykonywalna, nie musi być zapisywalna przez usera roboczego |
| `/etc/prometheus/` | `prometheus:prometheus` | `750` | proces musi czytać config; brak dostępu dla innych userów |
| `/etc/prometheus/prometheus.yml` | `prometheus:prometheus` | `640` | może zawierać dane wrażliwe (np. `bearer_token`, dane TLS) |
| `/var/lib/prometheus/` | `prometheus:prometheus` | `750` | proces musi mieć pełny R/W do danych TSDB |

W jednostce systemd warto dodatkowo ograniczyć proces dyrektywami hardeningowymi (`NoNewPrivileges=true`, `ProtectSystem=strict`, `ReadWritePaths=/var/lib/prometheus`) — patrz przykładowy unit file w module o instalacji.

## Flagi uruchomieniowe Prometheusa

Prometheus konfiguruje się w dwóch warstwach: przez plik `prometheus.yml` (co i jak scrapować, reguły, alerting) oraz przez **flagi startowe procesu** (jak działa sam silnik — ścieżki, retencja, limity, API). Flagi podaje się przy starcie procesu (w `ExecStart` unit filu, `command:` w compose, lub `args:` w manifeście Kubernetes).

| Flaga | Domyślna wartość | Opis |
|---|---|---|
| `--config.file` | `prometheus.yml` | ścieżka do głównego pliku konfiguracyjnego |
| `--storage.tsdb.path` | `data/` | katalog danych TSDB |
| `--storage.tsdb.retention.time` | `15d` | jak długo przechowywać dane (np. `30d`, `1y`) |
| `--storage.tsdb.retention.size` | brak | limit rozmiaru danych na dysku (np. `50GB`) — nadpisuje retencję czasową po osiągnięciu limitu |
| `--web.listen-address` | `0.0.0.0:9090` | adres i port nasłuchu API/UI |
| `--web.enable-lifecycle` | wyłączone | włącza endpointy `/-/reload` i `/-/quit` w API HTTP |
| `--web.enable-admin-api` | wyłączone | włącza administracyjne API (snapshoty, usuwanie serii) |
| `--web.external-url` | — | URL, pod jakim Prometheus jest widoczny zza reverse proxy |
| `--query.max-concurrency` | `20` | maksymalna liczba równoległych zapytań PromQL |
| `--query.timeout` | `2m` | maksymalny czas wykonania pojedynczego zapytania |
| `--log.level` | `info` | poziom logowania (`debug`, `info`, `warn`, `error`) |

### Przykład kompletnego wywołania

```bash
prometheus \
  --config.file=/etc/prometheus/prometheus.yml \
  --storage.tsdb.path=/var/lib/prometheus \
  --storage.tsdb.retention.time=30d \
  --storage.tsdb.retention.size=100GB \
  --web.listen-address=0.0.0.0:9090 \
  --web.enable-lifecycle \
  --log.level=info
```

## Checklist wdrożeniowa

- [ ] Konfiguracja i dane rozdzielone na osobne katalogi (`/etc/prometheus` vs `/var/lib/prometheus`).
- [ ] Dedykowany użytkownik systemowy `prometheus`, bez powłoki logowania i bez uprawnień `sudo`.
- [ ] Uprawnienia do plików konfiguracyjnych zawężone (`640`/`750`), szczególnie gdy zawierają tokeny/hasła.
- [ ] Retencja (`--storage.tsdb.retention.time` i/lub `.size`) dobrana do dostępnej przestrzeni dyskowej.
- [ ] `--web.enable-lifecycle` włączone świadomie, tylko gdy endpoint `/-/reload` jest odpowiednio zabezpieczony na poziomie sieci/proxy.
- [ ] Katalog `wal/` monitorowany pod kątem rozmiaru — nienaturalny wzrost sygnalizuje problem z zapisem do bloków.
