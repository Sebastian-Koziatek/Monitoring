# Opcje instalacji: binaria, pakiety, Docker, Kubernetes Helm Chart

Prometheus można uruchomić na kilka sposobów, zależnie od środowiska docelowego, modelu zarządzania infrastrukturą i wymagań operacyjnych zespołu. Wybór metody instalacji wpływa na sposób aktualizacji, integrację z systemem operacyjnym oraz łatwość automatyzacji. Poniżej omówiono cztery podstawowe podejścia: binarkę uruchamianą jako usługa systemd, pakiety dystrybucyjne, kontener Docker oraz wdrożenie w Kubernetesie za pomocą Helm charta.

## 1. Binarka ze strony prometheus.io + systemd

Projekt Prometheus publikuje statycznie linkowane binaria dla Linuksa, macOS, Windows oraz FreeBSD na stronie [prometheus.io/download](https://prometheus.io/download/). To najbardziej "surowa" metoda instalacji — brak zależności od menedżera pakietów, pełna kontrola nad wersją i lokalizacją plików.

### Kroki instalacji

```bash
# Utworzenie dedykowanego użytkownika systemowego (bez powłoki logowania)
sudo useradd --no-create-home --shell /usr/sbin/nologin prometheus

# Katalogi na dane i konfigurację
sudo mkdir -p /etc/prometheus /var/lib/prometheus

# Pobranie i rozpakowanie binarki (wersja przykładowa)
cd /tmp
wget https://github.com/prometheus/prometheus/releases/download/v2.53.0/prometheus-2.53.0.linux-amd64.tar.gz
tar xvf prometheus-2.53.0.linux-amd64.tar.gz
cd prometheus-2.53.0.linux-amd64

# Kopiowanie binariów
sudo cp prometheus promtool /usr/local/bin/
sudo cp -r consoles console_libraries /etc/prometheus/
sudo cp prometheus.yml /etc/prometheus/prometheus.yml

# Nadanie właściciela
sudo chown -R prometheus:prometheus /etc/prometheus /var/lib/prometheus
sudo chown prometheus:prometheus /usr/local/bin/prometheus /usr/local/bin/promtool
```

### Jednostka systemd

```ini
# /etc/systemd/system/prometheus.service
[Unit]
Description=Prometheus Monitoring System
Documentation=https://prometheus.io/docs/
Wants=network-online.target
After=network-online.target

[Service]
Type=simple
User=prometheus
Group=prometheus
ExecStart=/usr/local/bin/prometheus \
    --config.file=/etc/prometheus/prometheus.yml \
    --storage.tsdb.path=/var/lib/prometheus \
    --web.console.templates=/etc/prometheus/consoles \
    --web.console.libraries=/etc/prometheus/console_libraries \
    --web.listen-address=0.0.0.0:9090 \
    --storage.tsdb.retention.time=15d
ExecReload=/bin/kill -HUP $MAINPID
Restart=on-failure
RestartSec=5s
NoNewPrivileges=true
ProtectSystem=strict
ReadWritePaths=/var/lib/prometheus

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now prometheus
sudo systemctl status prometheus
```

**Zalety:** pełna kontrola nad wersją, minimalna liczba zależności, łatwe wpięcie w istniejące procesy hardeningu systemd (sandboxing, `ProtectSystem`, `NoNewPrivileges`).
**Wady:** aktualizacje i rollback trzeba zarządzać ręcznie lub przez własną automatyzację (Ansible, skrypty).

## 2. Instalacja z repozytoriów pakietów (apt/dnf)

Wiele dystrybucji Linuksa udostępnia Prometheusa w oficjalnych repozytoriach, choć wersje bywają tam znacząco starsze niż upstream. W środowiskach korporacyjnych z polityką pakietów RPM/DEB to jednak wygodne rozwiązanie, bo integruje się z istniejącym systemem zarządzania aktualizacjami.

```bash
# Debian/Ubuntu — pakiet z repozytorium dystrybucji
sudo apt update
sudo apt install prometheus prometheus-node-exporter

# RHEL/Fedora — z repozytorium EPEL
sudo dnf install epel-release
sudo dnf install golang-github-prometheus prometheus2
```

Pakiety te zwykle instalują od razu jednostkę systemd, plik konfiguracyjny w `/etc/prometheus/prometheus.yml` oraz dedykowanego użytkownika systemowego — analogicznie do instalacji ręcznej opisanej wyżej, ale bez potrzeby samodzielnego tworzenia unit file'a.

**Zalety:** integracja z systemowym menedżerem pakietów, automatyczne aktualizacje bezpieczeństwa przez `apt upgrade`/`dnf upgrade`, spójność z polityką patchowania serwerowni.
**Wady:** opóźnienie względem najnowszych wydań upstream (czasem kilka wersji minor), różnice w domyślnych ścieżkach między dystrybucjami — wymaga weryfikacji dokumentacji pakietu.

## 3. Uruchomienie w Dockerze

Oficjalny obraz `prom/prometheus` na Docker Hub to szybki sposób na uruchomienie instancji testowej lub produkcyjnej bez ingerencji w system hosta.

### docker run

```bash
docker run -d \
  --name prometheus \
  -p 9090:9090 \
  -v /path/na/hoscie/prometheus.yml:/etc/prometheus/prometheus.yml:ro \
  -v prometheus_data:/prometheus \
  prom/prometheus:v2.53.0 \
  --config.file=/etc/prometheus/prometheus.yml \
  --storage.tsdb.retention.time=15d
```

### docker-compose.yml

```yaml
version: "3.8"

services:
  prometheus:
    image: prom/prometheus:v2.53.0
    container_name: prometheus
    restart: unless-stopped
    ports:
      - "9090:9090"
    volumes:
      - ./prometheus.yml:/etc/prometheus/prometheus.yml:ro
      - prometheus_data:/prometheus
    command:
      - "--config.file=/etc/prometheus/prometheus.yml"
      - "--storage.tsdb.path=/prometheus"
      - "--storage.tsdb.retention.time=15d"
      - "--web.enable-lifecycle"

volumes:
  prometheus_data:
```

**Zalety:** izolacja od systemu hosta, powtarzalność środowiska (ten sam obraz na dev/stage/prod), łatwe wersjonowanie przez tag obrazu, szybkie wdrożenie obok innych kontenerów (Grafana, Alertmanager) w tym samym compose.
**Wady:** wymaga dodatkowej warstwy zarządzania (orkiestracja wolumenów, sieci Docker), narzut na obserwowalność samego środowiska kontenerowego, konieczność świadomego zarządzania trwałością danych TSDB (wolumeny).

## 4. Kubernetes — Helm chart (kube-prometheus-stack)

W środowiskach Kubernetes standardem de facto jest chart `kube-prometheus-stack` (Prometheus Community Helm Charts), który instaluje razem Prometheusa, Alertmanagera, Grafanę, node-exporter, kube-state-metrics oraz Prometheus Operator zarządzający cyklem życia przez CRD (`ServiceMonitor`, `PodMonitor`, `PrometheusRule`).

```bash
# Dodanie repozytorium i instalacja
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm repo update

helm install kube-prom prometheus-community/kube-prometheus-stack \
  --namespace monitoring --create-namespace \
  --set prometheus.prometheusSpec.retention=15d \
  --set prometheus.prometheusSpec.storageSpec.volumeClaimTemplate.spec.resources.requests.storage=50Gi
```

Konfigurację nadpisuje się przez plik `values.yaml` przekazywany flagą `-f values.yaml`, co pozwala trzymać ustawienia w repozytorium GitOps (ArgoCD/Flux).

**Zalety:** deklaratywne zarządzanie przez CRD, automatyczne wykrywanie targetów przez `ServiceMonitor`/`PodMonitor`, gotowa integracja z Grafaną i regułami alertowymi, naturalne dopasowanie do modelu operacyjnego Kubernetesa (rolling upgrade, self-healing przez Operatora).
**Wady:** wyższy próg wejścia (trzeba rozumieć CRD Prometheus Operatora), więcej ruchomych części niż samodzielny Prometheus, chart bywa "ciężki" domyślnie (instaluje komponenty, których część zespołów nie potrzebuje) — wymaga świadomego przycięcia przez `values.yaml`.

## Który wariant wybrać?

| Scenariusz | Rekomendowana metoda |
|---|---|
| Pojedynczy serwer bare-metal/VM, pełna kontrola nad wersją | Binarka + systemd |
| Środowisko korporacyjne z polityką pakietów i patchowania OS | Pakiet apt/dnf |
| Szybki PoC, laptop developera, stack testowy | Docker / docker-compose |
| Produkcja w Kubernetesie, wiele klastrów, GitOps | Helm chart (kube-prometheus-stack) |

W praktyce komercyjnej najczęściej spotyka się dwa bieguny: binarkę + systemd na klasycznej infrastrukturze VM oraz kube-prometheus-stack w środowiskach kontenerowych — obie metody dają pełną kontrolę nad wersją Prometheusa, w przeciwieństwie do pakietów dystrybucyjnych, które są wygodne, ale rzadko aktualne.
