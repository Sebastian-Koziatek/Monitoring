Plik `prometheus.yml` to jedyny plik konfiguracyjny, który Prometheus wczytuje bezpośrednio przy starcie (wskazany flagą `--config.file`). Ma format YAML i składa się z kilku głównych sekcji: `global`, `scrape_configs`, `rule_files` oraz `alerting`. Zrozumienie ich wzajemnych relacji jest podstawą do dalszej pracy z targetami, regułami i alertowaniem.

## Sekcja `global`

Definiuje ustawienia domyślne, które mają zastosowanie do całej instancji Prometheusa, chyba że zostaną nadpisane na poziomie konkretnego joba w `scrape_configs`.

```yaml
global:
  scrape_interval: 15s        # domyślny interwał scrapowania metryk
  evaluation_interval: 15s    # jak często silnik reguł ewaluuje reguły alertowania/rekordowania
  scrape_timeout: 10s         # maksymalny czas oczekiwania na odpowiedź targetu
  external_labels:            # etykiety dodawane do KAŻDEJ metryki wysyłanej na zewnątrz
    cluster: "prod-warszawa"
    replica: "prometheus-01"
```

- **`scrape_interval`** — jak często Prometheus odpytuje endpointy `/metrics`. Wartość zbyt niska zwiększa obciążenie targetów i rozmiar TSDB; zbyt wysoka pogarsza rozdzielczość danych i czas reakcji alertów.
- **`evaluation_interval`** — częstotliwość, z jaką silnik reguł sprawdza warunki reguł alertowania i rekordowania. Zwykle równa `scrape_interval`.
- **`external_labels`** — kluczowe przy federacji, remote_write do Thanosa/Mimira albo przy wielu instancjach Prometheusa w organizacji — pozwalają jednoznacznie zidentyfikować pochodzenie serii po agregacji danych z wielu klastrów.

## Sekcja `scrape_configs`

Lista "jobów" — logicznych grup targetów scrapowanych w ten sam sposób. Każdy job ma unikalną nazwę (`job_name`), która trafia jako etykieta `job` do każdej zebranej metryki.

```yaml
scrape_configs:
  - job_name: "prometheus"          # self-monitoring
    static_configs:
      - targets: ["localhost:9090"]

  - job_name: "node-exporter"
    scrape_interval: 10s             # nadpisanie interwału globalnego dla tego joba
    static_configs:
      - targets:
          - "10.0.1.11:9100"
          - "10.0.1.12:9100"
        labels:
          env: "production"

  - job_name: "app-api"
    metrics_path: "/actuator/prometheus"   # niestandardowa ścieżka (domyślnie /metrics)
    scheme: "https"                        # domyślnie http
    static_configs:
      - targets: ["api.internal.local:8443"]
```

- **`job_name`** — wymagany, unikalny w ramach pliku; staje się wartością etykiety `job`.
- **`static_configs`** — najprostsza forma service discovery: statyczna lista `targets` (host:port). Produkcyjnie zastępowana zwykle przez dynamiczne mechanizmy (`kubernetes_sd_configs`, `file_sd_configs`, `consul_sd_configs`), ale `static_configs` pozostaje fundamentem, na którym opierają się wszystkie pozostałe metody.
- **`metrics_path`** — endpoint HTTP, z którego pobierane są metryki (domyślnie `/metrics`); wiele aplikacji (np. Spring Boot Actuator) eksponuje metryki pod inną ścieżką.
- **`scheme`** — `http` (domyślnie) lub `https`; przy `https` zwykle towarzyszy blok `tls_config` z certyfikatami klienckimi lub `insecure_skip_verify` (tylko do testów).

## Sekcja `rule_files`

Wskazuje pliki (obsługuje wzorce glob) zawierające reguły alertowania i rekordowania, trzymane fizycznie poza `prometheus.yml`.

```yaml
rule_files:
  - "rules/alerting-rules.yml"
  - "rules/recording-rules.yml"
```

Rozdzielenie reguł od głównej konfiguracji ułatwia zarządzanie wersjami (osobne pull requesty), walidację i utrzymanie porządku przy dużej liczbie reguł.

## Sekcja `alerting`

Określa, do których instancji Alertmanagera Prometheus wysyła wygenerowane alerty (ocena reguł z `rule_files` odbywa się lokalnie w Prometheusie — Alertmanager zajmuje się routingiem, deduplikacją i wyciszaniem).

```yaml
alerting:
  alertmanagers:
    - static_configs:
        - targets:
            - "alertmanager-01:9093"
            - "alertmanager-02:9093"
      timeout: 10s
      path_prefix: "/"
      scheme: "http"
```

## Kompletny przykładowy plik

```yaml
# /etc/prometheus/prometheus.yml
global:
  scrape_interval: 15s
  evaluation_interval: 15s
  external_labels:
    cluster: "prod-warszawa"
    replica: "prometheus-01"

rule_files:
  - "rules/alerting-rules.yml"
  - "rules/recording-rules.yml"

alerting:
  alertmanagers:
    - static_configs:
        - targets: ["alertmanager:9093"]

scrape_configs:
  # Monitorowanie samego Prometheusa
  - job_name: "prometheus"
    static_configs:
      - targets: ["localhost:9090"]

  # Metryki systemowe hostów (node_exporter)
  - job_name: "node-exporter"
    static_configs:
      - targets:
          - "10.0.1.11:9100"
          - "10.0.1.12:9100"
        labels:
          env: "production"

  # Metryki aplikacyjne po HTTPS z niestandardową ścieżką
  - job_name: "app-api"
    metrics_path: "/actuator/prometheus"
    scheme: "https"
    tls_config:
      insecure_skip_verify: false
      ca_file: "/etc/prometheus/certs/ca.pem"
    static_configs:
      - targets: ["api.internal.local:8443"]
```

## Przeładowanie konfiguracji

Zmiana `prometheus.yml` nie wymaga pełnego restartu procesu — dostępne są trzy metody:

1. **Sygnał SIGHUP:**
   ```bash
   kill -HUP $(pgrep prometheus)
   ```
2. **API reload** (wymaga flagi startowej `--web.enable-lifecycle`):
   ```bash
   curl -X POST http://localhost:9090/-/reload
   ```
3. **Restart usługi systemd** (metoda "brutalna", zawsze działa, ale powoduje krótką przerwę w scrapowaniu):
   ```bash
   sudo systemctl restart prometheus
   ```

W praktyce produkcyjnej preferuje się metodę 2 (API reload) — jest bezprzestojowa i łatwa do zautomatyzowania w pipeline CI/CD po walidacji configu.

## Walidacja konfiguracji — promtool

Przed każdym reloadem konfigurację należy zwalidować narzędziem `promtool`, dołączonym do dystrybucji Prometheusa:

```bash
# Walidacja składni i semantyki prometheus.yml
promtool check config /etc/prometheus/prometheus.yml

# Walidacja plików z regułami (składnia PromQL, poprawność etykiet)
promtool check rules /etc/prometheus/rules/alerting-rules.yml

# Test reguł alertowania na przygotowanych danych testowych
promtool test rules /etc/prometheus/tests/alert_tests.yml
```

`promtool check config` weryfikuje nie tylko poprawność YAML, ale też m.in. istnienie plików wskazanych w `rule_files`, poprawność referencji w `scrape_configs` oraz zgodność ze schematem konfiguracyjnym danej wersji Prometheusa.

## Checklist dobrych praktyk

- [ ] `external_labels` ustawione zawsze, gdy dane trafiają do federacji, `remote_write` lub jest więcej niż jedna instancja Prometheusa w organizacji.
- [ ] `job_name` nazwany opisowo i konsekwentnie (np. `<aplikacja>-<środowisko>`), bo trafia bezpośrednio do etykiety `job` używanej w PromQL.
- [ ] Reguły trzymane w osobnych plikach (`rule_files`), nie w samym `prometheus.yml`.
- [ ] Każda zmiana configu poprzedzona `promtool check config` — najlepiej jako krok w CI przed mergem.
- [ ] Reload przez `--web.enable-lifecycle` + `POST /-/reload` zamiast pełnego restartu usługi, gdy zależy na ciągłości scrapowania.
- [ ] `scrape_timeout` zawsze mniejszy niż `scrape_interval` dla danego joba, inaczej konfiguracja zostanie odrzucona przy starcie.
